# ARCHITECTURES.md

Living documentation of how Rogue Emblem is structured. This tracks the _shape_ of the system — modules, their responsibilities, and how they connect — not implementation detail that's better read from the code itself. Per-class numbers (stats, growths, caps, weapons, skills) and the weapon table are tabulated in `UNITS.md`, which `src/game/unitsDoc.test.ts` keeps in sync with the code.

## Stack

- [Phaser 3](https://phaser.io/) for the game world: tilemap, sprites, animations, camera, map input, and the game loop.
- [React](https://react.dev/) for UI and the page around the game: the header, HUD panels, menus, dialogs — anything that's DOM-shaped rather than world-shaped. React renders the whole page, including the box the Phaser canvas mounts into and a DOM overlay on top of it.
- [Vite](https://vitejs.dev/) for dev server (hot reload) and production bundling. The dev server also takes the config editor's saves (`vite/saveConfigs.ts`).
- [TypeScript](https://www.typescriptlang.org/) in `strict` mode for all source. Vite strips types; `tsc` (`npm run typecheck`, and the first step of `npm run build`) only type-checks.
- [Vitest](https://vitest.dev/) for unit tests.
- [Prettier](https://prettier.io/) formats code and Markdown (`npm run format`); CI fails on unformatted files.
- [GitHub Actions](https://docs.github.com/actions) (`.github/workflows/deploy.yml`) runs the tests, builds, and deploys to GitHub Pages on every push to `main`. Vite builds with a relative `base` so the game works from the Pages subpath.

## Layering

The codebase is split into layers that don't reach into each other's internals:

- **Pure game logic** (`src/game/`) — plain TypeScript functions and data, no Phaser imports, no rendering, no hidden state. Every rule of the game (grid layout, movement, combat, turn order, etc.) belongs here so it can be unit tested without spinning up a `Phaser.Game`.
- **Phaser presentation** (`src/scenes/`) — Scenes are the thin glue layer. They call into `src/game/` for state and rules, then use Phaser APIs to draw the result and handle input. Game rules should never be implemented inline in a scene.
- **Bridge** (`src/bridge/`) — framework-agnostic store that Phaser writes to and React reads from. Neither Phaser nor React imports the other; this is the only point of contact.
- **React UI** (`src/ui/`) — components that render UI state from the bridge store. No game rules here either; components display snapshots and send player input (mouse clicks on menus, right-click cancel) back as commands through the bridge.

```
 src/game/  ◄── scenes call rules
     ▲
     │
 src/scenes/ ──setState(snapshot)──► src/bridge/gameStore ──useSyncExternalStore──► src/ui/
  (Phaser)                            (plain TS store)                              (React)
     ▲                                                                                 │
     └──────────────────── src/bridge/commands (send / subscribe) ◄────────────────────┘
```

```
src/
  game/       pure logic + data in TypeScript (tested with Vitest, no Phaser dependency)
    warband/  Warband Mode's own rules: regions, the regions file, a stage's battle
  scenes/     Phaser.Scene subclasses (rendering + input, calls into src/game/)
  bridge/     Phaser → React state store, React → Phaser command channel (plain TypeScript, tested with Vitest)
  ui/         React components: the page layout, sidebar, and HUD overlay
  assets/     art/tileset source files
  data/       authored content loaded at build time: characters, dialog files (see src/data/README.md)
  main.ts     composition root — builds Phaser.Game, mounts the React UI
```

## Modules

### `src/game/grid.ts`

Pure grid data structure for the tactics board. Grid state is `{ width, height, cells }`, cells stored row-major, each cell `{ x, y, terrain, unitId }`. All mutator-shaped functions (`setTerrain`, `setUnit`) return a **new** grid rather than mutating the input.

Key functions: `createGrid`, `isInBounds`, `getCell`, `setTerrain`, `setUnit`, `moveUnit` (relocates a unit id, throwing if the source is empty or the target occupied), `findUnit` (where a unit id stands, or `null`), `getCornerTiles` (the first/last N tiles in reading order from the top-left/bottom-right corner), `getNeighbors` (orthogonal only — no diagonal movement), `gridToWorld` / `worldToGrid` (grid coordinates ↔ pixel coordinates), `worldToTile` (the tile under a pixel, or `null` off the grid), `getDistance` (orthogonal/Manhattan steps between two tiles, used for movement adjacency and attack range), `isSameTile` and `findTileAt` (the first entry of a tile list standing on a given tile, or `null`).

Tested in `src/game/grid.test.ts`.

### `src/game/terrainMap.ts`

`parseTerrainMap(rows, legend)` builds a grid from a text layout — one string per row, one character per tile — so maps can be written as data that looks like the map. `DEFAULT_TERRAIN_LEGEND` maps `.` to grass, `~` to water, `,` to dirt and `#` to wall. Throws on an empty map, ragged rows, or a character the legend doesn't define. Tested in `src/game/terrainMap.test.ts`.

### `src/game/tileset.ts`

Names the art each piece of the map draws with, so scenes reference terrain/units/UI elements by name instead of magic frame numbers or file names. `TILE_SIZE` (32px) is the map tile, matching the overworld terrain sheet; `TERRAIN_SHEET` names that sheet's texture and size, `TERRAIN_BASE_TILE` the grass tile under every cell, and `TERRAIN_AUTOTILES` each autotiled terrain's source tiles and animation (see `autotile.ts`; water, dirt and dark-grass `meadow`). `FOREST_ART` and `MOUNTAIN_ART` list the overlay variants for forest and mountain cells, `BUILDING_ART` where each building kind sits on the sheet, and `BUILDING_PALETTES` the ten building colors (`a-stone` … `b-orange`: a building column offset, a rampart wall group, and whether it has flags), with `DEFAULT_BUILDING_PALETTE` `a-stone`; `mapArt.ts` turns these into sprites. `CURSOR_ANIMATION` lists the two sheet tiles the cursor pulses between and how long each shows, and `ARROW_TILES` the sheet tile for each `moveArrow.ts` piece. `UNIT_SPRITES` (keyed by unit class, so every unit of a class looks alike on either side; `getUnitSprite(unitClass)` looks one up, falling back to `DEFAULT_UNIT_SPRITE`) names each class's unit art, whose sheets (one per animation in `UNIT_ANIMATIONS`, keyed by `unitSheetKey`) are standalone images listed in `src/assets/sprites.ts`; `UNIT_SHEET` says how those sheets are cut (a row per facing), and `UNIT_SHADOW` sets the size, placement, and opacity of the blob shadow under units. Tested in `src/game/tileset.test.ts` (every unit animation has an image; cursor and arrow tiles are on the sheet).

### `src/game/pixelShapes.ts`

Pure pixel-art rasterizing. `getEllipseSpans(width, height)` returns the rows of pixels an ellipse covers as `[{ y, x, width }]` spans, so scenes can draw crisp shapes with rectangles instead of anti-aliased curves. Tested in `src/game/pixelShapes.test.ts`.

### `src/assets/sprites.ts`

`SPRITE_URLS`: texture key → imported URL for every standalone sprite image (units). The only module that imports sprite files — GridScene preloads each under its key, and the React `UnitSprite` shows one by key.

### `src/game/autotile.ts`

Blob autotiling: a terrain is drawn in its own cells, with its border inside the edge cells, over a grass base. Each cell is drawn as four quarter tiles. `getQuarterShapes(grid, x, y, terrain)` names each quarter's shape from its two side neighbors and the diagonal between them (`'outer'`, `'horizontal'`, `'vertical'`, `'inner'`, `'full'`), which covers all 47 neighbor combinations. Cells off the map take the nearest cell on it, so terrain reads as continuing past the edge. `getShapeTile` picks the sheet tile (from the set's plain 3x3 `block` or its `inner` corner tile) whose same quarter draws that shape. `getQuarterFrames` returns the four frame numbers on the sheet cut into half-size tiles, shifted along the sheet for an animation frame. `getQuarterFrameMap(grid, terrain, autotile, sheetColumns, animationFrame)` lays those out for the whole map as rows of half-size tiles (each cell's quarters in its own 2x2 block, `-1` where the cell isn't that terrain), the data GridScene turns into a tilemap layer per terrain. `getTileFrame` numbers whole tiles. Tested in `src/game/autotile.test.ts`.

### `src/game/cursor.ts`

Pure logic for the map cursor: a `{ x, y }` grid position. `moveCursor` takes a delta and clamps the result to the grid bounds; it never mutates the cursor it's given. Tested in `src/game/cursor.test.ts`.

### `src/game/actionMenu.ts`

Pure state for the unit action menu. `UNIT_ACTIONS` lists the offered actions (Attack, Skill, Item, Wait — moving happens before the menu opens) as `{ id, label }`; `getUnitActions({ hasSkills, hasItems, hasWeapons })` returns them for a particular unit, with Attack marked `disabled` when it has no weapon it can wield, Skill until the unit knows a skill, and Item when it carries no consumables; a menu is a frozen `{ actions, selectedIndex }`. `moveSelection` moves the highlight with wrap-around and returns a new menu (or the same one if nothing changed); `selectIndex` jumps straight to an index (ignoring out-of-range ones); `getSelectedAction` reads the highlighted action. The helpers work on any action list, so other menus (e.g. the title menu) reuse them. The module only tracks selection — carrying out an action belongs to whoever consumes the choice. Tested in `src/game/actionMenu.test.ts`.

### `src/game/titleMenu.ts`

`TITLE_ACTIONS` — the title screen's menu entries (Story Mode, Warband Mode, Training, Settings) as frozen `{ id, label }` — and `SETTINGS_ACTIONS`, the Settings submenu's entries (Game Configs). Selection uses the `actionMenu.ts` helpers. Tested in `src/game/titleMenu.test.ts`.

### `src/game/deployment.ts`

Pure rules for the **deployment phase** — the pre-battle step where the player places units from their roster onto a deployment zone (a list of `{ x, y }` tiles). `getDeploymentActions({ canStart })` builds the Place Units / Start menu entries (Start carries `disabled` until a unit is placed). `canPlaceUnit` accepts zone tiles that are empty or already hold that unit; `placeUnit` puts a unit there, lifting it off its previous tile (throws on an invalid tile). `isPlaced`, `canStartBattle(grid, roster)` (at least one roster unit on the map), and `getFirstOpenTile(grid, zone)` round it out. Each map caps how many units can be deployed: `getDeploymentLimit(roster, zone, maxDeployed)` is the level's `maxDeployed` capped by roster and zone size, `countPlaced` counts roster units on the map, `canDeployUnit(grid, roster, limit, unitId)` lets a placed unit always move but a new one only while a slot is free, and `isDeploymentComplete(grid, roster, limit)` says every slot is filled. Tested in `src/game/deployment.test.ts`.

### `src/game/dialog.ts`

Pure state for conversations. A script is a list of lines `{ speaker, team, unitClass, side, portrait, text }` (`portrait` is the speaker's portrait sprite key or null, and `unitClass` picks the unit art standing in when there's none; `side` is `'left'` | `'right'`, where the portrait sits). `createDialog(lines)` starts a frozen `{ lines, index, revealed }` (throws on an empty script, a line without text, or an unknown side). Text types out at `DIALOG_CHARS_PER_SECOND`: `getRevealDurationMs` is how long a line takes and `getRevealedLength` how much shows after a given time. `advanceDialog(dialog, elapsedMs)` is what confirm does — finish typing a line that's still typing, else move to the next line, or return `null` after the last. Tested in `src/game/dialog.test.ts`.

### `src/game/dialogScript.ts`

Parses dialog written as text into those scripts. `parseCharacters(json)` checks a character roster (`{ id: { name, team, unitClass, portrait } }`, `unitClass` and `portrait` defaulting to null). `parseDialogScript(text, characters, source)` reads a dialog file: `[section]` headers name when a conversation plays (`isDialogTrigger`: `opening`, `victory`, `defeat`, `turn N`), and each `speaker_id: text` row (optionally `speaker_id (left|right): text`) becomes a line with the character's name, team, unit class, portrait, and their team's side from `DEFAULT_SIDES` (player left, enemy right). Comments (`#`) and blank lines are skipped. `turnTrigger(n)` names a turn's section and `getTriggeredDialog(dialogs, trigger)` looks a conversation up (null when there's none). It returns `{ trigger: lines }`, frozen, and throws with `source:line` on an unknown speaker, section, or side, a repeated or empty section, a line before any section, or a row that isn't speech. Tested in `src/game/dialogScript.test.ts`.

### `src/data/`

Authored content, documented for writers in `src/data/README.md`. `characters.json` is everyone who can speak; `dialog/*.txt` holds each level's conversations, one file per level; `regions.json` is Warband Mode's regions (Meadowlands, Lakeside, Deep Woods, Highlands, Fortress), in the format `src/game/warband/regionsFile.ts` reads. `regions.ts` loads it (`REGIONS_TEXT` as written, `REGION_SETTINGS` and `REGION_CONFIGS` parsed, skipping the per-region map check, which `src/data/regions.test.ts` runs instead). `dialogs.ts` finds every dialog file with `import.meta.glob` (so new files need no registration), parses them against the roster, and exports `CHARACTERS`, `DIALOG_TEXTS` (file name → the file's raw text) and `DIALOGS` (file name → `{ trigger: lines }`, a `DialogFiles`, e.g. `DIALOGS.demo.opening`). Uploads from the config editor live here too, in the browser's `localStorage` through `customStorage.ts` (`browserStorage()`, and `createStoredText(storage, key)`: one file's text, with missing or blocked storage reading as empty and writes reporting failure). `customRegions.ts` keeps the uploaded regions file (under its Dungeon Mode storage key, so older uploads still play; `getActiveRegionSettings()` parses it, falling back to `REGION_SETTINGS` if it no longer parses), and `customContent.ts`'s `getActiveContent()` gathers every upload into the `GameContent` GridScene builds battles from. `customDialogs.ts` keeps dialog files the player uploads in the config editor: `createCustomDialogStore(storage)` saves, loads and removes uploaded text by file name in `localStorage` (guarded, so missing or blocked storage reads as empty and writes report failure), and `getActiveDialogs()` is `DIALOGS` with each upload that still parses in place of the built-in file of the same name — what GridScene builds levels with. Tested in `src/data/customDialogs.test.ts`. A broken file throws on import, which fails `src/data/dialogs.test.ts`; that test also checks every portrait key is in `SPRITE_URLS` and every `unitClass` is in `UNIT_CLASSES`. GridScene plays every trigger (see **Dialog** under GridScene).

### `src/game/demoLevel.ts`

`createDemoLevel()` builds the starting state of the demo battle (Level 1) as `{ grid, units, roster, deploymentZone, maxDeployed, dialogs, decorations, structures }` (`maxDeployed` is `DEMO_MAX_DEPLOYED`): the terrain comes from `DEMO_MAP` (a text layout parsed by `terrainMap.ts`, 16x14 tiles) — a grass field with a one-tile dirt path running north from the south edge to a paifang gate. The gate is a `structures` entry (`STRUCTURE_POSITIONS`, `{ x, y, structure }` by top-left tile, drawn from `STRUCTURE_SPRITES` in `tileset.ts`); every tile under it is walkable (the path down its middle, grass under its sides). `decorations` (`TREE_POSITIONS`) puts a stand of gold ginkgos right behind the gate and three clumps of green ginkgos in the field. Three enemy `Soldier`s hold the gate at `ENEMY_POSITIONS`, the player's roster (three named `Villager`s from `PLAYER_ROSTER`) is kept off the map, and `DEPLOYMENT_ZONE` (the south end of the path) is where they're placed. `dialogs` is `DIALOGS.demo` (from `src/data/dialog/demo.txt`), its conversations by trigger. `units` is the `unitId -> Unit` registry for both sides. A level may also carry `buildings` (`{ x, y, building }`, see `buildings.ts`) and a `palette` (a `BUILDING_PALETTES` name) that every building and wall is drawn in; the demo has neither. Stand-in until levels are loaded from data. Tested in `src/game/demoLevel.test.ts`.

### `src/game/unitClasses.ts`

`UNIT_CLASSES` — the unit classes the game can build, in menu order, as frozen `{ id, label, create(options) }` (the villager, then the soldier). `createUnitOfClass(classId, options)` builds a fresh `Unit` of a class by id (throws on an unknown one), so code that offers a choice of class doesn't import the subclasses. Tested in `src/game/unitClasses.test.ts`.

### `src/game/rng.ts`

Seeded randomness. `createSeededRng(seed)` returns an `Rng` (Mulberry32, numbers in [0, 1) like `Math.random`) that gives the same sequence for the same seed. It comes with `randomInt`, `randomItem` and `shuffle` helpers that take an `Rng`, and `randomSeed()`, the one unseeded function, which picks a fresh seed (for a new Warband stage's map or a new preview map). Tested in `src/game/rng.test.ts`.

### `src/game/mapGen.ts`

Pure procedural terrain built in layers from an `Rng`. `generateTerrain({ width, height, ... }, rng)` returns `{ grid, path, buildings }`; the options set how many of each layer to try and their sizes, with `MAP_GEN_DEFAULTS` for any left unset. It fills the map with grass, then `carvePath` cuts a one-tile-wide dirt path from the middle of the south edge to the north edge, never jogging sideways in two rows running so the path never forms a 2x2 block (the dirt autotile only has notched full tiles). On top of that: `placeCastle` stands a castle beside the path two or three rows from the north edge; `placeRuin` lays a one-tile-thick ring of `wall` (4–5 tiles a side, a tile in from the map's sides, with a doorway in its south side) around a temple or fort; `placeBuildings` scatters a few lone buildings (`FIELD_BUILDINGS`) on grass, never side by side; then `growPatch` grows blobs of `water`, `mountain`, `forest` and `meadow` over the remaining grass, each from a random grass tile that layer may grow on, so every patch asked for appears while there's room. Everything but the path stays out of the top row and the bottom two rows (the deployment area). Impassable terrain (water, mountains, walls) keeps a tile clear of the path, so the two ends of the map are always connected. Every building and the ruin keep a tile of open ground around them, so no patch crowds them or sits under their overhanging art. `getReachable(grid, start)` floods the walkable tiles, and `terrainToRows(grid)` prints a grid back as text rows (the inverse of `terrainMap.ts`'s default legend). Tested in `src/game/mapGen.test.ts`.

### `src/game/buildings.ts`

`BUILDING_KINDS` — every kind of building a map can hold (house, fort, temple, castle, …) — and `BuildingPlacement` (`{ x, y, building }`). Each building stands on one walkable tile; its art lives in `tileset.ts`.

### `src/game/mapArt.ts`

Pure picking of the one-tile overlays drawn from the terrain sheet over the terrain. `getFeatureSprites(grid, FOREST_ART, MOUNTAIN_ART)` gives a forest variant per forest cell and stacks mountains a column at a time (body, or body with the next peak baked in when a mountain is south; a cap in the cell north of a column's top, or the forest-with-peak tile when that cell is forest). `getBuildingSprites(buildings, palette, BUILDING_ART)` gives each building, a tall building's top over the cell north of it, and the palette's flags, all in one palette. `getWallAutotile(palette)` is the `wall` terrain's rampart autotile in that palette. Variants are picked by `pickVariant(x, y, count)`, a position hash, so a map always draws the same. Each sprite has a layer: `ground` (under units), `cap` (art poking into the cell north, still under units) or `roof` (over units). Tested in `src/game/mapArt.test.ts`.

### `src/game/battleSetup.ts`

Which battle the map runs and what follows it. `BattleSetup` is `{ mode: 'story', chapter }`, `{ mode: 'training', unitClass }` or `{ mode: 'warband', seed, stage }` (the store's `battleSetup` re-exports the type). `STORY_CHAPTERS` lists Story Mode's chapters in order as `{ name, createLevel(content) }`, each picking its own dialog file (just chapter 1, the demo battle, for now). `GameContent` (`{ dialogs, regions }`) is the authored data battles are built from, `DEFAULT_CONTENT` the built-in files; `createBattleLevel(setup, content = DEFAULT_CONTENT)` builds the level a setup names from it (story chapters' and training's dialog, a Warband stage's region), so uploaded configs can replace the built-in ones, and `describeBattle(setup, content)` names Warband stages from it too. `getNextBattle(setup, seed)` is where a victory leads: the next story chapter until the last one, then null (back to the title); the next Warband stage on a fresh map from `seed`, without end (for now); null after training. `describeBattle(setup)` titles a battle ("Chapter 1: The Old Gate", "Stage 2: Lakeside", "Training"). `FIRST_STORY_CHAPTER` and `firstWarbandStage(seed)` are what the title screen starts. `regionPreview(index, seed, settings)` is the battle that shows region `index` (its first stage, on the map `seed` makes, so the same map `createStageLevel` makes from that region), or null for a region that doesn't exist; the config editor's map preview runs it. Tested in `src/game/battleSetup.test.ts`.

### `src/game/objectives.ts`

A battle's objective, as data. `Objective` is `{ kind: 'rout' }` for now (`ROUT`, also `DEFAULT_OBJECTIVE` for levels that don't set one); a level's optional `objective` (on `Level`, and on a `RegionConfig` for special Warband maps) picks it. `describeObjective(objective)` gives the Objective screen's words as frozen `{ goal, defeat }`. The win/loss check is still `getBattleOutcome` in `turns.ts`. Tested in `src/game/objectives.test.ts`.

### `src/game/warband/regions.ts`

Warband Mode's regions: the shape of the per-stage map settings and the rules for picking a stage's region; the built-in regions themselves are data, in `src/data/regions.json` (see `src/data/`). A `RegionConfig` is `{ name, description?, terrain, enemies, treeChance, palette, objective? }`, where `terrain` is the `generateTerrain` options (map size included), `enemies` is a list of `EnemyGroup`s (see `enemySpawns.ts`), and `RegionSettings` is `{ stagesPerRegion, regions }`. `getRegionConfig(stage, regions, stagesPerRegion)` picks stage `stage`'s region (1-based): every `stagesPerRegion` stages move on to the next region, and stages past the end reuse the last one; `getStageRegion(stage, settings)` reads a stage's region from settings and `getRegionStages(index, count, stagesPerRegion)` says which stages a region covers. Tested in `src/game/warband/regions.test.ts`.

### `src/game/warband/regionsFile.ts`

`RegionSettings` as a JSON file players can write and upload. `parseRegionSettings(text)` checks every field against `REGION_LIMITS` (whole numbers in range, `[min, max]` size pairs, chances 0–1, known palettes, no unknown keys so typos fail), throwing with the field's path (`regions[2].terrain.lakes must be …`), then generates each region on a few seeds so an accepted file can't break a run or place fewer enemies than its groups ask for; `explainEnemyShortfall` says why not, aimed at the setting to change (a max distance closer than the area's nearest tile, a min distance past its farthest, an area nothing can reach, a count bigger than the spots that fit, or groups crowding each other out). Older files still read: Dungeon Mode's `{ floorsPerConfig, floors }` (its errors then name those keys), an enemy group's `region` as its `area`, and `enemyCount: n` as one group of `n` in `NORTH_THIRD`. `formatRegionSettings(settings)` writes settings back out, always in the current shape (the built-in ones are the editor's download), through `formatRegionsJson(json)`, which lays out any JSON, a draft being edited included, the way Prettier keeps the file: anything that fits on its line on one line. Tested in `src/game/warband/regionsFile.test.ts`.

### `src/game/enemySpawns.ts`

Pure enemy placement for generated maps. An `EnemyGroup` is `{ count, area?, minDistance?, maxDistance? }`: `area` (a `SpawnArea`) is a box as `[from, to]` fractions of the map's columns (`x`) and rows (`y`), and the distances are walking steps from the deployment zone. `getWalkingDistances(grid, starts)` is a breadth-first search giving each reachable tile's step count from the nearest start (impassable terrain blocks). `isInArea(p, area, width, height)` checks a tile against a box (tiles from `from × size` up to, not including, `to × size`, rounded down). `pickEnemyTiles(grid, groups, deploymentZone, rng)` returns one list of tiles per group, in order: each group's shuffled pick of reachable tiles outside the zone that pass its limits and that no earlier group took, shorter than `count` when too few qualify. `countEnemies(groups)` totals them, and `NORTH_THIRD` is the area older configs' enemies stood in. `getGroupRoom(grid, group, deploymentZone)` measures one group's room on its own (`{ inArea, nearest, farthest, fits }`: reachable tiles in its area, the fewest and most steps to them, and how many are within its distances), for explaining a group that won't fit. The Regions page's cards describe each group with `describeEnemyGroup` (`src/ui/enemyGroups.ts`). Tested in `src/game/enemySpawns.test.ts`.

### `src/game/warband/stageLevel.ts`

A Warband Mode stage's battle. `createStageLevel(seed, region)` returns the same shape as `createDemoLevel`, built from the seed and a `RegionConfig`. The terrain and buildings come from `generateTerrain` with `region.terrain`, and the level's `palette` is `region.palette`. The deployment zone is the path's south end and the tile on each side of it. An enemy `Soldier` stands on each tile `pickEnemyTiles` finds for `region.enemies` (numbered `enemy-1`, `enemy-2`, … in group order), and green ginkgos are scattered on grass that no building, overhang or mountain peak is drawn on (`region.treeChance`). The roster is the demo's `PLAYER_ROSTER`, deploying up to `WARBAND_MAX_DEPLOYED`, and there are no dialogs or structures. The title screen's Warband Mode sets `battleSetup` to `firstWarbandStage(randomSeed())`, and `createBattleLevel` builds each stage with `getStageRegion(stage, content.regions)`. Tested in `src/game/warband/stageLevel.test.ts`.

### `src/game/trainingLevel.ts`

The Training mode's practice battle. `getTrainingActions()` lists one `{ id, label }` menu entry per unit class. `createTrainingLevel(unitClass)` returns the same `{ grid, units, roster, deploymentZone, maxDeployed }` shape as `createDemoLevel` (empty roster and zone, `maxDeployed` 0): a 3x3 grass field (`TRAINING_MAP`) with the chosen class on the player team at `TRAINEE_POSITION` (west edge) and a "Sparring Partner" of the same class on the enemy team at `SPARRING_PARTNER_POSITION` (east edge). Both start on the map, so the roster and deployment zone are empty; `dialogs` is `getTrainingDialogs(unitClass)`: `DIALOGS.training` with the chosen class set as every line's `unitClass`, so the sparring partner's portrait art matches its class. Tested in `src/game/trainingLevel.test.ts`.

### `src/game/camera.ts`

`getFitZoom(mapSize, tileSize, canvasSize, maxZoom)` — the largest whole-number zoom at which the map fits the canvas, capped at `maxZoom` and never below 1. GridScene caps it at 2x, which every map up to 30x22 tiles reaches; only larger maps zoom out further. Tested in `src/game/camera.test.ts`.

### `src/game/pauseMenu.ts`

`PAUSE_ACTIONS` — the pause menu's entries (End Turn, Main Menu, Settings) as frozen `{ id, label }`. Selection uses the `actionMenu.ts` helpers. Tested in `src/game/pauseMenu.test.ts`.

### `src/game/structures.ts`

`getStructureTiles(sprite, x, y)` lays out a multi-tile structure (a `STRUCTURE_SPRITES` entry) placed by its top-left tile: one `{ x, y, frame, overUnits }` per tile in reading order, `frame` being the piece of the image cut into one-tile frames and `overUnits` true for its top `roofRows` rows. Tested in `src/game/structures.test.ts`.

### `src/game/movement.ts`

Pure movement rules. `TERRAIN_MOVE_COSTS` maps terrain to the movement points spent entering it (grass, dirt and meadow 1, forest 2; water, walls and mountains `Infinity` = impassable; unlisted terrain costs 1). `getMovementRange(grid, origin, movement, { terrainCosts, canPassThrough })` runs Dijkstra over orthogonal neighbors and returns every reachable destination as `[{ x, y, cost }]`, including the origin at cost 0. Other units block unless `canPassThrough(unitId)` allows them, and occupied tiles are never destinations. `getMovePath(grid, origin, destination, movement, options)` uses the same search to return the cheapest route as a list of orthogonally adjacent tiles from origin to destination (one entry per step), or `null` if the destination isn't in range — so the range and the path can never disagree. `extendMovePath(grid, path, target, movement, options)` updates a planned route as the cursor moves: it cuts back to a tile already on the path, appends an adjacent step while the traced route stays within movement, and otherwise falls back to `getMovePath` (leaving the path unchanged if the target is unreachable), so the route follows the way the player traced it. `getPathCost` sums the cost of the tiles a path enters. `canMoveAlongPath(range, path, to)` is whether a move can be confirmed: `to` must be in the movement range (not a tile the mover can only pass through) and where the planned route ends. Tested in `src/game/movement.test.ts`.

### `src/game/teams.ts`

Pure team relations over the `unitId -> unit` registry (anything with a `team`). `getTeamUnitIds(units, team)` lists a team's unit ids in registry order (the enemy phase's queue), `isAllyOf(units, team, unitId)` says a unit on `team` may walk through that unit (GridScene's `canPassThrough` for movement), and `isHostileTo(units, team, unitId)` says it may attack it (any other team). Ids missing from the registry are neither. Tested in `src/game/teams.test.ts`.

### `src/game/turns.ts`

Pure turn rules. A battle alternates phases in `PHASE_ORDER` (player, then enemy); the pair makes one turn. Turn state is a frozen `{ turn, team, moved, done }` from `createTurnState(turn, team)`: `moved` / `done` list the unitIds that have moved or finished this phase. `markMoved`, `unmarkMoved` (takes a move back, unless the unit is already done), and `markDone` (which also counts as moved) return new states; `hasMoved` / `isDone` read them; `isPhaseOver(state, unitIds)` is true once every one of the phase team's units in play is done (trivially true for none); `nextPhase` advances player → enemy (same turn) → player (next turn) with a clean slate. `getBattleOutcome(units)` returns `'victory'` when no enemy is alive, `'defeat'` when no player unit is (defeat wins a tie), else `null`. Tested in `src/game/turns.test.ts`.

### `src/game/enemyAI.ts`

Pure enemy decision-making. `planRushAction(grid, origin, unit, isHostile, movementOptions)` returns `{ path, target }` for one enemy, striking with its equipped weapon's range (min and max; an enemy without a weapon never finds a target and stays put): if any tile in its movement range lets it attack a hostile unit, it takes the cheapest such tile (so an enemy already adjacent stays put) and targets that unit; otherwise it finds the nearest tile it could attack from by walking distance (ignoring its movement limit, respecting terrain and blockers), follows the route there, and stops at the furthest tile it can reach and stand on this phase (allies can be walked through, not stopped on). With no reachable hostile it stays put (`path: [origin]`, `target: null`). Built on `movement.ts` and `combat.ts`. Tested in `src/game/enemyAI.test.ts`.

### `src/game/moveArrow.ts`

Pure logic for the movement arrow. `getArrowPieces(path)` returns `[{ x, y, piece }]` for every tile of a route after the origin: an arrowhead (`head-up`/`down`/`left`/`right`) on the last tile pointing the way it last stepped, and on the tiles before it a straight segment or corner named for the two tile edges it joins (`up-down`, `left-right`, `up-left`, `down-right`, …). `ARROW_TILES` in `tileset.ts` maps each piece name to its tile on the terrain sheet. Tested in `src/game/moveArrow.test.ts`.

### `src/game/keyRepeat.ts`

Pure key repeat for the arrow keys. `updateKeyRepeat(state, { isDown, justPressed }, deltaMs, timing)` advances one frame and returns `{ state, step }`, `step` being a `DIRECTIONS` entry or null: a press steps at once (even a tap shorter than a frame), holding repeats after `KEY_REPEAT.delayMs` and then every `intervalMs`, at most one step per frame. The most recently pressed key still held sets the direction, so the cursor never moves diagonally; letting go of it hands back to the older key after the delay. `GridScene.readArrowKeys` feeds it Phaser's key states each frame, so holding an arrow moves the cursor and menu highlights continuously. Tested in `src/game/keyRepeat.test.ts`.

### `src/game/facing.ts`

Pure logic for which way a unit faces (`'down'`, `'left'`, `'right'`, `'up'`, the rows of a unit sheet). `getStepFacing(from, to)` names a step's direction (null for a step in place), and `getPathFacings(path, initial)` gives the facing for each step of a route, which `GridScene.walkSprite` plays as the unit walks. Tested in `src/game/facing.test.ts`.

### `src/game/combat.ts`

Pure combat rules. `getAttackRange(grid, origin, maxRange, minRange = 1)` returns every in-bounds tile within that orthogonal distance band as `[{ x, y }]` — never the attacker's own tile, and not blocked by terrain or units. `getAttackTargets(grid, origin, maxRange, isHostile, minRange)` narrows that to occupied tiles whose unit `isHostile(unitId)` accepts, as `[{ x, y, unitId }]`. `getThreatRange(grid, stops, maxRange, minRange)` is the fringe of tiles a unit could strike after moving: every tile in attack range of any of `stops` (its movement range), minus the stops, without duplicates. A fighter brings its stats plus its equipped `weapon` (from `weapons.ts`; null for none) and the `weaponUses` it has left (null for one that never breaks). `DAMAGE_TYPES` maps each damage type to the attacker stat that powers it and the defender stat that guards it (`physical`: `strength` vs `defense`; `magical`: `magic` vs `resistance`), `getDamageType(attacker)` follows the weapon type (`WEAPON_DAMAGE_TYPES`; physical without a weapon, throws on unknown types), and `calculateDamage(attacker, defender)` is power plus weapon might minus guard for that type, floored at 0. `isInStrikeRange(unit, distance)` checks a distance against the unit's weapon `minRange`–`maxRange` (false without a weapon). `getStrikeOrder(attacker, defender, distance)` lists who strikes, in order, as `'attacker'`/`'defender'`: the attacker, the defender if the attacker is within its strike range, then whoever doubles (`canDouble`; the attacker takes precedence, and a defender that can't reach never doubles). Every strike spends a weapon use, hit or miss, so a side's strikes past its weapon's last use are dropped (the weapon broke) — which keeps breakage deterministic and the forecast exact; a side with no weapon never strikes. `resolveCombat(attacker, defender, { distance, rng = Math.random, trueHit = false })` plays that order without mutating anything: each strike rolls to hit against `getHitChance` and, if it lands, to crit against `getCritChance` (×`CRIT_MULTIPLIER`); a miss deals 0, and the exchange stops as soon as someone dies. It returns `{ strikes, attackerHealth, defenderHealth }`, where `strikes` is the ordered `[{ by, target, damage, hit, crit, lethal }]`. The RNG is injected so tests are deterministic. Applying damage is left to the caller (`Unit.takeDamage`). `getCombatForecast(attacker, defender, { distance })` previews the same exchange without rolling: per side `{ health, maxHealth, damage, hit, crit, strikes, counters }`, built from the same `getStrikeOrder`, `calculateDamage`, `getHitChance` and `getCritChance` so preview and outcome can't disagree (`damage` is a landed non-crit strike; a defender that can't reach has `counters: false`, 0 strikes and `null` damage/hit/crit). Tested in `src/game/combat.test.ts`.

### `src/game/combatStats.ts`

Pure Fire Emblem–style combat formulas, all whole percentages. The unit's `weapon` (`{ hit, crit, weight }`, optional) feeds them. `getAttackSpeed(unit)` = `speed − max(0, weight − strength)`; `getHit(unit)` = weapon hit + `skill × 2` + `luck / 2`; `getAvoid(unit)` = attack speed `× 2 + luck`; `getCrit(unit)` = weapon crit + `skill / 2`; `getDodge(unit)` = `luck` (halves round down, missing stats count as 0). `getHitChance(attacker, defender)` and `getCritChance(attacker, defender)` are rate minus the opponent's avoid/dodge, clamped to 0–100. `canDouble(unit, opponent)` is true when the unit's attack speed beats the opponent's by at least `DOUBLE_THRESHOLD` (4). `rollChance(chance, rng, { trueHit })` rolls 0–99 from the injected `rng` and succeeds under `chance`; with `trueHit` it averages two rolls (FE's "2RN"). Tested in `src/game/combatStats.test.ts`.

### `src/game/experience.ts`

Pure Fire Emblem–style experience and growth rules. `getHitExperience(level, enemyLevel)` = `max(1, floor((31 + enemyLevel − level) / 3))` (10 at an even level); `getKillExperience` adds `KILL_BONUS` (20) + 3 per level the opponent is above (never negative). `getCombatOutcome(strikes, side)` reads a `resolveCombat` strike list as `'died'` / `'kill'` / `'hit'` (landed damage) / `'miss'`, and `getCombatExperience(level, enemyLevel, outcome)` turns it into XP (`MISS_EXPERIENCE` 1 for a miss, 0 for a death or at `MAX_LEVEL` 20, at most 100). `addExperience(level, experience, amount, maxLevel)` carries overflow past each `EXPERIENCE_PER_LEVEL` (100) into further levels, stopping at the max with 0 XP. `rollLevelUp(stats, growths, rng, caps)` rolls each of `GROWTH_STATS` once in order — `floor(g/100)` sure points plus one with `(g mod 100)%` chance — never past a cap (health/mana compare their maximums, via `getGrowthStatValue`). `resolveExperienceGain(unit, amount, rng, trees)` combines them without mutating: `{ amount, level, experience, levelUps: [{ level, gains, stats, skills }] }`, with caps applied across consecutive level ups and the skills each new level teaches from `getSkillsLearnedBetween`. Tested in `src/game/experience.test.ts`.

### `src/game/Unit.ts`

Base `Unit` class that specific unit types extend. Holds stats (`name`, `unitClass`, `level` (default 1), `health`/`maxHealth`, `mana`/`maxMana` (default 0), `strength`, `magic`, `skill`, `speed`, `luck`, `defense`, `resistance` (all but `strength` and `defense` default to 0), `movement`, `team`), the `weaponTypes` its class masters (default none), and an `items` inventory of consumables and weapons (from `items.ts`, empty by default). Getters read the equipped weapon off the inventory (`weapons.ts`): `weapon` (the first weapon it can wield, or null), `weaponUses` (its uses left, null if it never breaks), `equippedWeapon` (`{ weapon, index, uses }`) and `wieldableWeapons`; `equip(index)` moves a weapon to the front, and `spendWeaponUse()` wears the equipped one down by a strike and returns `{ weapon, broke }` (a broken weapon leaves the inventory and the next wieldable one takes over). It also has the state changes every unit shares: `isAlive()`, `takeDamage(amount)`, `heal(amount)` (both clamp health between `0` and `maxHealth`), `spendMana(amount)` (throws if the unit can't afford it), `restoreMana(amount)` (clamped to `maxMana`), `useItem(itemId)` (restores a consumable's stat, uses one up, and returns `{ item, amount }` with the amount actually restored; throws if it isn't carried or is a weapon), and `levelUp(gains)` (level + 1 and the stat gains added; health and mana gains raise both maximum and current), and `gainExperience(amount, rng)` (runs `resolveExperienceGain` from `experience.ts`, applies each level up, stores the leftover `experience`, and returns the result). It also holds `experience` (default 0), `growths` and `caps` (default `{}`). No Phaser dependency — subclasses set their class, stat line, growths, caps, weapon types and starting items (`Soldier`: physical, an Iron Spear; `Villager`: physical, Fists). Tested in `src/game/Unit.test.ts`.

### `src/game/Villager.ts`

`Villager` — the player's `Unit` subclass in the demo battle: `unitClass: 'villager'`, default name "Villager". For now `VILLAGER_STATS`, `VILLAGER_GROWTHS` and `VILLAGER_CAPS` copy the soldier's numbers, and it carries `STARTING_ITEMS` unless given other `items`. Tested in `src/game/Villager.test.ts`.

### `src/game/Soldier.ts`

`Soldier` — the basic infantry `Unit` subclass: `unitClass: 'soldier'`, starts at level 1 with the `SOLDIER_STATS` line (10 HP, 5 MP, 4 STR, 0 MAG, 3 SKL, 3 SPD, 2 LCK, 2 DEF, 0 RES, 5 MOV). Carries `STARTING_ITEMS` (a health potion and a mana potion) unless given other `items`. Takes an optional `name` (e.g. "Enemy Soldier") and `level`. Levels up with `SOLDIER_GROWTHS` (70 HP, 40 MP, 45 STR, 5 MAG, 40 SKL, 40 SPD, 30 LCK, 30 DEF, 15 RES, in %) and `SOLDIER_CAPS` (40 HP, 30 MP, 20 for the rest). Tested in `src/game/Soldier.test.ts`.

### `src/game/skills.ts`

Pure skill rules. A skill is `{ id, label, manaCost, range, animation }` plus optional `might` (added to the user's attack power, default 0) and `damageScale` (multiplies the damage, default 1) — every skill's damage is a variant of the user's regular hit (`animation` names the effect the scene plays). `SKILL_TREES` maps each unit class to `[{ level, skill }]`, so every class has its own skills and a unit knows each one whose level it has reached — skills are gained by leveling up rather than stored on the unit. `getLearnedSkills(unitClass, level, trees)` lists the known skills in tree order, `getSkillsLearnedBetween(unitClass, fromLevel, toLevel, trees)` the ones a level up unlocks, `findLearnedSkill(unitClass, level, skillId, trees)` looks one up by id, `calculateSkillDamage(skill, user, defender)` is the user's regular `calculateDamage` (so its weapon's might and damage type count) with `might` added to its attack stat (strength or magic, by damage type), times `damageScale`, rounded up (so a halved hit that would have dealt damage deals at least 1), `canUseSkill(unit, skill)` checks mana, and `getSkillActions(unit, skills)` builds skill menu entries (`{ id, label, manaCost, disabled }`, disabled when unaffordable). The soldier learns `POWER_STRIKE` (2 mana, range 1, might 3 — soldier vs villager deals 6 instead of a regular 3) at level 1; the villager learns `THROW_STONES` (2 mana, range 4, damageScale 0.5 — half its regular damage, rounded up) at level 1. Tested in `src/game/skills.test.ts`.

### `src/game/items.ts`

Pure rules for items. An `Item` is a consumable or a weapon (`weapons.ts`), told apart by `kind`. A consumable is `{ kind: 'consumable', id, label, stat, amount }` — `stat` is what it restores (`'health'` or `'mana'`), `amount` the most it restores per use; `HEALTH_POTION` (+5 HP) and `MANA_POTION` (+3 MP) exist so far, and `STARTING_ITEMS` gives one of each (classes add their weapon). An inventory is a frozen list of `{ item, quantity }` entries — for a weapon, `quantity` is its uses left: `createInventory(entries)` builds one (dropping empty entries; throws past `MAX_INVENTORY_SLOTS`, 6 — each entry takes a slot whatever its quantity), `canAddItem` says whether an item stacks onto an entry (consumables only — weapons never stack) or has a free slot, `addItem(inventory, item, quantity)` returns a new inventory with it stacked or in a new slot (throws when full), `findItem` looks one up by id, and `removeItem` returns a new inventory with one used up (dropping an entry that runs out; throws if the item isn't there). `getItemRecovery(unit, item)` is what the item would actually restore — its amount capped by how far the stat is below its maximum, and 0 for a weapon — `canUseItem` is whether that's above 0, `getConsumables(inventory)` lists the consumable entries, and `getItemActions(unit, inventory)` builds item menu entries for the consumables (`{ id, label, quantity, disabled }`, disabled when the item would restore nothing). Tested in `src/game/items.test.ts`.

### `src/game/weapons.ts`

Pure weapon rules. A weapon is an item `{ kind: 'weapon', id, label, type, might, hit, crit, weight, minRange, maxRange, uses }`; `type` is one of `WEAPON_TYPES` — `physical`, `magical` or `siege` — which decides the damage it deals (`WEAPON_DAMAGE_TYPES`: siege hits physically) and who can wield it: each class masters a list of types (`canWield(weaponTypes, weapon)`). `uses` is a fresh weapon's strikes, or `null` for one that never breaks. `WEAPONS` holds one starter weapon per armed unit in the unit catalog (`FISTS`, `IRON_SPEAR`, `IRON_AXE`, `IRON_BOW`, `FIRE`, `POWDER_KEG`, `BALLISTA`; numbers in `UNITS.md`), and `weaponEntry(weapon)` is a fresh inventory entry with all its uses. In an inventory a weapon entry's `quantity` is its uses left. The equipped weapon is the first one the unit can wield: `getWieldableWeapons(inventory, weaponTypes)` lists them as `{ weapon, index, uses }` (uses null for one that never breaks) and `getEquippedWeapon` takes the first; `equipWeapon(inventory, index, weaponTypes)` moves one to the front (throws if there's no wieldable weapon there), and `spendWeaponUse(inventory, index)` returns `{ inventory, broke }` with one use spent — a weapon that runs out is removed, and one with `uses: null` is untouched. `getWeaponReach(weapons)` is the `{ minRange, maxRange }` span of several weapons (for the threat fringe), `formatWeaponRange` reads a range as "1" or "1–2", and `getWeaponActions(inventory, weaponTypes, hasTarget)` builds the weapon menu entries (`{ id, label, index, type, uses, might, hit, crit, weight, range, disabled }`, disabled when `hasTarget(weapon)` says nothing is in range). Tested in `src/game/weapons.test.ts`.

### `src/scenes/GridScene.ts`

The Phaser scene that renders a grid. Loads the terrain tileset and every sprite image in `SPRITE_URLS`, gets the starting grid, unit registry, roster, and deployment zone from a level — `createBattleLevel(setup, getActiveContent())` (`src/game/battleSetup.ts`, with any dialog the player uploaded) for its scene data, the store's `battleSetup` (the first story chapter if none) — converts it into Phaser tilemaps for terrain (a 32px grass layer, then one 16px quarter-tile layer per autotiled terrain from `autotile.ts`, with animated sets such as water stepped through their frames on a timer), draws the forest, mountain and building overlays from `mapArt.ts` (`renderMapSprites`; the `wall` autotile and the buildings come in the level's `palette`), the level's trees and multi-tile structures (each structure drawn tile by tile from `getStructureTiles`: its roof rows over units, so they pass behind the roof, but under the cursor; the rest under units) over the terrain, and places sprites for occupied cells using `gridToWorld` for positioning. Each unit gets a blob shadow from `addUnitShadow` (`src/scenes/unitShadow.ts`): a translucent pixel ellipse (`UNIT_SHADOW` in `tileset.ts`, rasterized by `pixelShapes.ts`) under its feet, since the unit sprites have none. The shadow follows its sprite every frame and is destroyed with it. Unit sprites are drawn by `addTileSprite`, stretched to fill one 32px tile. The terrain sheet is loaded as a 32px spritesheet, so the cursor sprite loops `CURSOR_ANIMATION`'s two tiles from it and each movement-arrow piece is a sprite of its `ARROW_TILES` frame. Also renders that cursor sprite and moves it one tile per keypress by calling `src/game/cursor.ts` from `update()` and re-rendering the sprite at the new position — the scene holds no movement rules itself. The canvas is as big as the stage the page gives it (see `src/ui/` and `main.ts`), and `fitCamera` zooms the map with `getFitZoom` — capped at 2x (the 16x14 demo map is 512x448 at 1x, so it reaches 2x on a stage of 1024x896 or more) — and centers it; it runs again whenever the canvas is resized. `pixelArt: true` (set in `main.ts`) keeps the pixel art crisp when scaled.

Occupied cells are backed by `src/game/Unit.ts` instances held in a `unitId -> Unit` registry (`this.units`) built alongside the grid; `cell.unitId` stays a plain string so grid data remains Phaser-free, and the registry is where actual stats/behavior live. Each frame, `updateHoveredUnit()` looks up the unit (if any) under the cursor and, only when it changes, publishes `toUnitView(unit)` (or `null`) to `gameStore` as `hoveredUnit`, along with `hoveredAnchor`, the TileAnchorView of the cursor's tile (or `null`), which the unit panel docks away from. GridScene has no knowledge of React — it only writes plain state.

On `create()` the scene resets the battle-related store fields, plays the level's `opening` dialog if it has one (see **Dialog** below), shows the Objective screen (`showObjective` publishes `toObjectiveView` of the battle's `describeBattle` title and the level's `describeObjective` as `objective`; confirm or cancel clears it in `hideObjective`), and then starts in the **deployment phase** (`phase: 'deployment'`) — or, when the level has no deployment zone (training), goes straight to the battle. The deployment zone is highlighted and the map cursor is hidden while a deployment menu has input (a hidden cursor hovers nothing, so the unit panel clears too). Input runs through three steps (published as `deploymentStep`): `'menu'` — the Place Units / Start menu (`deploymentMenu`); `'roster'` — the roster menu (`rosterMenu`, entries from `toRosterEntryView`, disabled when `canDeployUnit` says every slot is taken) to pick a unit; `'placing'` — the cursor roams and confirm on a tile `canPlaceUnit` accepts calls `placeUnit` and draws (or moves) the unit's sprite, then returns to the menu with Start highlighted once `isDeploymentComplete`, else Place Units. The scene computes the limit once from the level (`deploymentLimit`) and publishes it for the roster menu's count. Cancel steps back (placing → roster → menu). The cursor only shows during `'placing'`. Start is ignored while disabled; once chosen it clears the zone, drops roster units that weren't placed from the registry (they sit the battle out), sets `phase: 'battle'`, and starts turn 1 (see **Turns** below). All menus are mirrored to the store through `publishMenu(key, menu)`.

In the battle phase, pressing cancel on the bare map (no menu open, no range shown) opens the **pause menu** (`pauseMenu`, from `PAUSE_ACTIONS`), which owns input while open: cancel closes it, End Turn ends the player phase early (units that haven't acted forfeit their action) and starts the enemy phase, Main Menu resets the battle store fields and sets `screen: 'title'` (which makes `main.ts` remove the scene), and Settings is a placeholder.

Pressing confirm (Enter/Z) while hovering a ready player unit selects it (`activeUnit`, the unit and its tile) and goes straight to moving: the tiles from `getMovementRange` are drawn as translucent blue overlays (allies pass through, anyone else blocks), ringed in red by the tiles it could attack from there (`getThreatRange` over the span of all its wieldable weapons, `getWeaponReach`). While the range is shown the cursor moves freely; cancel clears it and lets go of the unit, and as the cursor moves the scene keeps a planned route with `extendMovePath` and draws it as an arrow from `getArrowPieces` (sprites above the range overlay, below units); confirm on an in-range tile at the end of that route walks the unit's sprite along it (`walkSprite`: a chain of linear tweens, one per tile, playing the move animation facing each step), ignoring input until it arrives, then commits the move to the grid with `moveUnit` (confirming the unit's own tile keeps it in place) and opens the action menu beside it: GridScene creates it with `src/game/actionMenu.ts` and publishes it to `gameStore` as `actionMenu`. While it's open the menu owns input — up/down call `moveSelection`, confirm reads `getSelectedAction`, and cancel takes the move back and shows the move range again. Sprites are kept in a `unitId -> sprite` map (`this.unitSprites`) so moves can find them. Choosing **Attack** (greyed out without a weapon the unit can wield) opens the **weapon menu** (`weaponMenu`, from `getWeaponActions`): each wieldable weapon with its uses, greyed out when nothing hostile is in its range from the unit's tile; cancel returns to the action menu, and confirm equips the weapon (`Unit.equip`) and draws the tiles from `getAttackRange` for its range in red, putting the cursor on the first hostile unit in range; confirm only accepts a tile holding a hostile unit (any other team) from `getAttackTargets`, and cancel backs out to the weapon menu, so picking another weapon re-forecasts with it. While the cursor is on such a target, GridScene publishes `combatForecast` (`getCombatForecast` → `toCombatForecastView`, anchored to both units' tiles merged with `mergeTileAnchors`), refreshed whenever the cursor moves or the camera refits and cleared when the range is hidden. `resolveAttack` gets the exchange from `resolveCombat` and plays its strikes in order with input locked: each strike spends a use of the striker's weapon (`Unit.spendWeaponUse`, with a "Broke!" popup over it if that breaks the weapon), and each struck unit takes the strike's damage right away (the hovered-unit snapshot is republished so the HUD updates), its sprite plays the hit flash from `src/scenes/effects.ts`, and a damage popup is published to `gameStore` (see below); a unit at 0 health is removed from the grid, the registry, and the sprite map once its flash ends, which also ends the exchange. So the defender counterattacks when it can reach, a faster unit strikes a second time, and a counter can kill the attacker. Afterwards `awardCombatExperience` gives the player unit in the fight (only player units gain XP, in either phase), if it survived, the XP from `getCombatExperience`; a damaging skill earns XP as one landed strike. `showExperienceGain` applies it with `Unit.gainExperience` and publishes `experienceGain` (`toExperienceGainView`) for `EXPERIENCE_BAR_MS`, then one `levelUp` (`toLevelUpView`) per level gained for `LEVEL_UP_MS` each, with input still locked, before the action finishes. A missed strike shows a "Miss" popup and pauses briefly instead of flashing; a crit shows a "Crit!" popup and shakes the camera. Move/attack share one range overlay (`rangeMode` + `rangeTiles`).

Damage numbers are drawn by React, not Phaser: `showDamagePopup` converts the hit sprite's top center to canvas pixels with `worldToScreen` (using the camera's `worldView` and zoom), then to fractions of the canvas with `toCanvasFraction` (so the popup lands on the unit however large the canvas is displayed), appends a `toDamagePopupView` snapshot to `gameStore.damagePopups`, and removes it after `DAMAGE_POPUP_DURATION_MS`. The same duration travels in the snapshot so React's CSS animation and the entry's lifetime agree. The same popups show crits, misses, and recovery: `showDamagePopup(sprite, amount, kind)` with `kind` `'crit'`, `'miss'`, `'health'`, `'mana'`, or `'broke'` (a weapon wearing out).

The action menu is built per unit with `getUnitActions`, so **Skill** is greyed out (and confirm ignores it) until the unit has learned a skill from its class's tree. Choosing it replaces the action menu with the **skill menu** (`skillMenu`, from `getSkillActions`), which owns input while open: cancel returns to the action menu, and confirm on an affordable skill shows its range (`getAttackRange` with the skill's `range`) in orange as `rangeMode: 'skill'`, remembering the skill as `activeSkill`. Cancel while aiming goes back to the skill menu; confirm on a hostile unit in range spends the mana, applies `calculateSkillDamage`, and plays the skill's animation via `playSkillAnimation` (`'stone'`: `playStoneThrow` onto the target, then a hit flash; `'strike'`: `playLunge` toward the target, then a hit flash and camera shake) before publishing the new health and damage popup and removing a defeated unit.

**Item** is greyed out while the unit carries no consumables (weapons aren't listed there). Choosing it opens the **item menu** (`itemMenu`, from `getItemActions`), which works like the skill menu: cancel returns to the action menu, and confirm on an item that would restore something calls `unit.useItem` right away (the HUD shows the new HP/MP), publishes a `+N HP` / `+N MP` popup, and plays `playPotionGlow` from `effects.ts` in the stat's color from `POTION_COLORS` (green for health, blue for mana). Items target the user, so there's no range to aim, and using one finishes the unit.

**Mouse.** The mouse feeds the same confirm / cancel as the keyboard. A queued `main-menu` command (the header's Main Menu button) is checked before the input lock and calls `exitToTitle` at once, so it works mid-animation, during a dialog, or in the enemy phase; removing the scene stops whatever was playing out. Phaser pointer events on the map (`hover-tile` / `click-tile`, converted with `worldToGrid`) and commands from `gameCommands` are queued as they arrive and drained at the top of `update()` (`drainPointerInput`), so they respect `inputLocked` like keys. While no menu has input (`canRoamCursor`: bare map, aiming a range, placing a unit) the cursor follows the pointer — extending the move arrow in move mode — and a left click moves the cursor there and confirms; hovering or clicking a React menu entry highlights / picks it; right click anywhere on the stage cancels (which on the bare map opens the pause menu); a click once the battle is decided returns to the title.

**Dialog.** `playDialog(lines, onDone)` hides the cursor and shows a conversation: the scene keeps a `dialog` from `src/game/dialog.ts` and publishes `toDialogView` of it as `dialog`, with the unit art for each line's `unitClass` from `getUnitSprite`. While it shows it owns input: confirm calls `advanceDialog` with the time since the line started (the scene clock), so a line still typing finishes at once and a finished one moves on; cancel skips the rest. The cursor is hidden meanwhile and restored as it was when the dialog closes, then `onDone` runs. `playTriggeredDialog(trigger, onDone)` plays the level's conversation for a trigger, or just runs `onDone` when there's none: `opening` on `create()`, `turn N` once the player phase banner of turn N ends, and `victory` / `defeat` from `checkOutcome` — which sets `battleOutcome` on the scene at once (ending the battle) but only publishes it to the store, showing the result, after the dialog. A victory also works out the next battle with `getNextBattle` (a fresh `randomSeed()` for a Warband stage) and publishes its `describeBattle` title as `nextBattle`. Confirming the result runs `leaveBattle`: with a next battle it clears the battle state and stores the new `battleSetup`, which makes `main.ts` restart the scene with it (everything is reset in `create()`, and the shared animations and textures are only made once); otherwise it returns to the title. The dialog is checked before the outcome in `update()` so it keeps input until then.

**Preview.** When the store's `screen` is `'preview'` (the config editor's map preview), `create()` builds and draws the level as usual but skips the opening dialog, the Objective screen and deployment, and `update()` hands all input to `updatePreview`: the deployment zone is highlighted, the cursor starts on it and roams (so the unit panel shows whoever it's over, enemies included), confirm on a unit draws how far it reaches — its move range and the tiles it threatens, from `drawUnitReach`, the same highlight a selected unit gets — and confirm again (or on an empty tile) clears it, and cancel clears it or else returns to the title. No units can be placed, moved or ordered, and no turn starts.

**Turns.** GridScene keeps a turn state from `src/game/turns.ts` (`this.turnState`) and publishes `toTurnView` of it as `turn`. `startPhase` clears every unit's "done" tint, publishes a `phaseBanner` (`toPhaseBannerView`) and locks input for `PHASE_BANNER_DURATION_MS`, then either hands input to the player (cursor on their first unit) or runs the enemy phase. In the player phase, a unit that's done can't be selected; once it has moved the unit is `markMoved` and the action menu opens at its new tile; cancelling that menu undoes the move (the unit snaps back to where it started, `unmarkMoved` gives the move back, and its move range shows again). **Attack**, **Skill**, **Item**, and **Wait** finish the unit (`finishPlayerAction` → `markDone`, sprite tinted grey); once `isPhaseOver` for the living player units, the enemy phase starts. `runEnemyPhase` takes each enemy in turn: the cursor jumps to it, it follows `planRushAction`'s path (via the same `walkSprite` as the player), commits the move, attacks its target if it has one through the shared `resolveAttack` (the same exchange, so player units counter), and is greyed out; then the next phase begins. After every action `checkOutcome` runs `getBattleOutcome`; once the battle is decided it publishes `battleOutcome`, hides the cursor, and only confirm is accepted, which returns to the title.

### `src/scenes/effects.ts`

Presentation-only sprite effects that never touch game state; each calls `onDone` when finished. `playHitFlash(scene, sprite, onDone)` blinks a sprite solid white a few times on the scene clock. `playStoneThrow(scene, from, to, onDone)` lobs a small grey circle along an arc between two world points, flying longer and higher the farther the throw. `playLunge(scene, sprite, toward, onImpact, onDone)` darts a sprite a few pixels toward a world point and back, calling `onImpact` at the far end. `playPotionGlow(scene, sprite, center, color, onDone)` is the potion effect: sparkles rise from the unit's feet in the given color while the sprite pulses that color — one animation for every potion, colored per stat via `POTION_COLORS`. None need sprite art: the shared particle texture is drawn with `Graphics` and generated at runtime the first time it's used.

### `src/bridge/store.ts`

`createStore(initialState)` → `{ getState, setState, subscribe }`. A minimal observable store: `setState` takes a partial object or `(state) => partial`, shallow-merges into a **new** state object, and notifies subscribers only if a top-level value actually changed. Its shape matches React's `useSyncExternalStore` contract. Tested in `src/bridge/store.test.ts`.

### `src/bridge/gameStore.ts`

The single app-wide store instance and its initial state shape. `BATTLE_STATE_DEFAULTS` holds the fields that only matter while the map runs; the map scene resets them on start and on exit so nothing leaks between battles. New UI-facing state gets added here as plain, serializable values. `weaponMenu`, `skillMenu` and `itemMenu` are the open weapon, skill and item menus. `turn` (turn number, team, and phase label), `phaseBanner` (the phase announcement while it's up), and `battleOutcome` (`'victory'` | `'defeat'` | `null`) describe the turn flow. `phase` (`'deployment'` | `'battle'` while the map runs), `deploymentStep`, `deploymentLimit`, `deploymentMenu`, and `rosterMenu` describe the deployment phase. `screen` (`'title'` | `'battle'` | `'preview'`) is which top-level screen is showing (`'preview'` runs the map read-only, see **Preview** under GridScene), and `battleSetup` (`{ mode: 'demo' }` | `{ mode: 'training', unitClass }`) which battle the map runs; they're the fields React writes (Story Mode or picking a Training unit sets both), and `main.ts` reacts by starting the map scene with `battleSetup` as its scene data.

### `src/bridge/commands.ts`

`createCommandChannel()` → `{ send, subscribe }`: the React → Phaser direction of the bridge. React sends plain command objects and the running scene subscribes (unsubscribing when it shuts down). `gameCommands` is the app-wide instance. Commands: `hover-menu` / `select-menu` (`{ menu, index }`, where `menu` is the store field of an open menu), `confirm`, and `cancel` — the same inputs the keyboard produces, so the scene handles them through its existing input steps — plus `main-menu`, which leaves the battle for the title screen even while input is locked. Tested in `src/bridge/commands.test.ts`.

### `src/bridge/views.ts`

Pure snapshot functions that turn live game objects into frozen plain objects for the UI: `toUnitView` (stats, the equipped weapon's `range` as text — "1", "1–2", "–" — and name, plus the carried items as `{ id, label, quantity, weapon, equipped }`, `quantity` being a weapon's uses left or null for one that never breaks), `toDamagePopupView` (a floating number with a `kind` — `'damage'`, `'crit'`, `'miss'`, `'health'`, `'mana'`, or `'broke'` — and the `text` to show: the bare number for damage, `Crit! N` for a crit, `Miss` for a miss, `+N HP` / `+N MP` for recovery, `Broke!` for a worn-out weapon), `toRosterEntryView` (a roster menu entry: id, name, sprite frame, placed flag), `toTurnView` (turn number, team, and "Player Phase" / "Enemy Phase" label from a turn state), `toPhaseBannerView` (a turn view plus an `id` and `durationMs` for the phase announcement), `toDialogView` (the dialog line being spoken: speaker, side, text, the portrait and the stand-in sprite, whether the player skipped its typing, and the typing speed, with an `id` per line), `toTileAnchorView` (a map tile's edges as canvas fractions, which GridScene publishes as `menuAnchor` for the active unit whenever its action, weapon, skill, or item menu opens and again after the camera refits), `mergeTileAnchors` (the smallest anchor covering two, e.g. attacker and target), `toCombatForecastView` (a `getCombatForecast` result with each side's name, team and weapon name, plus the merged anchor), `toExperienceGainView` (the post-combat XP bar: name, starting level, XP gained, and the fill's start/end percent — 100 on a level up), `toLevelUpView` (one level gained: name, new level, each stat's label/new value/gain, and learned skill labels), plus `worldToScreen` (world point + `{ x, y, zoom }` camera view → pixels at the canvas's own resolution) and `toCanvasFraction` (canvas pixels → 0–1 fractions of the canvas) for placing map-anchored UI, which React positions in percentages. React never holds live `Unit` instances — a mutation like `takeDamage()` must be followed by publishing a fresh snapshot, which is what triggers the re-render. Tested in `src/bridge/views.test.ts`.

### `src/ui/`

React renders the whole page, mounted by `mountUI(container)` into `#root` (see `index.html`). It renders synchronously, so the `#game` element the Phaser canvas goes in exists before `main.ts` builds the game. The page, styled with the title screen's navy/gold theme (shared tokens on `:root` in `ui.css`), is a header, then the **stage** (the canvas plus the HUD overlay, framed in gold) filling the rest of the window. The page fills the window: the stage fills the space below the header at every window size (the header wraps on narrow windows), and Phaser's `Scale.RESIZE` keeps the canvas the same size (one canvas pixel per CSS pixel). HUD text is sized in `rem` and isn't scaled with the map, so it follows the browser's font size and zoom; animations fall back to plain fades under `prefers-reduced-motion`, and the header status is an `aria-live` region. All in-battle UI (menus, banners, damage popups, dialogs, the unit panel) goes in the HUD overlay on top of the canvas, so the map gets the whole width; reference panels drop down from header buttons. The HUD overlay has `pointer-events: none` so input falls through to the canvas; interactive panels (`.panel`) opt back in. Components read state through `useGameStore(selector)` — a thin `useSyncExternalStore` wrapper; selectors must return stored references, not freshly built objects. Current components: `App` (page root — always renders the battle layout, since `#game` must stay mounted, and covers it with `TitleScreen` while `screen` is `'title'`, or with `ConfigsPage` on the `#/configs` route), `LoadingScreen` (mounted while `screen` is `'battle'`: covers the page with the title screen's backdrop and a bar filled from `mapLoadProgress`, which GridScene publishes from its loader's progress, then fades out once GridScene sets `mapReady` at the end of `create()`, so starting a battle never shows a blank canvas), `PageHeader` (wordmark plus a status slot holding `DeploymentBanner` or `TurnIndicator`, and an actions slot holding `ControlsButton` (a keyboard icon button whose drop-down is the key reference), `SettingsButton` (a placeholder drop-down with no settings yet) — both built on `HeaderPopover`, a header button with a drop-down panel that closes on a second click, a click elsewhere, or Esc (stopped before it reaches Phaser), the open/close behavior coming from `usePopover`, which the config editor's `InfoPopover` shares — and `MainMenuButton`, which shows once the map is ready and sends `main-menu`, so the player can return to the title at any time without pausing), `TitleScreen` (the full-viewport landing page: title, crest, and the Story Mode/Warband Mode/Training/Settings menu; driven by arrows + Enter/Z or the mouse, holds its menu selection in local state via the `actionMenu.ts` helpers; Story Mode starts chapter 1 (the demo battle), Training swaps in a unit-class menu from `getTrainingActions` (Esc/X or right click goes back) whose choice starts a training battle, Settings swaps in the `SETTINGS_ACTIONS` menu the same way, whose Game Configs opens the config editor at `#/configs`), `DeploymentBanner` (header status: names the deployment phase and hints at the current step), `DeploymentMenu` (Place Units / Start, with Start greyed while disabled; like `RosterMenu`, centered on the map), `RosterMenu` (units available to deploy, each with its sprite via `UnitSprite`, which shows a sprite image by texture key; its title counts placed units against `deploymentLimit`, and units that can't be placed once it's reached are greyed), `PauseMenu` (the End Turn / Main Menu / Settings menu over a dimmed map), `UnitPanel` (card for the unit under the cursor, docked in a top corner of the map and kept compact: sprite, name and level (XP for player units), thin HP/MP bars, a borderless 3x3 stat grid, and items one per row with long names cut short by an ellipsis — potions with their count, weapons with their uses (∞ for Fists) and the equipped one in gold (left out when there are none); RNG is the equipped weapon's range, with the team as the accent color; the pure `pickCornerAwayFromTile` (`src/ui/menuPlacement.ts`, tested) puts it in the corner away from `hoveredAnchor`, it ignores the pointer so the map under it stays hoverable, it hides while the combat forecast is up, and it renders first in the HUD so every other overlay paints over it), `ActionMenu` (the open action menu with its highlighted entry, disabled entries greyed; input is handled by GridScene — like every map menu, its entries forward hover/click through `menuItemPointerProps` in `menuPointer.ts`), `WeaponMenu` (after Attack: the active unit's wieldable weapons with their uses, ones with nothing in range greyed, and the highlighted weapon's Mt / Hit / Crit / Wt / Rng / type underneath), `SkillMenu` (the active unit's skills with their mana cost, unaffordable ones greyed), `ItemMenu` (the active unit's consumables with how many are left, ones that would restore nothing greyed) — these four open beside the active unit through `useMenuBesideUnit`, which measures the menu and places it with the pure `placeMenuBesideTile` (`src/ui/menuPlacement.ts`, tested): to the unit's right when it fits, otherwise its left, top lined up with the tile and kept on the stage — `CombatForecast` (while aiming an attack at a target: each side's name, weapon, HP, Dmg with ×2 when it doubles, Hit and Crit, attacker left and defender right, "–" for a defender that can't counter; ### Routing and the config editor

The page's routes are read from the URL hash so they work from the GitHub Pages subpath without server rewrites: the config editor's index (`#/configs`), one config's page (`#/configs/<id>`), a Warband region's map preview (`#/configs/regions/preview/<index>/<seed>`), and the game (any other hash). `src/ui/route.ts` is the pure `parseRoute(hash)` / `routeHash(route)` pair (tested in `route.test.ts`), and `useRoute()` (`src/ui/useRoute.ts`) re-renders on `hashchange`. The battle layout stays mounted on every route; on the config routes `ConfigEditor` covers it like the title screen does, and ends any running battle when it opens (it sends `main-menu`) so Phaser stops taking keyboard input underneath. The title screen's Settings menu links to it. `ConfigEditor` shows the page `CONFIG_PAGES` has for the route's id, or the index; every page shares the `ConfigLayout` frame (title, lede, back link).

`ConfigsPage` is the editor's index: every piece of authored or tunable data, grouped (Story & Dialog, Maps, Units, Equipment, Rules), each card naming its source files and summarizing what's in it now. The list is `getConfigCatalog()` in `src/ui/configCatalog.ts`, which reads its counts from the live data (dialogs, regions, unit classes, weapons, …); `configCatalog.test.ts` checks that ids are unique and every source path exists. Cards for configs with a page link to it; the rest are marked as coming.

`DialogConfigPage` (`#/configs/dialogs`) takes `.txt` dialog files by picker or drag and drop. `checkDialogUpload` (`src/game/dialogUploads.ts`) accepts a file named after a level's dialog file (`demo.txt`, `training.txt`) whose text parses against the character roster, reporting parse errors with their line number; accepted uploads go to `customDialogStore` and play from the next battle. Each dialog file is listed as built-in or uploaded, with its conversations (in play order, `compareTriggers`) expandable to their lines, a Download button (the upload, or the built-in file as a starting point) and, for uploads, Reset to Built-in. `applyCustomDialogs` merges uploads over the built-in files, and an upload that stops parsing (say, a character was removed) is flagged on the page while the built-in file plays. `dialogUploads.ts` is tested in `dialogUploads.test.ts`.

`RegionsConfigPage` (`#/configs/regions`) edits Warband Mode's regions as a form. It keeps a draft, the settings as plain JSON (`src/ui/regionsDraft.ts`, tested: `getIn` / `setIn` and the list edits `insertAt` / `removeAt` / `moveItem` return new drafts; `checkDraft` runs the draft through `parseRegionSettings`, map test included; `pathLabel` / `isErrorAt` / `isErrorWithin` match the parser's error, which names the field at fault, to a field or a region (an old Dungeon Mode upload's errors, which name `floors`, read the same); `readNumberText` reads a number box, blank clearing the setting; `readableError` rewrites an error's path in the form's words, e.g. "Meadowlands › Enemy group 1 › Max distance is 5, …", for the save bar, region cards and upload notices, and `errorReason` drops the path for the message shown under the field it names). The form is built from `DraftFields.tsx` (number, `[min, max]` / `[from, to]` pair, text, select and checkbox fields, each bound to a draft path and marked invalid when the error names it, with the reason beneath; blank optional fields show the generator's `MAP_GEN_DEFAULTS` as placeholders; a field whose setting has an entry in the form's `help`, which the page fills from `FIELD_HELP` in `src/ui/regionFieldHelp.tsx` (tested to cover every setting on the form), gets an `InfoPopover` beside its label: an "i" button opening a plain-words explanation, with a diagram of an example area for the enemy groups' areas) and `RegionEditor` (one card per region: name, description, map, terrain and enemy groups, with Move Up/Down, Duplicate and Remove, plus Add Enemy Group). The page adds Stages per region and Add Region, and a save bar while there are unsaved changes: the draft's error, Discard, and Save (disabled until the draft parses). Saving goes through `src/data/projectSave.ts`: on the dev server (`CAN_SAVE_TO_PROJECT`, i.e. `import.meta.env.DEV`) `saveConfigToProject` POSTs the file to `vite/saveConfigs.ts`, which writes `src/data/regions.json` (and clears any browser upload, which would hide it); the dev server then reloads the page, and a session-storage message reports the save across the reload. Elsewhere Save keeps the file in this browser with `customRegionsStore`. Leaving the page with unsaved edits asks first. A `.json` file can still be uploaded in place of the regions (checked with `parseRegionSettings` and kept with `customRegionsStore`; the next run uses it); the page shows whether the regions are built-in or uploaded (flagging an upload that no longer parses), with Download (the saved file), Reset to Built-in and New Preview Maps. Each region card shows a map generated from it with the preview seed (the last draft that parsed, while there's an error), drawn a square per tile from `getMapPreview(level)` (`src/ui/mapPreview.ts`, tested: each tile's terrain and one marker for an enemy, building, deployment tile or tree), and each enemy group's summary from `describeEnemyGroup`. For a region that matches what's saved, the thumbnail and a View Full Map button open that same map on the battle stage: `RegionPreview` (the preview route, in place of `ConfigEditor`) sets `screen: 'preview'` and `battleSetup` to `regionPreview(index, seed, getActiveRegionSettings())`, showing `LoadingScreen` while it loads. The header swaps in `RegionPreviewBanner` (the region's name, its stages, and the controls) and `RegionPreviewActions` (New Map, which puts a fresh seed in the route and so restarts the scene, and Back to Regions) for `DeploymentBanner`/`TurnIndicator` and `MainMenuButton`. Leaving the route ends the preview (setting the store straight to the title, so it ends even mid-load), and the scene ending it (Esc) sends the page back to the Regions page. Both pages share `UploadDrop` (a drop zone that's also a file picker, with the last upload's results) and `downloadText`.

### `vite/saveConfigs.ts`

The dev server's config save endpoint, a Vite plugin applied only to `vite serve` (so builds and `vite preview` can't write files). `POST /__configs/<id>` with the save header (`SAVE_CONFIG_PATH` and `SAVE_CONFIG_HEADER` in `src/data/configSaveApi.ts`, shared with the editor; the custom header means a page from another site can't send it) saves config `<id>` from `SAVABLE_CONFIGS` (just `regions`, to `src/data/regions.json`): `saveConfig(request, configs, deps)` loads the config's parser and formatter through the dev server (`ssrLoadModule`, so they import as they do in the game), turns away text the parser rejects with its message, and writes the formatted file, laid out by Prettier. `formatRegionSettings` writes what fits on one line on one line and keeps each region's terrain settings in the file's order, so saving an unchanged file leaves it byte for byte the same. Tested in `vite/saveConfigs.test.ts` (with the file system and module loading stubbed) and `src/data/projectSave.test.ts`.

### `src/main.ts`

Composition root. Mounts the React page first (which opens on the title screen and provides `#game`), then constructs the single `Phaser.Game` instance in `#game` (RESIZE scale mode, so the canvas matches `#game`'s size) with no scenes running, and keeps `GridScene` in step with `gameStore`: when `screen` leaves `'title'` (for `'battle'` or `'preview'`) it adds and starts the scene with `battleSetup` as scene data, when `battleSetup` changes while it runs (the next battle after a victory, another preview map) it restarts the scene with the new one, and when `screen` goes back to `'title'` it removes the scene (so the next battle starts fresh). It also applies the store's state once at boot, since `mountUI` runs React's effects first and a preview link opened directly has already asked for the map. Phaser and React are started independently here and only communicate through `src/bridge/`. Should stay free of game logic.

### `src/assets/` sprites
