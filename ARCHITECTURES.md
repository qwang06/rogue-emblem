# ARCHITECTURES.md

Living documentation of how Rogue Emblem is structured. This tracks the _shape_ of the system — modules, their responsibilities, and how they connect — not implementation detail that's better read from the code itself. Per-class numbers (stats, growths, weapons, skills) and the weapon table are tabulated in `UNITS.md`, which `src/game/unitsDoc.test.ts` keeps in sync with the code.

## Stack

- [Phaser 3](https://phaser.io/) for the game world: tilemap, sprites, animations, camera, map input, and the game loop.
- [React](https://react.dev/) for UI and the page around the game: the header, HUD panels, menus, dialogs — anything that's DOM-shaped rather than world-shaped. React renders the whole page, including the box the Phaser canvas mounts into and a DOM overlay on top of it.
- [Vite](https://vitejs.dev/) for dev server (hot reload) and production bundling. The dev server also takes the config editor's saves (`vite/saveConfigs.ts`).
- [TypeScript](https://www.typescriptlang.org/) in `strict` mode for all source. Vite strips types; `tsc` (`npm run typecheck`, and the first step of `npm run build`) only type-checks.
- [Vitest](https://vitest.dev/) for unit tests.
- [Prettier](https://prettier.io/) formats code and Markdown (`npm run format`); CI fails on unformatted files.
- [GitHub Actions](https://docs.github.com/actions): `.github/workflows/ci.yml` checks formatting, runs the full test suite and builds on every pull request to `main` and every push to it; `.github/workflows/deploy.yml` runs the same checks, builds, and deploys to GitHub Pages only when run manually (`workflow_dispatch`). Vite builds with a relative `base` so the game works from the Pages subpath.

## Layering

The codebase is split into layers that don't reach into each other's internals:

- **Pure game logic** (`src/game/`) — plain TypeScript functions and data, no Phaser imports, no rendering, no hidden state. Every rule of the game (grid layout, movement, combat, turn order, etc.) belongs here so it can be unit tested without spinning up a `Phaser.Game`.
- **Phaser presentation** (`src/scenes/`) — Scenes are the thin glue layer. They call into `src/game/` for state and rules, then use Phaser APIs to draw the result and handle input. Game rules should never be implemented inline in a scene.
- **Bridge** (`src/bridge/`) — framework-agnostic store that Phaser writes to and React reads from. Neither Phaser nor React imports the other; this is the only point of contact.
- **React UI** (`src/ui/`) — components that render UI state from the bridge store. No game rules here either; components display snapshots and send player input (mouse clicks on menus, right-click cancel) back as commands through the bridge. Components may also call pure `src/game/` helpers directly (menu selection, battle titles, config parsing, map previews) and read `src/data/` for the config editor, but never live Phaser state.
- **Audio** (`src/audio/`) — sound effects (recorded samples, with synthesized stand-ins) and synthesized music, played with Web Audio. It only listens to the bridge store: `getSoundCues(prev, next)` turns each store change into cues (a new damage number, phase banner, level up, menu opening...) and `getMusicTrack(state)` picks the music, so nothing in the game asks for a sound directly and sounds follow what's on screen at the game's speed.
- **Authored data** (`src/data/`) — the built-in content files and their loaders, plus the player's uploads kept in `localStorage`. Game modules take content as arguments and fall back to `src/data/` only for defaults, so `src/game/` and `src/data/` import each other.

```
 src/game/  ◄── scenes call rules
     ▲
     │
 src/scenes/ ──setState(snapshot)──► src/bridge/gameStore ──useSyncExternalStore──► src/ui/
  (Phaser)                            (plain TS store)                              (React)
     ▲                                                                                 │
     └──────────────────── src/bridge/commands (send / subscribe) ◄────────────────────┘
```

```
src/
  game/       pure logic + data in TypeScript (tested with Vitest, no Phaser dependency)
    warband/  Warband Mode's own rules: regions, the regions file, a stage's battle, the run, relics, level-up boons, evolutions, promotion at camp, stage rewards, the convoy, the roster screen, the run's recap and renown
  scenes/     Phaser.Scene subclasses (rendering + input, calls into src/game/)
  audio/      synthesized sound effects and music, played from store changes, and the sound settings
  bridge/     Phaser → React state store, React → Phaser command channel (plain TypeScript, tested with Vitest)
  ui/         React components: the page layout, header, HUD overlay, title screen and config editor
  assets/     art/tileset source files
  data/       authored content (characters, dialog files, Warband regions) and the config editor's uploads (see src/data/README.md)
  featureFlags.ts  switches for built features that are off for now (music)
  main.ts     composition root — builds Phaser.Game, mounts the React UI
vite/         dev-server plugin that saves the config editor's files
```

## Modules

### `src/game/grid.ts`

Pure grid data structure for the tactics board. Grid state is `{ width, height, cells }`, cells stored row-major, each cell `{ x, y, terrain, unitId }`. All mutator-shaped functions (`setTerrain`, `setUnit`) return a **new** grid rather than mutating the input.

Key functions: `createGrid`, `isInBounds`, `getCell`, `setTerrain`, `setUnit`, `moveUnit` (relocates a unit id, throwing if the source is empty or the target occupied), `findUnit` (where a unit id stands, or `null`), `getNeighbors` (orthogonal only — no diagonal movement), `gridToWorld` / `worldToGrid` (grid coordinates ↔ pixel coordinates), `worldToTile` (the tile under a pixel, or `null` off the grid), `getDistance` (orthogonal/Manhattan steps between two tiles, used for movement adjacency and attack range), `isSameTile` and `findTileAt` (the first entry of a tile list standing on a given tile, or `null`).

Tested in `src/game/grid.test.ts`.

### `src/game/terrainMap.ts`

`parseTerrainMap(rows, legend)` builds a grid from a text layout — one string per row, one character per tile — so maps can be written as data that looks like the map. `DEFAULT_TERRAIN_LEGEND` maps `.` to grass, `~` to water, `,` to dirt and `#` to wall. Throws on an empty map, ragged rows, or a character the legend doesn't define. Tested in `src/game/terrainMap.test.ts`.

### `src/game/tileset.ts`

Names the art each piece of the map draws with, so scenes reference terrain/units/UI elements by name instead of magic frame numbers or file names. `TILE_SIZE` (32px) is the map tile, matching the overworld terrain sheet; `TERRAIN_SHEET` names that sheet's texture and size, `SEASON_TERRAIN_SHEETS` the copy of it (same layout, so every frame number works on each) a map in each `Season` draws from (`summer` the green sheet, `autumn` and `winter` their own; the map's `season` comes from its region, and GridScene loads each sheet's URL from `TERRAIN_SHEET_URLS` in `src/assets/sprites.ts`), `SEASON_TREES` the decorative tree a generated map scatters in each, `TERRAIN_BASE_TILE` the grass tile under every cell, and `TERRAIN_AUTOTILES` each autotiled terrain's source tiles and animation (see `autotile.ts`; water, dirt and dark-grass `meadow`). `FOREST_ART` and `MOUNTAIN_ART` list the overlay variants for forest and mountain cells, `BUILDING_ART` where each building kind sits on the sheet, and `BUILDING_PALETTES` the ten building colors (`a-stone` … `b-orange`: a building column offset, a rampart wall group, and whether it has flags), with `DEFAULT_BUILDING_PALETTE` `a-stone`; `mapArt.ts` turns these into sprites. `CURSOR_ANIMATION` names the cursor's own two-frame sheet (`tile-cursor`, cream brackets outlined dark so they read on pale and dark tiles alike), which frames it pulses between and how long each shows, and `ARROW_TILES` the sheet tile for each `moveArrow.ts` piece. `UNIT_SPRITES` (keyed by unit class, so every unit of a class looks alike on either side; `getUnitSprite(unitClass)` looks one up, falling back to `DEFAULT_UNIT_SPRITE`) names each class's unit art, whose sheets (one per animation in `UNIT_ANIMATIONS`, keyed by `unitSheetKey`) are standalone images listed in `src/assets/sprites.ts`; `UNIT_SHEET` says how those sheets are cut (a row per facing), `ITEM_SPRITES` names the icon for each item id (`getItemSprite(itemId)`, null for an unknown id; every run item and weapon has one), and `UNIT_SHADOW` sets the size, placement, and opacity of the blob shadow under units. Tested in `src/game/tileset.test.ts` (every unit animation has an image, every run item and weapon an icon; arrow tiles are on the sheet).

Unit art comes in two cuts. The pack's art is `idle` and `move` sheets of one-tile frames, four per facing (`PACK_SHEET_LAYOUT`). `UNIT_ART` lists art cut otherwise, per animation (`UnitSheetLayout`: frame size, frame count, and `tileX`/`tileY`, where the unit's tile sits in a frame so bigger frames spill over the tiles around it), plus viewer-only `extras`, the attack's `impactFrame` and `bakedShadow`. The red dragon (`Red_Dragon`, the `dragon` class) is the first: idle in one-tile frames, move (flight) in 48x32, attack (fire breath) in 112x96, hit and die. `UNIT_ANIMATIONS` names every animation (`idle`, `move`, `attack`, `hit`, `die`) with its sheet suffix, frame time and whether it loops; `getUnitAnimations(art)`, `getUnitSheet(art, animation)` (null for one the art lacks), `getAllUnitSheets(art)` (extras included), `getUnitSheetFrameSizes()` (how GridScene loads the bigger sheets), `hasBakedShadow` and `getImpactFrame` read them. Tested in `src/game/tileset.test.ts`.

### `src/game/pixelShapes.ts`

Pure pixel-art rasterizing. `getEllipseSpans(width, height)` returns the rows of pixels an ellipse covers as `[{ y, x, width }]` spans, so scenes can draw crisp shapes with rectangles instead of anti-aliased curves. `getOutlineMask` rings a sheet's opaque pixels frame by frame (frames may be wider than tall, and a `minAlpha` leaves a see-through baked shadow out). Tested in `src/game/pixelShapes.test.ts`.

### `src/assets/sprites.ts`

`SPRITE_URLS`: texture key → imported URL for every standalone sprite image (units, plus the structure and tree images: `gates.png`, `ginkgo_tree_green.png`, `gold_ginkgo_tree.png`). The only module that imports sprite files — GridScene preloads each under its key, and the React `UnitSprite` shows one by key.

### `src/game/autotile.ts`

Blob autotiling: a terrain is drawn in its own cells, with its border inside the edge cells, over a grass base. Each cell is drawn as four quarter tiles. `getQuarterShapes(grid, x, y, terrain, joins?)` names each quarter's shape from its two side neighbors and the diagonal between them (`'outer'`, `'horizontal'`, `'vertical'`, `'inner'`, `'full'`), which covers all 47 neighbor combinations. A set's `joins` lists other terrains drawn as part of it (water runs under bridges and fords, dirt and walls through gates). Cells off the map take the nearest cell on it, so terrain reads as continuing past the edge. `getShapeTile` picks the sheet tile (from the set's plain 3x3 `block` or its `inner` corner tile) whose same quarter draws that shape. `getQuarterFrames` returns the four frame numbers on the sheet cut into half-size tiles, shifted along the sheet for an animation frame. `getQuarterFrameMap(grid, terrain, autotile, sheetColumns, animationFrame)` lays those out for the whole map as rows of half-size tiles (each cell's quarters in its own 2x2 block, `-1` where the cell isn't that terrain), the data GridScene turns into a tilemap layer per terrain. `getTileFrame` numbers whole tiles. Tested in `src/game/autotile.test.ts`.

### `src/game/cursor.ts`

Pure logic for the map cursor: a `{ x, y }` grid position. `moveCursor` takes a delta and clamps the result to the grid bounds; it never mutates the cursor it's given. Tested in `src/game/cursor.test.ts`.

### `src/game/autoSpeed.ts`

The four game speeds (1x–8x) and the pure, bounded `changeAutoSpeed` step used by the header's minus and plus buttons. The speed plays the map's animations, banners and waits faster whether Auto is on or not. Tested in `src/game/autoSpeed.test.ts`.

### `src/game/actionMenu.ts`

Pure state for the unit action menu. `UNIT_ACTIONS` lists the offered actions (Attack, Skill, Item, Wait — moving happens before the menu opens) as `{ id, label }`; `getUnitActions({ hasSkills, hasItems, hasWeapons, canHeal })` returns them for a particular unit, with Attack marked `disabled` when it has no weapon it can wield, Skill until the unit knows a skill, and Item when it carries no consumables; a unit with a staff (`canHeal` given) also gets `HEAL_ACTION` right after Attack, disabled when `canHeal` is false; a menu is a frozen `{ actions, selectedIndex }`. `moveSelection` moves the highlight with wrap-around and returns a new menu (or the same one if nothing changed); `selectIndex` jumps straight to an index (ignoring out-of-range ones); `getSelectedAction` reads the highlighted action; `getDefaultActionIndex(actions, { hasTarget })` is the entry the unit menu opens on (Attack with something in reach, else an enabled Heal, else Wait). The helpers work on any action list, so other menus (e.g. the title menu) reuse them. The module only tracks selection — carrying out an action belongs to whoever consumes the choice. Tested in `src/game/actionMenu.test.ts`.

### `src/game/titleMenu.ts`

`TITLE_ACTIONS` — the title screen's menu entries (Story Mode, Warband Mode, Training, Settings) as frozen `{ id, label }` — `SETTINGS_ACTIONS`, the Settings submenu's entries (Game Configs), `getWarbandActions(savedRun)`, the submenu Warband Mode opens (Continue Run (Stage N), or a disabled Continue Run when nothing is saved, then New Run), `describeRenown(meta)`, the renown line under it (the renown so far and the next unlock), `STARTING_CLASS_ACTIONS` (one `{ id, label, description, units }` per `BASE_ORIGINS` entry) and `getStartingClassActions(meta)`, the submenu New Run opens (those, then each `UNLOCKABLE_ORIGINS` entry, disabled with "Unlocks at N renown" until `meta.ts` says it's open), `hasHeatPick(meta)` and `getHeatActions(meta)`, the Heat submenu (No Heat, then Heat 1 to `MAX_HEAT` as `heat-<n>`, each pitched with its name and rule, locked above `meta.heat`) with `getHeatOfAction(id)`, and `getFirstEnabledIndex(actions)`, the entry a submenu opens on. Selection uses the `actionMenu.ts` helpers. Tested in `src/game/titleMenu.test.ts`.

### `src/game/deployment.ts`

Pure rules for the **deployment phase** — the pre-battle step where the player places units from their roster onto a deployment zone (a list of `{ x, y }` tiles). `getDeploymentActions({ canStart })` builds the Place Units / Start menu entries (Start carries `disabled` until a unit is placed). `canPlaceUnit` accepts zone tiles that are empty, already hold that unit, or hold one of the `swappable` units (the roster); `placeUnit` puts a unit there, lifting it off its previous tile and swapping a roster unit on the tile to where it stood, or benching it when the placed unit wasn't on the map (throws on an invalid tile). `canDeployUnitAt` combines that with the slot rule (`canDeployUnit`, or `replacesPlacedUnit` once every slot is taken), and `canPickToDeploy` says which roster entries can be picked to place. `isPlaced`, `canStartBattle(grid, roster)` (at least one roster unit on the map), and `getFirstOpenTile(grid, zone)` round it out. Each map caps how many units can be deployed: `getDeploymentLimit(roster, zone, maxDeployed)` is the level's `maxDeployed` capped by roster and zone size, `countPlaced` counts roster units on the map, `canDeployUnit(grid, roster, limit, unitId)` lets a placed unit always move but a new one only while a slot is free, and `isDeploymentComplete(grid, roster, limit)` says every slot is filled. Tested in `src/game/deployment.test.ts`.

### `src/game/dialog.ts`

Pure state for conversations. A script is a list of lines `{ speaker, team, unitClass, side, portrait, text }` (`portrait` is the speaker's portrait sprite key or null, and `unitClass` picks the unit art standing in when there's none; `side` is `'left'` | `'right'`, where the portrait sits). `createDialog(lines)` starts a frozen `{ lines, index, revealed }` (throws on an empty script, a line without text, or an unknown side). Text types out at `DIALOG_CHARS_PER_SECOND`: `getRevealDurationMs` is how long a line takes and `getRevealedLength` how much shows after a given time. `advanceDialog(dialog, elapsedMs)` is what confirm does — finish typing a line that's still typing, else move to the next line, or return `null` after the last. Tested in `src/game/dialog.test.ts`.

### `src/game/dialogScript.ts`

Parses dialog written as text into those scripts. `parseCharacters(json)` checks a character roster (`{ id: { name, team, unitClass, portrait } }`, `unitClass` and `portrait` defaulting to null). `parseDialogScript(text, characters, source)` reads a dialog file: `[section]` headers name when a conversation plays (`isDialogTrigger`: `opening`, `victory`, `defeat`, `turn N`), and each `speaker_id: text` row (optionally `speaker_id (left|right): text`) becomes a line with the character's name, team, unit class, portrait, and their team's side from `DEFAULT_SIDES` (player left, enemy right). Comments (`#`) and blank lines are skipped. `turnTrigger(n)` names a turn's section and `getTriggeredDialog(dialogs, trigger)` looks a conversation up (null when there's none). It returns `{ trigger: lines }`, frozen, and throws with `source:line` on an unknown speaker, section, or side, a repeated or empty section, a line before any section, or a row that isn't speech. Tested in `src/game/dialogScript.test.ts`.

### `src/data/`

Authored content, documented for writers in `src/data/README.md`. `characters.json` is everyone who can speak; `dialog/*.txt` holds each level's conversations, one file per level; `regions.json` is Warband Mode's regions (Meadowlands, Lakeside, Deep Woods, Highlands, Fortress), each an 8x8 map so the fighting starts within a turn or two, in the format `src/game/warband/regionsFile.ts` reads. `regions.ts` loads it (`REGIONS_TEXT` as written, `REGION_SETTINGS` and `REGION_CONFIGS` parsed, skipping the per-region map check, which `src/data/regions.test.ts` runs instead). `dialogs.ts` finds every dialog file with `import.meta.glob` (so new files need no registration), parses them against the roster, and exports `CHARACTERS`, `DIALOG_TEXTS` (file name → the file's raw text) and `DIALOGS` (file name → `{ trigger: lines }`, a `DialogFiles`, e.g. `DIALOGS.demo.opening`). Uploads from the config editor live here too, in the browser's `localStorage` through `customStorage.ts` (`browserStorage()`, and `createStoredText(storage, key)`: one file's text, with missing or blocked storage reading as empty and writes reporting failure). `customRegions.ts` keeps the uploaded regions file (under its Dungeon Mode storage key, so older uploads still play; `getActiveRegionSettings()` parses it, falling back to `REGION_SETTINGS` if it no longer parses), and `customContent.ts`'s `getActiveContent()` gathers every upload into the `GameContent` GridScene builds battles from. `runSave.ts` keeps the Warband Mode run in progress (`loadSavedRun`, which reads a save that doesn't parse as no run, `saveRun`, `clearSavedRun`); the title screen saves a new run, and the map saves it after each won stage. `metaSave.ts` keeps Warband Mode's meta-progression across runs (`loadMeta`, a fresh `NEW_META` when there's none or it doesn't parse, and `saveMeta`); the map records each run that ends into it. `customDialogs.ts` keeps dialog files the player uploads in the config editor: `createCustomDialogStore(storage)` saves, loads and removes uploaded text by file name in `localStorage` (guarded, so missing or blocked storage reads as empty and writes report failure), and `getActiveDialogs()` is `DIALOGS` with each upload that still parses in place of the built-in file of the same name; `getActiveContent()` combines it with the active Warband regions, and is what GridScene builds levels with. Tested in `src/data/customStorage.test.ts`, `customDialogs.test.ts` and the other `src/data/*.test.ts` files. A broken file throws on import, which fails `src/data/dialogs.test.ts`; that test also checks every portrait key is in `SPRITE_URLS` and every `unitClass` is in `UNIT_CLASSES`. GridScene plays every trigger (see **Dialog** under GridScene).

### `src/game/demoLevel.ts`

`createDemoLevel()` builds the starting state of the demo battle (Level 1) as `{ grid, units, roster, deploymentZone, maxDeployed, dialogs, decorations, structures }` (`maxDeployed` is `DEMO_MAX_DEPLOYED`): the terrain comes from `DEMO_MAP` (a text layout parsed by `terrainMap.ts`, 16x14 tiles) — a grass field with a one-tile dirt path running north from the south edge to a paifang gate. The gate is a `structures` entry (`STRUCTURE_POSITIONS`, `{ x, y, structure }` by top-left tile, drawn from `STRUCTURE_SPRITES` in `tileset.ts`); every tile under it is walkable (the path down its middle, grass under its sides). `decorations` (`TREE_POSITIONS`) puts a stand of gold ginkgos right behind the gate and three clumps of green ginkgos in the field. Three enemy `Soldier`s hold the gate at `ENEMY_POSITIONS`, the player's roster (three named `Villager`s from `PLAYER_ROSTER`) is kept off the map, and `DEPLOYMENT_ZONE` (the south end of the path) is where they're placed. `dialogs` is `DIALOGS.demo` (from `src/data/dialog/demo.txt`), its conversations by trigger. `units` is the `unitId -> Unit` registry for both sides. A level may also carry `buildings` (`{ x, y, building }`, see `buildings.ts`) and a `palette` (a `BUILDING_PALETTES` name) that every building and wall is drawn in; the demo has neither. Stand-in until levels are loaded from data. Tested in `src/game/demoLevel.test.ts`.

### `src/game/unitClasses.ts`

`UNIT_CLASSES` — the unit classes the game can build, in menu order, as frozen `{ id, label, create(options), monster?, neutral?, promotedFrom? }`: the villager, its four tier-2 classes (archer, soldier, vanguard, sapper, each building a fresh unit of its own class and marked `promotedFrom: 'villager'`), the specialized units (scout, beast, beast rider, siege, ram, acolyte), the four elementals (water, fire, air, earth, marked `neutral: true`), then the monsters (slime, goblin, skeleton, bat, orc, dragon, marked `monster: true`). `PLAYABLE_CLASSES` is every class but the promoted, neutral and monster ones: the ones the player can start as, recruit or train; a unit only becomes a tier-2 class by promoting. `createUnitOfClass(classId, options)` builds a fresh `Unit` of a class by id (throws on an unknown one), so code that offers a choice of class doesn't import the subclasses; `options.faction` picks a faction unit's faction. Tested in `src/game/unitClasses.test.ts`.

### `src/game/promotions.ts`

Pure promotion rules (roadmap 4.5, shared with Warband Mode's W.7). The villager and the acolyte promote: `PROMOTIONS` holds the villager's four tier-2 classes (Archer, Soldier, Vanguard, Sapper) (tier 2) and the acolyte's Mage (tier 3, the only one so far), each `{ id, label, from, tier, description, bonuses, growths, weaponTypes, experienceRate, passive, gift }`. The bonuses are what the class's own stat line starts above the stat line of the class it promotes from (`from`, default the villager; and the MOV difference), added on the spot; growths, weapon types (the sapper adds siege) and XP rate are the class's own; the passive `{ name, description, modifiers }` lives in the class file (`ARCHER_PASSIVE` and so on, also applied by the class constructor) and is carried into every battle (see `modifiers.ts`); the gift is the class's weapon. `canPromote({ classId, level })` needs `PROMOTION_LEVEL` (5, so units promote mid-run) and a class with promotions; `getPromotionGains(unit, promotion)` is the bonuses in full (there are no stat caps); `promoteUnit(unit, promotion)` (changing the unit, like `levelUp`) sets the class, growths, weapon types and XP rate (`becomePromotedClass`, which also adds the passive's modifiers) and adds the gains, keeping level, XP, items and boons. `findPromotion`, `getPromotions(classId)` and `isPromotedClass` look them up. A tier-2 class has its own skill tree (`SKILL_TREES` in `skills.ts`) and faction art (`FACTION_BODIES`). Tested in `src/game/promotions.test.ts`; `UNITS.md` lists every class.

### `src/game/rng.ts`

Seeded randomness. `createSeededRng(seed)` returns an `Rng` (Mulberry32, numbers in [0, 1) like `Math.random`) that gives the same sequence for the same seed; `createResumableRng(seed)` is the same generator plus `state()`, a seed that carries the sequence on from where it got to (a battle's rolls, see `src/game/battle/`). It comes with `randomInt`, `randomItem` and `shuffle` helpers that take an `Rng`, and `randomSeed()`, the one unseeded function, which picks a fresh seed (for a new Warband stage's map or a new preview map). Tested in `src/game/rng.test.ts`.

### `src/game/mapGen.ts`

Pure procedural terrain built in layers from an `Rng`. `generateTerrain({ width, height, ... }, rng)` returns `{ grid, path, buildings }`; the options set how many of each layer to try and their sizes, with `MAP_GEN_DEFAULTS` for any left unset. It fills the map with grass, then `carvePath` cuts a one-tile-wide dirt path from the middle of the south edge to the north edge, never jogging sideways in two rows running so the path never forms a 2x2 block (the dirt autotile only has notched full tiles). On top of that: `placeCastle` stands a castle beside the path two or three rows from the north edge; `placeRuin` lays a one-tile-thick ring of `wall` (4–5 tiles a side, a tile in from the map's sides, with a doorway in its south side) around a temple or fort; set pieces, when the frame gives some (`FillFrame.setPieces`, see `setPieces.ts`), each go where they fit, centered in the zone their role asks for (the patch-start picker with `"piece:<role>"`), keep a tile of open ground around them like a building, and are listed on the result as `setPieces` (`{ name, x, y }`, the top-left corner); `placeBuildings` scatters a few lone buildings (`FIELD_BUILDINGS`) on grass, never side by side and never with a building or its art (its `getBuildingFootprint`: its tile, a tall building's top and the flag row) on another's; on a cave map (`caves`) `growCaveWalls` raises rock walls by cellular automaton (kept off the road's margin, the side routes themselves, the structures and the deployment rows) and `fillPockets` fills any open ground they wall off; then `growShapedPatch` (`terrainShapes.ts`) grows clumps of `water`, `forest` and `meadow` and ridges of `mountain` over the remaining grass, each from a random grass tile that layer may grow on, so every patch asked for appears while there's room, and one `smoothPatches` round fills the notches and one-tile holes the lakes and ridges leave. Everything but the path stays out of the top row and the bottom two rows (the deployment area). Impassable terrain (water, mountains, walls) keeps a tile clear of the path, so the two ends of the map are always connected. Every building and the ruin keep a tile of open ground around them, so no patch crowds them or sits under their overhanging art. Everything after the path is `fillTerrain(options, rng, path, keepClear?, pickStart?, frame?)`, which the planned generator reuses with its side routes as `keepClear` (kept free of impassable terrain like the path) and a `pickStart` that chooses where each patch starts growing (a random allowed grass tile by default). A `FillFrame` (`{ grid?, reserved?, buildings? }`) lets a map type lay its own terrain first: `grid` is the base to fill, `reserved` replaces the default top-row and bottom-two-rows edges as the tiles patches stay off, and `buildings` are placed before any others. `getReachable(grid, start)` floods the walkable tiles, and `terrainToRows(grid)` prints a grid back as text rows (the inverse of `terrainMap.ts`'s default legend). Tested in `src/game/mapGen.test.ts`.

### `src/game/mapPlan.ts`

The planned map generator, picked per region with `terrain.generator: 'planned'` (`generateMap(options, rng)` dispatches: a `terrain.archetype` other than `advance` goes to `generateArchetypeTerrain`, else planned or classic, classic being the default). `planBattle(width, height, routes, rng)` decides where the fight happens first: a three-tile deployment zone centered on any column of the south row, and an anchor in the north third for each side route (`routes - 1` of them, default 3 routes in all), alternating sides of the deployment zone and at least two columns clear of its middle. `carveRoute(width, height, from, to, rng, wobble)` walks a 4-connected route that mostly steps closer and sometimes sideways (never twice running), dropping any loop. `generatePlannedTerrain(options, rng)` carves the dirt path from the middle of the deployment zone (`carvePath` with a start column), a side route from the deployment tile on each anchor's side, then calls `fillTerrain` with the side routes kept clear and patches started by zone (`mapZones.ts`), and returns the terrain plus its `plan` and `routes`. `generateArchetypeTerrain(options, archetype, rng)` builds a map type's map (`mapArchetypes.ts`): it lays the plan's terrain, zones the map from the plan's enemy zones and roads, and calls `fillTerrain` with the plan as its frame (no castle or ruins, and the plan's own lake or mountain counts), returning the terrain with the plan's `deploymentZone`, `enemyZones` and `seizeTile`. Tested in `src/game/mapPlan.test.ts`.

### `src/game/mapArchetypes.ts`

Map types: each sets where the two sides start and the map's overall layout, and the generator fills in the rest. `MAP_ARCHETYPES` lists them: `advance` (the planned generator's own south-to-north map) and seven planned layouts, each a pure `plan<Type>(width, height, rng)` returning an `ArchetypePlan` (`deploymentZone`, `enemyZones` (one tile list per enemy group of spots), the dirt `path`, side `routes`, placed `terrain`, `reserved` tiles patches keep off, `buildings`, an optional `seizeTile` and `fill` overrides). **Crossroads**: two roads cross in the middle columns of the north half, the enemy on both flanks and the crossing to seize. **Ambush**: the warband deploys in the middle, the enemy on two or three edges with a road out to each. **Gauntlet**: a south-corner start and a road folded between one or two mountain ridges, each with a varied end and one forest gap, up to the enemy on the north edge. **Islands**: a river across the map (rows held at least two columns, level at each crossing), crossed by two or three bridges or fords, the far bank sometimes split by a two-wide channel with its own bridge. **Fortress**: a ring of wall around a fort to seize, with one or two gates in its south wall and a road through each. **Pincer**: the warband deploys on a road through the middle of the south half and the enemy closes in from both side edges at once, a route out to each. **Camps**: a south start and the enemy split between two camps (three on maps 10 or more wide), each a tent in a 3x2 clearing over the north half, the road to the nearest and routes to the rest, so they can be taken in turn. `carveRoad` walks a monotone road (it can never form a 2x2 dirt block) and `planArchetype` dispatches. Tested in `src/game/mapArchetypes.test.ts`.

### `src/game/setPieces.ts`

Hand-made bits of map the stage generator drops into procedural maps, the way roguelikes mix authored rooms into generated levels. A `SetPiece` is `{ name, role, rows, seasons? }`: text rows north to south in the terrain legend plus `?` (leave the map as it is) and a letter per building (`BUILDING_LETTERS`), a `role` (`cover`, `flank`, `outpost`, `homestead`) saying which zone it belongs in, and the seasons it shows up in (all when unset). The pieces are data in `src/data/setPieces.json` (loaded and checked by `src/data/setPieces.ts`). `checkSetPiece` throws on a malformed piece (unknown role or character, ragged rows, a building without open ground north of it for its art, `getArtRows`); `getSeasonPieces` filters by season; `getSetPieceCount(width, height)` is one per `TILES_PER_SET_PIECE` (45) tiles, at least one; `drawSetPieces(pieces, count, rng)` draws different pieces, each mirrored (`mirrorPiece`) half the time, biggest first. `canPlacePiece(grid, piece, origin, limits)` / `getPieceOrigins` find where one fits: every tile it changes on the map, on grass (or on the road, under open ground other than a building, which leaves the road running through), off blocked tiles; walls and water off the road's margin; no wall on the west or east column; each building's art rows on the map and under no other art. `stampPiece(grid, piece, origin)` gives the tiles to lay (none on the road) and the buildings. `fillTerrain` places them. Tested in `src/game/setPieces.test.ts` and `src/data/setPieces.test.ts`.

### `src/game/terrainShapes.ts`

Natural shapes for the generator's terrain, after Brogue's lakes and caves. `growShapedPatch(grid, start, size, rng, blocked, terrain, shape)` grows a patch one grass tile at a time like a flood, picking each next tile by weight (`weightedShuffle`): a `blob` favors the tiles it already wraps most, so it grows into a clump with few spurs; a `ridge` favors its line through the start (west to east or north to south, half the time each), then the rows beside it (`RIDGE_PULL`), so mountains run in chains a tile or two thick. `smoothPatches(grid, terrains, canFill)` is one cellular-automaton round: grass with at least `FILL_NEIGHBORS` (5) of its 8 neighbors of one terrain turns into it. `growCaveWalls(grid, rng, blocked)` is the classic cave automaton over the map's grass (seed rock at `CAVE_FILL` odds, then `CAVE_STEPS` rounds of "rock with 5 or more rock neighbors, or 4 if already rock"; off the map counts as rock, so walls hug the sides), with `blocked` tiles taking part but left open at the end; `fillPockets(grid, from, keep)` fills open ground walled off from `from`. Tested in `src/game/terrainShapes.test.ts`.

### `src/game/mapLoops.ts`

The loop pass, after Brogue's: a battle map with only one way from the deployment zone to the enemy gets a second. `findChokepoint(grid, from, to)` finds a tile every way runs through (null when `countRoutes` finds two or more, or none); `findDetour(grid, from, to, avoid)` is the cheapest way round it, walking at 1 a tile and opening water or mountain (`OPENINGS`) at `OPEN_COST` (4) a tile, never through walls; `openLoops(grid, from, to)` opens up to `MAX_LOOPS` detours, water turned to fords and mountains to grass. `layOutStage` runs it on every candidate. Tested in `src/game/mapLoops.test.ts`.

### `src/game/mapZones.ts`

Where on a planned map the fight happens. `getZones(width, height, deploymentZone, enemySide, routes)` gives each tile the first zone that fits, by straight steps: `home` (within 2 of the deployment zone), `enemyHome` (within 2 of the enemy side), `midfield` (about as far from one side as the other), `flank` (2 or more tiles off every route) or `lane`. `pickZonedStart(zones, terrain, index, starts, rng)` picks where a patch starts (or a set piece is centered) from `PATCH_ZONES`: water and mountains on the flanks, forests by turns in the midfield and near each side's start, set pieces by role (`piece:cover` in the midfield, `piece:flank` on the flanks, `piece:outpost` by the enemy's start, `piece:homestead` near home or on a flank), anything else anywhere, falling back to any start when none is in its zones. `generatePlannedTerrain` passes it to `fillTerrain` as the patch-start picker. Tested in `src/game/mapZones.test.ts`.

### `src/game/mapCheck.ts`

The hard rules every generated battle map must keep, in one place. `checkMap({ grid, buildings, deploymentZone, enemyTiles })` returns a sentence for each rule broken (empty when none): every deployment and enemy tile can be walked to from the first deployment tile; no 2x2 block of dirt (the dirt autotile can't draw one); no wall on the map's west or east column (the wall autotile would draw it as a thick block); and every building stands on grass, on its own tile, with room north of it for its art (a tall building's top and a flag) and no other building's art over it. `mapGen.ts` is built to keep these; the check catches a generator change that doesn't. Tested in `src/game/mapCheck.test.ts`.

### `src/game/mapScore.ts`

Pure grading of a battle map for pace and fairness. `getMapMetrics(grid, deploymentZone, enemyTiles)` measures `nearestEnemy` (fewest walking steps from a deployment tile to an enemy, via `getWalkingDistances`; null when none can be reached), `meanEnemy` and `farthestEnemy` (the average and most steps to the reachable enemies), `routes` (how many tile-disjoint paths join the two sides, i.e. how many tiles must be blocked to cut them apart, found by `countRoutes` with a small max flow and capped at `MAX_ROUTES`), `openShare` (walkable tiles over all tiles) and `playerCover` / `enemyCover` (forest within `COVER_REACH` steps of each side). `scoreMap(metrics, targets?)` turns them into a penalty against `MAP_SCORE_TARGETS` (or `CAVE_SCORE_TARGETS`, the same but at least 62% open, for a cave map; an enemy at most 6 steps out so a fight can start on turn 1, the enemies on average at most 9 and at most 13 steps out so the whole enemy is in the fight by turn 2 or 3 on a big map, at least 2 routes, at least 75% open ground, even cover): 0 meets every target, lower is better, and an unreachable enemy scores worst of all. Tested in `src/game/mapScore.test.ts`.

### `src/game/mapSize.ts`

Pure sizing of a Warband stage's map for the fight on it. `getMapSize(unitCount, archetype, rng, min?)` aims at `TILES_PER_UNIT` (8) walkable tiles per unit on the field, assuming `OPEN_SHARE` (0.85) of the map is walkable (`CAVE_OPEN_SHARE`, 0.72, for a cave map, so it's sized up for its walls; `getTargetArea`), shapes it by the archetype's aspect (`ARCHETYPE_SHAPES`: crossroads, islands, pincer and camps wide, ambush near square, gauntlet capped at 10x9 since its switchback road grows twice as fast as the map), nudges the width a column either way from the Rng, and keeps it between `min` (the region's size, `MIN_MAP_SIZE` 8x8 by default) and `MAX_MAP_SIZE` (14x10, a pace cap, not a screen cap). Maps grow wide before deep, since depth is what the warband walks. `resizeMapOptions(options, size, rng)` sets the size and scales the lake, mountain, forest, meadow, ruin and building counts by the area (`scaleCount` rounds a fraction up or down by chance), keeping patch sizes, so a region keeps its feel on a bigger map. Used by `sizeStageRegion` in `warband/stageLevel.ts`. Tested in `src/game/mapSize.test.ts`.

### `src/game/buildings.ts`

`BUILDING_KINDS` — every kind of building a map can hold (house, fort, temple, castle, …) — and `BuildingPlacement` (`{ x, y, building }`). Each building stands on one walkable tile; its art lives in `tileset.ts`.

### `src/game/mapArt.ts`

Pure picking of the one-tile overlays drawn from the terrain sheet over the terrain. `getFeatureSprites(grid, FOREST_ART, MOUNTAIN_ART)` gives a forest variant per forest cell and stacks mountains a column at a time (body, or body with the next peak baked in when a mountain is south; a cap in the cell north of a column's top, or the forest-with-peak tile when that cell is forest). `getBuildingSprites(buildings, palette, BUILDING_ART)` gives each building, a tall building's top over the cell north of it, and the palette's flags, all in one palette. `getWallAutotile(palette)` is the `wall` terrain's rampart autotile in that palette (it joins gates, so a wall runs on through its gateway). `getCrossingSprites(grid, BRIDGE_ART, GATE_ART, FORD_ART, MAP_PROPS_SHEET)` draws the map types' crossings: a bridge over water (vertical when water or ford lies west or east, else horizontal), ford stepping stones, and a gate's posts under units with its lintel over them, the last two from `src/assets/map-props.png`. `getHazardSprites(grid, SPIKES_ART, SPIKES_SHEET)` puts a spike trap (the resting frame of `TRAP_ART.spikes`, the strip in `src/assets/traps/`) on each spikes cell, under units; GridScene's `springTrap` plays a trap's strip once when a unit is shoved onto spikes or trips a mine. A sprite can name its `sheet`, the terrain sheet by default. Variants are picked by `pickVariant(x, y, count)`, a position hash, so a map always draws the same. Each sprite has a layer: `ground` (under units), `cap` (art poking into the cell north) or `roof` (over units). Art drawn north of the cell it stands on (a mountain's cap, a flag, a tall building's top) also carries `baseY`, its cell's row, and GridScene y-sorts it against the units with `depthOrder.ts`. Tested in `src/game/mapArt.test.ts`.

### `src/game/depthOrder.ts`

Pure draw order between units and tall map art. `unitDepth(row)` puts each unit in a narrow band of depths sorted by row (GridScene's `sortUnitDepths` re-applies it every frame from the sprite's position, so a walking unit sorts by its fractional row; an attacking unit keeps `ATTACK_DEPTH` until its swing ends). `tallArtDepth(baseY)` sorts art rising out of row `baseY` half a row north of it, so it covers units north of its base and stays behind units on it or south of it (a unit standing north of a mountain is hidden behind its peak, a tall orc on the mountain pokes in front). The band sits over range highlights and intent arrows, under rank badges, the attacking unit and roofs. Tested in `src/game/depthOrder.test.ts`.

### `src/game/battleSetup.ts`

Which battle the map runs and what follows it. `BattleSetup` is `{ mode: 'story', chapter }`, `{ mode: 'training', unitClass }` or `{ mode: 'warband', seed, stage, run?, camp? }` (the store's `battleSetup` re-exports the type; `camp` is a run back at camp over its site, with nothing to fight, which `runCamp(run)` builds for `warbandFlow.enterCamp`). `STORY_CHAPTERS` lists Story Mode's chapters in order as `{ name, createLevel(content) }`, each picking its own dialog file (just chapter 1, the demo battle, for now). `GameContent` (`{ dialogs, regions }`) is the authored data battles are built from, `DEFAULT_CONTENT` the built-in files; `createBattleLevel(setup, content = DEFAULT_CONTENT)` builds the level a setup names from it (story chapters' and training's dialog, a Warband stage's region), so uploaded configs can replace the built-in ones, and `describeBattle(setup, content)` names Warband stages from it too. `getNextBattle(setup, seed)` is where a victory leads: the next story chapter until the last one, then null (back to the title); the next Warband stage on a fresh map from `seed`, without end (for a stage with no run, i.e. a region preview); null after training. A stage of a run throws there: its next stage comes from `finishStage`. `runStage(run)` is the battle for a run's current stage: `{ mode: 'warband', seed: getStageSeed(run.seed, run.stage), stage, run }`, which `createBattleLevel` builds with the run's roster (`restoreRoster`) and deploy cap. `getBattleDiceSeed(setup)` is the seed a battle's dice are fixed to: a stage of a run's `getBattleSeed`, else null (roll fresh). `describeBattle` titles a battle ("Chapter 1: The Old Gate", "Stage 2: Lakeside", "Training"). `FIRST_STORY_CHAPTER` and `runStage` are what the title screen starts. `regionPreview(index, seed, settings)` is the battle that shows region `index` (its first stage, on the map `seed` makes, so the same map `createStageLevel` makes from that region), or null for a region that doesn't exist; the config editor's map preview runs it. `generatedMap(seed, settings, region = null)` is the Map Generator's battle: region `region` (or, with none, one picked from the seed) previewed the same way, so one seed is always one map; null for a region that doesn't exist. Tested in `src/game/battleSetup.test.ts`.

### `src/game/objectives.ts`

A battle's objective, as data, and the rule that decides the battle by it. `Objective` is `{ kind: 'rout' }` (`ROUT`, also `DEFAULT_OBJECTIVE` for levels that don't set one), `{ kind: 'seize', tile }`, `{ kind: 'boss', unitId, name }` or `{ kind: 'survive', turns }`; a level's optional `objective` (on `Level`) picks it. `ObjectiveSpec` is the unplaced form a Warband region names (`{ kind }`, plus optional `turns` for survive, `SURVIVE_TURNS` when unset). `describeObjective(objective)` gives the Objective screen's words as frozen `{ goal, defeat }`, and `getObjectiveStatus(objective, turn)` the header's short readout, the kind and the turn out of the turns it has ("Seize 3/40", "Survive 2/4"). `getObjectiveOutcome(objective, snapshot)` decides the battle from a `BattleSnapshot` (`{ turn, units: [{ unitId, team, alive, position }] }`): losing every player unit is a defeat whatever else happened (via `turns.ts`'s `getBattleOutcome`), every enemy down wins any kind, and each kind adds its own win: a living player unit on the seize tile, the boss down or gone, or the turn passing the survive turns. Every kind but survive is lost once the turn passes `TURN_LIMIT` (40) undecided (`isPastTurnLimit`), so a battle that stalls still ends, played by hand or by Auto. Tested in `src/game/objectives.test.ts`.

### `src/game/warband/regions.ts`

Warband Mode's regions: the shape of the per-stage map settings and the rules for picking a stage's region; the built-in regions themselves are data, in `src/data/regions.json` (see `src/data/`). A `RegionConfig` is `{ name, description?, terrain, enemies, treeChance, palette, objective?, biome?, season? }` (`season` the art its maps are drawn in, see `tileset.ts`) (`objective` an `ObjectiveSpec` every stage in the region plays; `biome`, one of `REGION_BIOMES`, the land a realm site must stand on to play it, see `realm/realmRegions.ts`), where `terrain` is the `generateTerrain` options (map size included), `enemies` is a list of `EnemyGroup`s (see `enemySpawns.ts`), and `RegionSettings` is `{ stagesPerRegion?, regions, finalStage?, parkedRegions? }` (`finalStage` the stage whose win wins the run; unset, a run never ends in victory; `parkedRegions` regions kept in the file but out of the run, e.g. Starship while it's built). `getRegionStages(index, settings)` says which stages a region covers: with `stagesPerRegion`, that many each in turn; without it (the built-in 30-stage run over 13 regions), the stages before `finalStage` shared out evenly among all but the last region, which plays the final stage; stages past the end reuse the last region. `getStageRegion(stage, settings)` / `getStageRegionIndex` read a stage's region. A region's enemy group levels are relative: the battle puts its weakest group at the stage's level (`enemyCurve.ts`). Tested in `src/game/warband/regions.test.ts`.

### `src/game/warband/regionsFile.ts`

`RegionSettings` as a JSON file players can write and upload. `parseRegionSettings(text)` checks every field against `REGION_LIMITS` (whole numbers in range, `[min, max]` size pairs, chances 0–1, known palettes, no unknown keys so typos fail), throwing with the field's path (`regions[2].terrain.lakes must be …`), then generates each region on a few seeds so an accepted file can't break a run or place fewer enemies than its groups ask for; `explainEnemyShortfall` says why not, aimed at the setting to change (a max distance closer than the area's nearest tile, a min distance past its farthest, an area nothing can reach, a count bigger than the spots that fit, or groups crowding each other out). Older files still read: Dungeon Mode's `{ floorsPerConfig, floors }` (its errors then name those keys), an enemy group's `region` as its `area`, and `enemyCount: n` as one group of `n` in `NORTH_THIRD`. `formatRegionSettings(settings)` writes settings back out, always in the current shape (the built-in ones are the editor's download), through `formatRegionsJson(json)`, which lays out any JSON, a draft being edited included, the way Prettier keeps the file: anything that fits on its line on one line. Tested in `src/game/warband/regionsFile.test.ts`.

### `src/game/warband/realm/`

The realm a Warband run travels across, Tactics Ogre style: one seeded map per run, grown from home in the west to the Warlord's Hold in the east, with battlefields, villages, forts, towns and shrines joined by roads. All pure; `realm.test.ts` and a test per module cover it, and `.claude/skills/tileset/scripts/realm-preview.ts` renders realms to PNG for a look.

- `realm.ts` — `generateRealm(seed, settings)` builds a frozen `Realm` (`{ seed, name, depth, shape, sea, grid, sites, roads, rivers, seasons, provinces, buildings, palette }`). The depth is `getRealmDepth(settings)` (the final stage). Sites stand one column per depth, every `REALM_COLUMN_SPACING` tiles (`layOutColumns`: home and the Hold alone, two at depth 1 and before the Hold, else two or three). `pickKinds` decides each site's `SiteKind`: two battles at depth 1, villages at depth 2, then a mix weighted by `SITE_WEIGHTS` with a fight at every depth, forts from `FORT_FROM`, a town at least every `TOWN_EVERY` depths and always one before the Hold, at most one each of a town, shrine, elite lair (`'elite'`, see `elites.ts`) and wayside (`'event'`, see `events.ts`) per depth. Each site is a `Site` (`id` `"<depth>-<row>"`, `name`, `kind`, `depth`, the `biome` of the land around it, the `region` it plays and its enemies' `levelOffset`). Roads (`{ from, to, path }`) only join neighboring depths, never crossing. `getSite`, `getNextSites` (north to south), `getRoad`, and `getRealm(seed, settings)`, a small cache so the overworld, the map scene and the simulator share one build.
- `realmTerrain.ts` — the land: value noise (`createValueNoise`) for height, wetness and woods turned into mountains, lakes, forests and meadows by `LAND_RULES`, with the land rising toward the east so mountains gather around the Hold and the west stays open; `clearSpecks` dries up ponds too small to read as lakes. `generateRealmLand(width, height, rng, { shape, sea })` draws the same noise whatever the shape and then reshapes it: `ranges` rises toward the east, `spine` raises a ridge of mountains along the middle rows, `valley` raises walls along the outer rows, `lakeland` wets the middle, and `coast` (like any shape with a `sea`) turns the rows along one edge to water, as deep as noise says column by column (`LAND_RULES.seaDepth`, deeper on a coast).
- `realmRivers.ts` — `layRivers(land, sites, roadTiles, rng)` lays the realm's rivers (`RIVER_RULES`: one per 32 columns, one to four), each from a mountain tile with open ground beside it toward the nearest lake far enough away (else the nearest map edge), one tile at a time to the neighbor nearest its end plus a random nudge, with a cost for turning so it bends in curves, never through a mountain, a tile by a site, another river or a tile it has been on, stepping onto a road only to cross it (never two road tiles in a row, no road for a few steps after a crossing). Rivers roll their own dice from the seed, so a realm's land, sites and roads are what they were before it had rivers. `riverCrossings` finds where a river crosses a road and which way it runs there. `seasonsByDepth` in `realm.ts` gives each depth the season most of its sites' regions are drawn in (home taking the first stop's), so the map's paper changes along the run, and `provincesByDepth` the realm's `Province`s (`{ region, name, from, to }` by depth): runs of depths playing mostly one region, a lone depth joining the province before it. The realm's `shape` (`REALM_SHAPES` in `realmTerrain.ts`: `ranges`, `spine`, `valley`, `lakeland`, `coast`) and `sea` (`'north'`, `'south'` or none; a coast always has one, the rest half the time) roll from their own dice too.
- `realmRoads.ts` — `linkColumns(west, east, rng)` links two columns of sites without crossings, every site getting a way in and on; `carveRoad` lays a road with A\* over `ROAD_COSTS` (round lakes and mountains, reusing road already laid, bridging water only when the way round is far longer), never through another site, kept between the two columns and never closing a 2x2 block of dirt, which the autotile can't draw.
- `realmRoutes.ts` — `getRoadNetwork` joins actual road steps into the tile network shared by travel and `realmInk.ts`. `getOnwardRoads` follows its junctions to sites at the next depth, stopping at every site and using only roads between the current and next columns. `getNextSites` and `getRoad` use these routes, so a branch visible at a shared junction is selectable even when it wasn't an original generated link. Original paths are preserved; extra routes follow existing road steps, with results cached per realm and starting site. Seeded map generation and saved routes stay unchanged.
- `realmRegions.ts` — which region a site plays (`pickSiteRegion`): one meant for its depth or one before (`REGION_WINDOW`), preferring one whose `biome` matches the land around the site (`detectBiome`: lake, hills, forest or meadow); a fort plays a `'fort'` region `FORT_LEVELS` stronger (its `levelOffset`, 0 elsewhere, since enemy levels come from the stage); depth 1 plays the first region, the Hold the last, and the last is kept for the Hold.
- `realmNames.ts` — `nameRealm` ("The Sundered Reach") and `nameSite(kind, biome, rng, taken)` ("Ashford", "Greyfen Marsh", "Fort Rook"), never repeating.
- `realmInk.ts` — the realm as an old parchment map in the manner of Tactics Ogre and Final Fantasy Tactics. `getRealmInk(realm)` lays it out: which cells are water, the season bands (`getSeasonBands`: `realm.seasons` as stretches of columns, runs of one season joined), the ink symbols (`INK_STAMPS`, 32x32 images in `src/assets/realm/ink/`: the season's trees on forests and peaks on mountains with foothills, tufts on meadows, cracked ground in the underworld, waves on open water with ships on the open sea and the odd serpent, reeds on open ground by water, and out on open ground away from sites the rare ruin, standing stones or windmill; `SEASON_INK` says which stamps each season draws: snowy pines, bare trees and snow-capped peaks in winter, dead trees and cracks in the underworld), placed by `hashCell` so the same realm always looks the same and sorted back to front; the rivers (`realm.rivers`) as lines pinned through the middle of every tile where they cross a road, with a bridge stamp there (`bridge-h` across a river running north–south, else `bridge-v`); the road network cut into stretches between sites, forks and river crossings (`getRoadChains`, so road two routes share is drawn once and the road too passes through the bridge's middle), each straightened (`simplifyLine`), nudged as if hand-drawn (`wobbleLine`) and rounded (`smoothLine`); the provinces as stretches of columns (`getProvinceBands`), which cells are mountain and forest (for the raster's relief), and names for the biggest lakes, woods and ranges (`findPatches`; a lake along the map's edge is a sea), with each province's name lettered along the edge the sea isn't on, on two rows by turns. `getRouteLine` joins the stretches a route of road tiles runs along into one line (the screen highlights and walks it), and `pointAlong` finds a point some way along a line.
- `inkRaster.ts` — `paintRealmInk(ink, seed, stamps)` paints that layout into an RGBA buffer, no DOM: mottled parchment (value noise) in each season band's paper (`SEASON_PAPER`: summer's tan, autumn warmer, winter pale and cool, the underworld scorched; blended over a tile and a half across a ragged, noise-wandered edge), a faint graticule, lakes blended between cell centres and roughened into curving shapes, washed darker (in the band's water) away from a thick ink coast with a faint red line outside it, hatching down the east face of every range and stipple round every wood (`paintRelief`), rivers as water lines edged in ink widening to their mouths, dotted province borders wandering a little (`paintProvinceBorders`), a double ink border inside the edge, roads as pale lines edged in ink, then the stamps. `OverworldScreen` puts the buffer on a canvas, and the tileset skill's `realm-preview.ts` writes it to a PNG.

### `src/game/warband/elites.ts` and `events.ts`

The realm's two riskier stops. `elites.ts`: `ELITE_AFFIXES` (Armored, Swift, Berserk, Regenerating, Keen, Brutal), each `{ id, name, description, modifiers }`; an elite lair rolls two from the run's seed and depth (`rollEliteAffixes`), and `createBattleLevel` gives each enemy one in turn and the boss both (`applyEliteAffixes`: the modifiers through `applyModifiers`, the id in `Unit.eliteAffixes`, the name before the unit's, e.g. "Armored Goblin", and `Unit.rank` `'elite'` for all but the boss, which the map badges); the unit info screen lists them with the boons. Elite creep brings affixes to ordinary battles too (`applyEliteCreep(units, seed, stage, bossUnitId)`, from `createBattleLevel` outside lairs): from `ELITE_CREEP_FROM_STAGE` (5) each enemy has `getEliteCreepChance` (3% a stage, up to 100%) to carry one random affix, and the boss `getBossAffixCount` (one per `BOSS_AFFIX_STAGES`, 6, stages) different ones, seeded by the battle's seed and stage. A lair's reward pick is relics the run doesn't hold (`isEliteClear` in `rewards.ts`). `events.ts`: twelve `EVENTS` (Old Shrine, Deserter, Gambler, Healing Spring, Bandit Toll, Abandoned Cart, Wandering Swordmaster, Broken Wagon, Knight's Grave, Ruined Chapel, Mercenary Camp, Blood Altar), each two or three `EventChoice`s (`label`, `detail`, `blocked`, the reason the run can't take it, and `resolve`). Arriving at a wayside draws one the run hasn't met (`rollEvent`) as `pendingEvent`; `getEventChoices` and `resolveEvent(run, index)` (the effect, the event settled and added to `seenEvents`, and a line saying what happened) do the rest. `addToConvoy` adds an item to the convoy. Tested in `elites.test.ts` and `events.test.ts`.

### `src/game/warband/travel.ts`

A run's journey across its realm. A run that travels carries a `route` (`RunRoute`: the ids it has `visited` from home, and `at`, a `RunSite` snapshot of the site it stands at, so a battle can be set up without rebuilding the realm); a run without one is a linear stage-after-stage run. `startRoute` sets a run out at home (`HOME_SITE_ID`). The run's `stage` is its site's depth, so everything keyed on the stage keeps working, and a won battle moves it past the site, which is how `isSiteDone` tells a finished site (a shrine's is its blessing picked; a town is never done, but can always be left). `getTravelChoices(run, realm)` lists where the roads lead on once it's done, `canTravel` checks one, and `travelTo` arrives (at a shrine, owing a free reward pick, its blessing; at a wayside, owing its event). `isInTown`, `getSiteRegion(run, settings)` (the site's region at the stage's level plus the site's `levelOffset`, `levelRegionForStage`), `getClearGold` (a stage's clear gold, `FORT_GOLD_MULTIPLIER` times at a fort) and `isFinalBattle` (the Hold, or the final stage on a linear run). Tested in `src/game/warband/travel.test.ts`.

### `src/game/bosses.ts`

Bosses with rules of their own, as a data table plus the pure rules that read it. `BOSS_RULES` holds a `BossRules` per boss (`{ id, title, name, taunt, horn?, enrage? }`); the first is `ORC_WARLORD` ("Grukk, Orc Warlord"), then `RED_DRAGON` ("Ignareth, Red Dragon", the Dragon's Roost at stage 10: no horn, enrages at half health). A boss objective whose target's name matches an entry's `title` (`findBossRules`, any case) fights by it: `createBossState(objective)` gives the battle's `BossState` (`{ unitId, rulesId, enraged, incoming, called }`, null for a boss without rules, such as a generic "<Class> Chief"). `horn` (`{ every, unitClass, level, limit, reach }`): on turn 1's enemy phase and every `every` turns after (`isHornTurn`), the boss marks the open tile nearest it on foot (`pickHornTile`), and at the next enemy phase a `unitClass` enemy of `level` arrives there (`horn-1`, `horn-2`, ...), done for that phase, unless someone stands on it (`canArrive`), which blocks it; at most `limit` a battle. `enrage` (`{ below, strength }`): once an action leaves the boss alive at or under `below` of its max HP (`shouldEnrage`), it gains `strength` STR and stops holding its ground, so the enemy AI marches it. `battle/commands.ts` applies both. Tested in `src/game/bosses.test.ts` and `src/game/battle/boss.test.ts`.

### `src/game/enemySpawns.ts`

Pure enemy placement for generated maps. An `EnemyGroup` is `{ count, unitClass?, area?, level?, minDistance?, maxDistance?, health?, levelUpOnKill?, boss? }` (`level` fields its enemies above level 1; `boss` names its first enemy as the stage's boss): `area` (a `SpawnArea`) is a box as `[from, to]` fractions of the map's columns (`x`) and rows (`y`), the distances are walking steps from the deployment zone, and `unitClass` is the class id (a `UNIT_CLASSES` id, checked by the regions parser) its enemies are. `getWalkingDistances(grid, starts)` is a breadth-first search giving each reachable tile's step count from the nearest start (impassable terrain blocks). `isInArea(p, area, width, height)` checks a tile against a box (tiles from `from × size` up to, not including, `to × size`, rounded down). `pickEnemyTiles(grid, groups, deploymentZone, rng)` returns one list of tiles per group, in order: each group's shuffled pick of reachable tiles outside the zone that pass its limits and that no earlier group took, shorter than `count` when too few qualify. `pickZonedEnemyTiles(grid, groups, deploymentZone, zones, rng)` places them for a map type instead: enemies dealt round-robin across its enemy zones (keeping each group's distances but not its area), falling back to another zone and then any reachable tile two or more steps away; with no zones it is `pickEnemyTiles`. `countEnemies(groups)` totals them, and `NORTH_THIRD` is the area older configs' enemies stood in. `getGroupRoom(grid, group, deploymentZone)` measures one group's room on its own (`{ inArea, nearest, farthest, fits }`: reachable tiles in its area, the fewest and most steps to them, and how many are within its distances), for explaining a group that won't fit. The Regions page's cards describe each group with `describeEnemyGroup` (`src/ui/enemyGroups.ts`). Tested in `src/game/enemySpawns.test.ts`.

### `src/game/warband/run.ts`

A Warband Mode run, the state carried from stage to stage: `RunState` is `{ seed, stage, roster, convoy, gold, relics, deployCap, fallen, pendingReward?, pendingRecruitment?, pendingGuest?, pendingDraft?, pendingBoons?, chronicle?, route? }` (`route` the run's journey across its realm, see `travel.ts`), frozen (`pendingReward`, `{ stage, rerolls, clearGold, flawless }`, is set while a won stage's reward pick is still owed), with the roster stored as plain `UnitSnapshot`s (`id`, `name`, `classId`, level, XP, current and max HP/MP, the other stats, its bag as `{ itemId, quantity }`, its worn gear as `equipment` (slot → item id) and its `innate` attacks by id, plus the `boons` it has taken and the `quirk` it joined with; `parseRun` sorts an older save's single inventory into that shape with `normalizeSnapshot`, sending what doesn't fit to the convoy) so a run saves as JSON. `snapshotUnit(id, unit)` takes a snapshot and `restoreUnit(snapshot)` rebuilds the Unit through `createUnitOfClass`, which supplies what a snapshot doesn't store (movement, weapon types, growths); `restoreUnit` gives the unit its boons' and quirk's modifiers and `restoreRoster(run)` gives the roster as Units by unitId, each also carrying the run's relics' modifiers (see `modifiers.ts`), and `RUN_ITEMS` is every item a saved inventory can name (weapons, armor, the Heal staff, potions). `createRun(seed, roster)` starts on stage 1; `applyBattleResult(run, { units, convoy?, kills?, bossDefeated?, elapsedMs? })` writes each deployed roster unit's XP, levels, HP and inventory back and moves the dead to `fallen` for good (the Phoenix Feather keeps the first at 1 HP instead, and is spent), leaving undeployed units and enemies alone, adds any items the battle sent to the convoy (loot a full-handed unit couldn't carry) to its end, and records the battle in the run's `chronicle` (`chronicle.ts`; a run saved without one reads as empty); `finishStage(run, result, outcome, finalStage?)` → `{ run, over, won }` is what the map calls when a stage's battle ends: the result written back, then on a victory the next stage; a defeat (or a roster left empty) ends the run, and a victory on `finalStage` (the regions' `finalStage`) wins it, ending it on that stage with `won` set. `advanceStage`, `isRunOver` (an empty roster) `getStageSeed(runSeed, stage)` (a stage's map seed, the same for the same pair) and `getBattleSeed(runSeed, stage)` (the seed its battle's dice roll from, so a whole run replays from its seed) round it out. `serializeRun` / `parseRun` save and load it, `parseRun` returning null for anything that isn't a valid run or names an unknown class or item. Tested in `src/game/warband/run.test.ts`.

### `src/game/warband/relics.ts`

Run-long relics, Slay the Spire style. A `Relic` is `{ id, name, description, modifiers }`; `RELICS` lists the 17 there are. Most are modifiers every roster unit carries into battle (`getRelicModifiers(relicIds, stage)`, applied by `restoreRoster` in `run.ts` at the run's stage): Hawk's Lens, Gambler's Coin, Feather Cloak, Duelist's Gauntlet, Bulwark Crest, Berserker's Brand, Hunter's Charm, Winged Boots, Bloodpact, Mending Charm, Mana Spring, Whetstone and Scholar's Quill. Four change a run rule instead, and the rule checks for them by id with `hasRelic`: `BOUNTY_LEDGER` (gold per kill, `getStageClearGold` in `rewards.ts`), `PHOENIX_FEATHER` (the first ally to fall stays on at 1 HP, once, `applyBattleResult` in `run.ts`), `FOUR_LEAF_CLOVER` (four reward choices, `getRewardChoices`) and `FIELD_KITCHEN` (a free rest, `getRestCost` in `camp.ts`). A modifier relic's flat damage, guard and healing grow with the stage like boons (`getScaledRelicModifiers`, using `getStageScalePercent` and `scaleModifier` from `boons.ts`); rates, MOV, MP and XP stay put. A relic made only of modifiers that add up (`isStackingRelic`) can be held twice (`MAX_RELIC_COPIES`), each copy adding its modifiers again (`countRelic`, `canTakeRelic`); `getOfferableRelics(held)` is what a reward may offer (unheld, or a stacking one held once), and `getRelicDescription(relic, stage, copies)` fills a relic's `template` with its number then, copies added up (the camp's list via `toRelicViews(relicIds, stage)`, one entry per relic with "×2" on a doubled one). `rollStartingRelics(runSeed)` is the three a new run picks from (seeded, so the same run always offers the same), `rollRelics(rng, held, count)` draws relics a run doesn't hold (starting picks and waysides), `rollOfferableRelics` draws offerable ones (reward picks), and `findRelic` / `getUnownedRelics` look them up. Tested in `src/game/warband/relics.test.ts`.

### `src/game/warband/boons.ts` and `levelUpPicks.ts`

Level-up boons, Vampire Survivors style: each level a roster unit gains lets it pick one of three on top of its fixed growth gains. `boons.ts` holds `BOONS` (each a first-rank common one at the base scale), each `{ id, kind, name, description, stat?, modifiers, rarity, stagePercent, rank, entry, tags }`: **stat** boons (+2 to a stat, +4 max HP, repeatable), **skill** boons (a skill from the unit's own class's `CLASS_SKILL_PICKS`, as a `skill` modifier; the retired Power Strike, Cleave, Shield Bash and Throw Stones boons are kept only so old saves resolve) and **passives** (a unit's own modifiers, e.g. Keen Eye +15 hit, Stalwart, Monster Hunter, Fleet, Bloodthirst, Regeneration, Quick Study, Ferocity +8% damage, Thick Skin −8% damage taken, and the procs Twin Strike (10% a strike to strike again), Finisher (fells a foe left at 4% of max HP or less), Cleave Through (25% of a hit splashed beside the target), Chain Kill (20% a kill earns a free strike) and Momentum (a kill lets the unit move 2 more tiles; max rank 2)), each taken up to its max rank (`MAX_BOON_RANK` 5; Fleet and Quick Study 2), every rank stacking. Every stat and passive offer rolls a rarity (`rollBoonRarity` with `getRarityOdds(stage, luck)`: common / rare / epic / legendary at `RARITY_PERCENT` 100 / 150 / 250 / 400) and grows with the stage it's offered at (`getStageScalePercent`: 6% a stage past stage 4); flat damage, guard, healing and stats scale with both, rates, percent terms and MP with rarity only, MOV, XP and skills not at all. A taken boon is kept in `Unit.boons` as an entry string (`encodeBoonEntry`: the bare id for a common one at the base scale, else `id|rarity|percent`), which the unit's snapshot keeps (`UnitSnapshot.boons`) and `restoreUnit` turns back into scaled modifiers (`getBoonModifiers`, `findTakenBoon`, `getTakenBoonList`); evolutions read the ids (`getBoonIds`). `isBoonEligible(unit, boon)` keeps out STR for a caster and INT for a fighter, a skill outside the unit's class picks or already known, and a passive at its max rank; `rollBoons(unit, rng, stage, banished?)` offers a stat boon, a skill (a second passive when none is left) and a passive (the next rank of one the unit has, `OWNED_PASSIVE_CHANCE` of the time), topping up from what's left; `takeBoon(unit, boon)` raises the stat and records the entry. `levelUpPicks.ts` is the run side: `queueLevelUpBoons(before, after, taken?)` owes a pick (`RunState.pendingBoons`, `{ unitId, level, stage?, gains? }`, the stage being `before`'s, which the offer grows with) for every level gained between two runs along with its rolled stat gains, bar the `taken` ones (picked in battle), `getBoonOffer(run)` rolls the first owed pick's offers from `getBoonSeed(runSeed, unitId, level)` (so a reload offers the same), `pickBoon(run, index)` takes one and moves on, and `settleBoons` drops picks it can't offer (a unit gone, nothing left to take). A pick can be redrawn (`getBoonRedraws`): once per battle for free (`rerollBoonPick` rolls the pick again from `getBoonSeed(..., roll)`, the pick keeping its `roll`, and marks `RunState.boonRerollStage`; a battle's own picks and those owed after it, until the next battle, share one), and `BOON_BANISHES` (2) times a run by banishing a boon (`banishBoonPick`: its id joins `RunState.banishedBoons`, which every later offer leaves out, and the pick is drawn anew); the run commands are `reroll-boons` and `banish-boon`, and the level-up screen shows them as Reroll and Banish under the boons (Banish switches the screen to picking the boon to banish). In a battle the pick comes as the level up happens: GridScene opens `getBattleBoonOffer(run, unitId, unit, level, gains, { roll, banished })` (the same seeded boons, rolled on the unit as it stands) on the level-up screen right after the XP bar, mid-playback, and the pick is a `take-boon` battle command, so undoing the action that leveled the unit takes it back too; the battle's result lists the picks taken (`BattleResult.boonsTaken`, from `getBoonPicks(history)`) so the run doesn't owe them again, along with whether the battle spent its free reroll (`boonRerolled`) and what it banished (`banishedBoons`), which `applyBattleResult` writes to the run. Headless runs take no picks in battle and owe them all after it. Tested in `src/game/warband/boons.test.ts` and `levelUpPicks.test.ts`.

### `src/game/warband/boonTags.ts`

Build tags for level-up boons (Power, Precision, Guard, Evasion, Kill, Blood, Mana, Move, Status, Team), so offers grow a build instead of a pile of the biggest numbers. `getBoonTags(id)` gives a boon's zero to two tags (stamped on each `Boon` as `tags`), `CLASS_TAGS` gives each class one or two leanings, and `getUnitTagCounts(classId, boons)` counts a unit's leanings plus every tag of each passive and skill boon it has taken (each rank counts, stat boons don't). `rollBoons` draws each slot with `weightedShuffle` (`rng.ts`) by `getAffinityWeight(id, counts)`: 1 for a boon sharing no tag, +`AFFINITY_PER_TAG` per shared count, capped at `MAX_AFFINITY_WEIGHT`. The level-up screen shows the tags, lighting the ones the unit already leans toward (`boonPickView.ts`), and the run policy (`getBestOfferIndex` in `runPolicy.ts`) leans the same way. Tested in `src/game/warband/boonTags.test.ts`.

### `src/game/warband/keystones.ts`

Keystones, Path of Exile style: one rule-breaking pact for the whole warband. Clearing every `KEYSTONE_INTERVAL` (10) stages replaces the stage's reward pick with `KEYSTONE_CHOICES` keystones (`rollStageRewards`, a `keystone` reward); the warband holds one at a time (`RunState.keystone`), a new pick replacing it. Each `{ id, name, description, modifiers, curses }` gives every unit its modifiers in `restoreRoster` (Frenzy Pact always doubles, Glass Lens ×5 crits, Avatar of War `encore`, Vampire Court lifesteal, Iron Legion thorns + reflect, Plague Host marks, exploits and spreads debuffs) and pays with curses that strengthen the enemy side (`curses.ts`). The curses are marked `shared`, so `getDeployedCurses` lays them once a battle however many holders deploy. The camp's relic list shows the keystone first (`toRelicViews`). Tested in `src/game/warband/keystones.test.ts`.

The Lone Wolf relic (`relics.ts`) gives a `lone-wolf` modifier: `startBattle` gives a unit deployed alone combat modifiers for that battle (its percent more damage, half that less taken, +20 hit and avoid). Modifiers aren't snapshotted, so nothing outlasts the battle; a one-unit run is a real choice.

### `src/game/warband/trophies.ts`

Run trophies: passives whose gains stay for the whole run. After a won stage, `finishStage` (`run.ts`) runs `applyTrophies(snapshot, kills)` on each unit that fought: Soul Harvest (`soul-harvest`) adds its amount of max HP per foe felled, Trophy Hunter (`trophy-hunter`) adds its amount to the unit's highest stat of STR, INT, DEX, SPD, DEF and RES if it felled any. Both reach rank III and don't scale with rarity. Tested in `src/game/warband/trophies.test.ts`.

### `src/game/warband/evolutions.ts`

Evolutions, Vampire Survivors style (Warband idea 33): `EVOLUTIONS` is a recipe table, each `{ id, name, description, boons, ranks, relics, classes, modifiers }`. A unit that has taken every named boon (and each of `ranks` to that rank), in a warband holding every named relic, and (when classes are named) is one of them (a promoted class counting) has the evolution, and carries its modifiers into battle: a skill only an evolution teaches (Volley, Inferno, Earthshaker) or stronger passives (Vampiric, Juggernaut, Wind Dancer, Executioner, Slayer, Prodigy, Evergreen), and the rank evolutions, a passive at `RANK_EVOLUTION_RANK` (rank III, short of the top rank 5 so a build pays off by mid-run) plus the matching relic: Berserk (Brawler + Duelist's Gauntlet, always doubles), Troll Blood (Regeneration + Mending Charm, 25% max HP each phase), Eagle Eye (Keen Eye + Hawk's Lens, never misses, ×4 crits) and Vampire Lord (Bloodthirst + Bloodpact, heals half the HP it takes). Three build evolutions need boons only, no relic: Reaper (Chain Kill + Bloodlust II, `encore`), Plague (Exploit + Opportunist, `contagion` + `linger-debuffs`) and Iron Maiden (Spite + Thorns III, `taunt-aura`); their passives (Bloodlust, Exploit, Opportunist, Thorns, Spite, Desperation) reuse the gear effects in `modifiers.ts`. Nothing is stored: `getEvolutions(unit, relics)` works them out from a snapshot's class and boons and the run's relics, and `restoreRoster` (`run.ts`) gives each fielded unit their modifiers and ids (`Unit.evolutions`, shown as passives on the unit info screen), so losing a relic loses what it fed. Recipes stay hidden; `completesEvolution(unit, relics, { boon?, classId? })` is what flags a boon card ("evolves!", `toBoonActions`) or a promotion on the promotion screen that would finish one, and `getNewEvolutions(before, after, relics)` lists what a change unlocked. Tested in `src/game/warband/evolutions.test.ts`.

### `src/game/warband/promotion.ts` and `promotionScreen.ts`

The run side of promotion (roadmap W.7). A first promotion (to tier 2, a villager's) is free; a second (to tier 3, an acolyte's Mage or Bishop) spends a seal (`needsSeal(promotion)` in `promotions.ts`). Seals are `MASTER_SEAL` items (`items.ts`, kind `'seal'`), bought from the merchant for 60 gold or won as a `seal` stage reward (offered while the warband holds none and someone is a level short of a second promotion); `countSeals(run)` counts them in the convoy and on units. `getPromotionCandidates(run)` is the roster units that `canPromote`; `canPromoteInRun(run, unitId, promotionId)` also needs one of the unit's own promotions and, when it `needsSeal`, a seal; `canAnyonePromote(run)` says whether anyone can take one now; `promoteInRun` spends a seal when needed (the unit's own, then the convoy's, then another unit's), promotes the snapshot through `restoreUnit` / `promoteUnit` / `snapshotUnit`, and hands over the gift weapon (into the convoy when the unit is full). The camp menu shows Promote once someone could promote (disabled while nobody can take one) and the `promote` run command does the same; the default run policy promotes at once, to one of the class's promotions picked at random (`pickPromotion`, seeded by the run, the unit and its level), and buys a seal for a second promotion when it has gold to spare. `promotionScreen.ts` is the screen as a pure state machine: `openPromotionScreen(run)` lists `getPromotionOptions(run)` (each candidate's two promotions, "Ada: Villager → Archer", a second promotion disabled without a seal), `movePromotionCursor` / `pointPromotionCursor` move the cursor, `confirmPromotion` promotes and relists, and `isPromotionScreenDone` says nobody is left (GridScene then closes it). Tested in `src/game/warband/promotion.test.ts` and `promotionScreen.test.ts`.

### `src/game/warband/chronicle.ts`, `runSummary.ts` and `meta.ts`

A run's story and the renown it earns across runs. `chronicle.ts`: a `RunChronicle` (`{ kills, fallenOn, bossesDefeated, playMs }`: kills by unitId, the stage each fallen unit fell on, boss stages won and the real time played) rides on the run as plain JSON; `recordBattle(chronicle, battle)` adds a battle (only the warband's units' kills count), `addPlayTime` adds time spent at camp, and `parseChronicle` checks a saved one. `runSummary.ts`: `summarizeRun(run, won)` is the recap of a run that ended (stages cleared, bosses, kills, play time, the MVP (most kills, living or fallen, the earliest on the roster on a tie), the survivors, a memorial entry per fallen unit with its stage, the relics held) and `formatPlayTime(ms)` shows a time as "7:05" or "1:02:09". `meta.ts`: `MetaState` (`{ renown, runs, wins, bestStage, heat }`, `NEW_META` to start; `heat` is the highest Heat a new run may pick); `getRunRenown(summary)` pays `RENOWN_PER_STAGE` per stage cleared, `RENOWN_PER_BOSS` per boss and `RENOWN_FOR_VICTORY`, plus `RENOWN_PERCENT_PER_HEAT`% of that per Heat level, line by line; `UNLOCKS` are horizontal (each `UNLOCKABLE_ORIGINS` origin at a renown total: Militia 40, Beast Tamer 80, Peddlers 120, Survivors 200), read with `isUnlocked`, `getUnlockedOrigins` and `getNextUnlock`; Heat opens by winning, not renown (`getHeatAfterRun`: a win at the highest Heat open opens the next); `recordRun(meta, summary)` → `{ meta, earned, unlocked, heatUnlocked }` adds a finished run, saying what it newly opened; a save from before Heat with a win reads as Heat 1 open; `serializeMeta` / `parseMeta` save it (`src/data/metaSave.ts`). GridScene counts the play time with `takePlayTime` (real time since the scene started or last counted, passed with the battle's result and added to the run on Next Stage), and when a run ends it summarizes it, records it into the saved meta state and publishes `toRunSummaryView` (`src/bridge/runSummaryView.ts`: units named by class and sprite, the time as text, relics named by their `relics.ts` name (`humanizeId` for an unknown id), and the renown earned, the new total, what it unlocked and the next unlock) as `runSummary`, which `RunSummary` shows. Tested in `src/game/warband/chronicle.test.ts`, `runSummary.test.ts`, `meta.test.ts`, `src/data/metaSave.test.ts` and `src/bridge/runSummaryView.test.ts`.

### `src/game/warband/recruitment.ts`

Recruitment uses a non-deployable allied guest during selected battles: on the realm, every village battle (`hasGuest`); on a linear run, stage 2 always and a stage in each later three-stage group chosen from the run seed. `rollGuest` fixes the candidate from the run seed before battle, and `createBattleLevel` puts it on the map on the `guest` team, so the AI plays it on the guest phase that opens each turn (see `turns.ts`), outlined green. Being a guest, it does not count as a warband unit for defeat or seize, but it earns XP and takes loot like one. If the guest survives a victory, `finishBattle` saves its battle-end snapshot as `pendingGuest`, and the player may recruit or decline before the ordinary reward pick. The other way to recruit is a **draft**: taking a Recruit reward (`rewards.ts`) sets `pendingDraft` to the stage, and `rollDraft(run, stage)` offers `DRAFT_CHOICES` (3) recruits of different classes, names and quirks, seeded from the run and stage so a reload offers the same ones; `settleDraft(run, index | null)` adds the pick (or nobody) and clears it. Both go through the run's `'recruit'` phase. Warband maps and runs allow five deployed units.

### `src/game/warband/quirks.ts`

Recruit quirks, Darkest Dungeon style: every recruit (`rollRecruit` in `rewards.ts`, so drafted ones and guests alike) gets one random quirk, kept by id on its snapshot and `Unit.quirk`. `QUIRKS` lists them (Brave +2 damage attacking, Lucky +10 avoid, Sturdy +3 max HP, Keen +10 hit, Ruthless +5 crit, Stoic 1 less damage taken defending, Eager +25% XP); a quirk is either modifiers (`modifiers.ts`) that `restoreUnit` hands the unit, or max HP baked into its stats as it joins. `rollQuirk(rng, exclude)` picks one, `findQuirk` and `getQuirkModifiers` look one up. The unit info screen lists it under Quirk. Tested in `src/game/warband/quirks.test.ts`.

### `src/game/warband/rewards.ts`

What a run earns for clearing a stage. `getStageClearGold(stage, losses, { kills, relics })` → `{ gold, flawless }` is the clear's pay: a base, `STAGE_CLEAR_GOLD_PER_STAGE` (10) more per stage, a bonus when nobody died, and the Bounty Ledger's gold per kill. `rollRewards(run, stage, rng, count = 3)` (`rollStageRewards` asks for `getRewardChoices(run)`, four with the Four-Leaf Clover) offers up to `count` rewards of different kinds, shuffled, from the kinds that would do something: **rest** (full HP and mana for everyone, when anyone needs it, never after stage 1, whose quick fight leaves the warband near full), **supplies** (a Health Potion for every unit with room), a **relic** the run can take (`getOfferableRelics` in `relics.ts`: unheld, or a second copy of a stacking one; relics replaced the old Training and Field Drill cards), an **arms cache** (one fresh weapon that someone in the roster can wield, delivered to the convoy), a **veteran's lesson** (every unit gains exactly the XP to its next level), and a gold purse, plus a **Recruit** draft (`{ kind: 'draft', stage }`, see `recruitment.ts`) while the roster has room, always among the offers while it's below `getRecruitTarget(stage)` (2 after stage 1, then one more every other stage, so 4 by stage 4 and 6 by stage 8). A lesson reward carries a `seed` for its level ups' stat rolls; `applyLessonReward` returns each `{ name, levelUp }`, which GridScene shows on the level-up panel before moving on. `getRewardSeed(runSeed, stage)` seeds the roll, so a stage always offers the same picks. Instead of taking a reward the player can skip (`skipRewards`, paying `getSkipGold(stage)`) or reroll (`rerollRewards(run, stage, rerolls)`, spending `getRerollCost(rerolls)`, which rises with each reroll, or null when the run can't afford it); `rollStageRewards(run, stage, rerolls)` is the offers for a stage and reroll count; a big clear (`isBigClear`: an elite lair, `isEliteClear`, or a fort, `isFortClear`) offers `BIG_CLEAR_EXTRA_CHOICES` more, an elite lair's all relics and a fort's always with one. `applyReward(run, reward)` applies one, `addGold` adds gold, `markRewardPending(run, pending)` marks the pick as owed when the stage is won and saved, and taking or skipping clears it (`clearPendingReward`); `getPendingRewardOffer(run)` rolls the owed pick's offers again for a loaded run, so reloading on the reward screen reopens it with the same offers (GridScene's `resumeRewardPick`, over the next stage's map), and `describeReward(reward, classes?, run?)` gives the screen's label and line (a relic's number at the run's stage, "×2" when it'd be a second copy), and `previewRewardHealth(run, reward)` gives each unit's HP after a Rest (null for other rewards, the lesson included so its level ups stay a surprise). A `Reward` carries everything it needs; recruit data is also used for the guest's and the draft's recruit picks, and `rollRecruit` gives each recruit a quirk (`quirks.ts`). Tested in `src/game/warband/rewards.test.ts`.

An elite lair's offers are signature gear instead of relics: `gear` rewards (`rollOfferableGear`, from `getOfferableGear`: kit gear the convoy and roster hold none of, so one copy a run) that send the piece to the convoy and describe it from `GEAR_DESCRIPTIONS`.

### `src/game/warband/rewardFacts.ts`

What a reward does, in numbers, for its card on the reward screen. `getRewardFacts(reward, run?)` → a frozen list of `{ label, value, after?, gold?, wide? }`: an Arms, gear or Supplies reward's item stats (`getItemFacts`: a weapon's Pow, Hit, Wt and Rng, armor's Def and Wt (plus Avo or Res), a staff's Pow and Rng, what a potion restores) and, for Supplies, how many units have room (`canTakeItem` in `rewards.ts`); the purse before and after a Gold reward; the warband's size before and after a draft (capped at `MAX_ROSTER_SIZE`); the HP a Rest heals and on how many units (or that everyone is at full HP); a lesson's level ups. Empty for a recruit (its card shows its stat line) and for a relic, keystone, seal or scroll, whose description says it all. `toRewardAction` carries it as `facts`.

### `src/game/warband/enemyCurve.ts`

How strong and how many a stage's enemies are, the surge curve. `levelRegionForStage(region, stage, offset)` tops the region up to `getStageEnemyCount(stage)` enemies (1 + one per `ENEMIES_PER_STAGE`, 4, stages, up to `MAX_STAGE_ENEMIES`, 8; the extras go to groups without a boss, the biggest first) and puts each enemy group at the stage's level plus how far it was authored above the region's weakest group (`getRegionBaseLevel`; so a boss group 2 up stays 2 up) plus the site's offset (a fort's `FORT_LEVELS`); `battleSetup.ts` and the overworld's site card use it, through `getSiteRegion` on the realm. From past `SURGE_FROM_STAGE` (4) every enemy stat but MOV is multiplied by `getSurgePercent(stage, rate)` (compounding `rate`% a stage, `BASE_SURGE_RATE` 4.5 at Heat 0, `HeatRules.surgeRate` above it), applied by `applySurge` to each enemy after `createStageLevel`, before elite affixes; about ×3.1 at stage 30. The rate was tuned so the default policy wins about a third of 30-stage runs at Heat 0. Tested in `src/game/warband/enemyCurve.test.ts`.

### `src/game/battle/reinforcements.ts`

Enemies that join a battle after it starts. A level may carry `ReinforcementRules` (`{ level, surgePercent, waves? }`, `Level.reinforcements`), which `createBattleState` turns into `BattleState.reinforcements` (`{ rules, arrived }`, null without). Every arrival comes at least at the rules' level and with their surge (`createArrival`, using `applySurge` from `warband/enemyCurve.ts`): a boss's horn call (`runBossHorn` in `commands.ts`) and the waves. With `waves` (`{ every, classes, limit }`), on every `every`th enemy phase (`isWaveTurn`) one enemy of the next class in turn (`createWaveArrival`, id `getWaveUnitId(n)`, `wave-n`) arrives on the free walkable tile farthest from the deployment zone but within `WAVE_REACH` (10) straight steps of it, so on a big map it joins the fight instead of marching in (`pickWaveTile`), done for that phase, as a `reinforced` event the scene already plays. `getStageReinforcements(stage, region, surgePercent)` in `battleSetup.ts` sets a Warband stage's: the level of its weakest group, its surge, and from `WAVES_FROM_STAGE` (10) waves of its region's non-boss classes every `WAVE_EVERY` (2) phases, up to `WAVE_LIMIT` (6). Tested in `src/game/battle/reinforcements.test.ts`.

### `src/game/warband/stageClearExperience.ts`

The XP a won stage pays. No level is guaranteed: `getStageClearExperience(stage, level)` is `CLEAR_EXPERIENCE` (20) plus `CLEAR_EXPERIENCE_PER_STAGE` (2) a stage, `CATCH_UP_PERCENT` (15%) more for each level the unit is below the stage and as much less for each level above, never under `MIN_CLEAR_PERCENT` (20%), so units that miss kills keep up while a unit fed every kill still pulls ahead. `applyStageClearExperience(run, stage, fought)` → `{ run, levelUps }` gives it to every roster unit in `fought` (those that deployed and survived; benched units earn nothing), scaled by its XP rate and on top of what its kills earned, its stat gains rolled from `getRewardSeed` salted, so a stage always gives the same ones. `finishBattleWithEvents` (`runCommands.ts`) applies it to a won stage before paying the clear and rolling the reward offers. Tested in `src/game/warband/stageClearExperience.test.ts`.

### `src/game/warband/convoy.ts`

The run's `convoy` (items held for the whole warband, no slot limit) is the warband's armory, and this moves items between it and the units between stages. `giveFromConvoy(run, unitId, convoyIndex)` hands a unit one of a consumable (into its bag, stacking onto the one it carries) or wears a piece of gear in its slot (`equipGear` in `equipment.ts`), whatever that displaces (the slot's old gear, and a shield when a two-handed weapon or a staff goes in) going back to the convoy; `canGiveFromConvoy` / `canCarry` say whether it can (bag room, `MAX_INVENTORY_SLOTS`, for a consumable; `canEquip` for gear; seals stay in the convoy). `unequipToConvoy(run, unitId, slot)` takes a slot's gear off into the convoy (`canUnequip`), and `storeInConvoy(run, unitId, itemIndex)` stores one of a bag consumable (`canStoreInConvoy`). `getUnitEquipment(snapshot)` reads a snapshot's worn gear, and `isSuitedTo(run, unitId, itemId)` says whether gear is a natural pick for a unit (a weapon it's trained in at its main weapon's range, a staff for a healer, armor for an empty slot), for the merchant's default recipient. `lookUpItem(itemId)` finds an item in `RUN_ITEMS`. Natural weapons (`NATURAL_WEAPON_IDS`) never move. Each returns a new frozen run. Tested in `src/game/warband/convoy.test.ts`.

Cursed gear (`isCursed` in `gearKits.ts`) sticks to its wearer: `canCarry` refuses anything that would displace it, and taking it off costs `CLEANSE_COST` gold (`getUnequipCost`; `canUnequip` checks the run can pay and `unequipToConvoy` charges it). The Equipment screen shows its Remove choice as "Cleanse (40 gold)".

### `src/game/warband/rosterScreen.ts`

The roster screen between stages, as a pure state machine over `convoy.ts`. `RosterScreenState` is `{ run, tab, column, unitIndex, itemIndex, convoyIndex, actions }`: `tab` is the panel beside the units (`ROSTER_TABS`: `'stats'`, `'skills'` or `'items'`), and the cursor sits in the `'units'` column or, on the Items tab, the `'items'` (the picked unit's bag) or `'convoy'` column. `openRosterScreen(run)` starts on the first unit's Stats; `moveRosterCursor(state, dx, dy)` walks one strip sideways (Stats, Skills, Items on the units, then the bag and the convoy, stopping at the ends) and a column up and down (wrapping); `pointRosterCursor(state, target, index)` is the mouse's version, `'tabs'` opening a tab (leaving Items puts the cursor back on the units); `confirmsOnClick(target)` says whether a click also confirms (not on a unit or a tab, so clicking through the units keeps the open tab); `confirmRoster` moves from a unit into its bag on the Items tab, opens a bag item's actions (`getItemActions`: Store), takes the picked action, or gives the highlighted convoy item to the picked unit (gear is worn, see `giveFromConvoy`); `cancelRoster` closes the actions, steps back to the units, or returns null to close the screen. Indices are pulled back into range whenever the lists change. Worn gear is managed on the equipment screen. Tested in `src/game/warband/rosterScreen.test.ts`.

### `src/game/warband/equipmentScreen.ts`

The equipment screen between stages, Tactics Ogre style, as a pure state machine over `convoy.ts` and `equipment.ts`. `EquipmentScreenState` is `{ run, column, unitIndex, slotIndex, gearIndex }`, the cursor in the `'slots'` (the picked unit's paper doll, `getUnitSlots`: five slots for a humanoid, special and accessory for a monster) or `'gear'` column. The unit is picked only through its tabs, `stepEquipmentUnit(state, delta)` (Q / E, wrapping) and `pickEquipmentUnit(state, index)` (a click), never by moving or pointing the cursor, so the mouse can't switch units by passing over them; the column and slot are kept where the new unit has them. `getGearChoices(state)` is what the gear column offers for the picked slot: Remove while it holds something, then each convoy item for that slot (special gear only when made for the unit's class), then what each teammate wears there (`kind: 'worn'`), disabled when the unit can't wear it (a shield beside a two-handed weapon, `isOffHandLocked`) or a teammate's gear is cursed. `openEquipmentScreen(run)` starts on the first unit's slots; `moveEquipmentCursor(state, dx, dy)` steps between the two columns and within one (wrapping); `pointEquipmentCursor(state, column, index)` is the mouse's version (a click also confirms); `confirmEquipment` opens the gear, or in the gear column wears the choice with `giveFromConvoy` (a teammate's goes through the convoy with `unequipToConvoy` first, leaving them without it; Remove takes the slot's gear off) and returns to the slots; `cancelEquipment` goes back to the slots, or returns null to close. `previewGearChoice(state)` is the run as it would be with the highlighted choice, for the before/after numbers. Tested in `src/game/warband/equipmentScreen.test.ts`.

### `src/game/warband/camp.ts`

The camp between stages, once a won stage's reward is taken. `getCampActions(run)` is its menu: Manage Roster, Equipment (the equipment screen, `equipmentScreen.ts`), Merchant (on the realm only in a town, `hasMerchant`), Promote (once someone could promote, disabled without a Master Seal, see `promotion.ts`), Rest (labelled with `getRestCost(run)`, `REST_COST` or free in a town or with the Field Kitchen, disabled when the run can't afford it or nobody `needsRest`), Mentors (the mentor screen, disabled while nobody `canTakeLesson`; left out while `MENTORS_ENABLED` in `mentors.ts` is off, as it is for now) and Next Stage (Travel on the realm). The camp menu opens on Next Stage, with the run's relics listed beside it. `restAtCamp(run)` spends that cost and restores every unit to full HP and mana (`canRest` says whether it can). Tested in `src/game/warband/camp.test.ts`.

### `src/game/warband/mentors.ts` and `mentorScreen.ts`

Secondary skill sets, Final Fantasy Tactics style scaled down to one slot. A roster unit can learn one other class's skill set (`UnitSnapshot.secondaryClass`, carried to `Unit.secondaryClass` by `restoreUnit`) and then knows that class's skills as it reaches their levels (`getSecondarySkills` in `skills.ts`). `getSecondaryClassIds(unit)` is every playable class with a skill tree but its own; `findMentor(run, unitId, classId)` is a roster unit of that class that knows one of its skills; `getLessons(run, unitId)` lists a `Lesson` per class (`{ classId, mentorId, source, known }`, `source` `'mentor'` while the warband can pay `MENTOR_FEE`, else `'scroll'` while it holds a Mentor's Scroll, else null); `learnSecondary(run, unitId, classId)` spends the fee or the scroll and replaces the unit's set (`canLearnSecondary` guards it). Scrolls are `RunState.scrolls` (`getScrolls`, `addScrolls`), won as a `scroll` reward (`rewards.ts`, from stage 2, only while `MENTORS_ENABLED` is on) and meant to come from events too. `mentorScreen.ts` is the camp screen as a pure state machine (`{ run, column, unitIndex, lessonIndex }`, units and lessons columns), the same shape as the merchant's, and `bridge/mentorView.ts` (`toMentorScreenView`) is what React draws. Tested in `src/game/warband/mentors.test.ts`, `mentorScreen.test.ts` and `src/bridge/mentorView.test.ts`.

### `src/game/warband/merchant.ts`

The camp's merchant, buying into and selling from the run's convoy. `getMerchantStock(stage)` is what it sells on a stage, by item id: every piece of the two newest gear ladder tiers it has unlocked (`TIER_STAGES`: wooden from stage 1, iron from 4, steel from 11, silver from 20; `STOCKED_TIERS`), the newest first, then the Heal staff and the Master Seal; the functions that take a `stock` default to the run's stage's. `getItemPrice(item)` is a fresh item's price from `ITEM_PRICES` (a ladder piece it doesn't name costs its tier's `WEAPON_TIER_PRICES`, or `HEAD_TIER_PRICES` for shields and head pieces), falling back to the kind's `DEFAULT_PRICES` for an unlisted item (natural weapons have none). `buyItem(run, itemId)` spends the price and adds one to the convoy (`getPurchaseQuantity`: one; a consumable stacking), `canBuy` refusing what isn't stocked or can't be afforded. `buyItemFor(run, itemId, unitId)` buys straight onto a unit (a consumable into its bag, gear worn with what it displaces sent to the convoy; `canBuyFor` also needs `canCarry` in `convoy.ts`), or into the convoy for a null `unitId`. `sellItem(run, convoyIndex)` sells one of a consumable or the whole entry of anything else for `getSellPrice` (half the price, rounded down), `canSell` refusing natural weapons. A unit's gear is sold by taking it off into the convoy first. Tested in `src/game/warband/merchant.test.ts`.

### `src/game/warband/runCommands.ts`

A run between battles as JSON commands, the way `src/game/battle/` does a battle. A `RunSession` is `{ run, phase }`, the phase `'relic'`, `'battle'`, `'boon'`, `'recruit'`, `'reward'`, `'camp'`, `'travel'` (on the realm, choosing where to go next), `'event'` (at a wayside, `pick-event`, which reports an `event-outcome`), `'over'` (fallen) or `'won'`. `startRunSession(run)` opens a new run on its starting relic pick (`getRelicOffers`, `pick-relic`, after which a realm run goes to `'travel'`); `resumeRunSession(run)` opens a saved run on its owed boon, recruit or reward pick, in that order, or else its battle, its town's camp or the overworld; `finishBattle(session, result, outcome, finalStage?)` writes a battle back (`finishStage`) and, on a win, levels up the units below the stage's guaranteed level (`applyStageClearExperience`), owes a boon pick for every level the stage gained bar those taken in battle (`queueLevelUpBoons` with `result.boonsTaken`, phase `'boon'`, taken one `pick-boon` at a time before the recruit and reward picks), pays the clear's gold (with `result.kills` for the Bounty Ledger) and marks the reward pick owed (`'reward'`), wins the run on the final stage (`'won'`), or ends the run (`'over'`). `applyRunCommand(session, command)` is the one dispatcher for the rest: `pick-relic` and `pick-boon` on those picks; `pick-reward`, `skip-reward` and `reroll-rewards` on the reward pick (a lesson's level ups owe boons before camp); `rest`, `buy`, `sell`, `give`, `store`, `equip`, `promote`, `learn-secondary` and `march` at camp. Each case wraps the module that owns the rule (`rewards.ts`, `camp.ts`, `merchant.ts`, `convoy.ts`), and anything not allowed where the run stands throws a `RunCommandError`. A lesson reward reports its level ups as a `level-ups` event, and so does `finishBattleWithEvents` (what `finishBattle` wraps) for a stage clear's level ups, which GridScene shows before the stage's result. `getRewardOffers(session)` is the pick's offers, and `getLegalRunCommands(session)` every command the session accepts, for an AI to choose from. Tested in `src/game/warband/runCommands.test.ts`.

### `src/game/warband/autoRun.ts`, `runPolicy.ts` and `simulate.ts`

A whole Warband run played without the game running. `autoRun.ts`: a `RunPolicy` is `{ battle, relic?, boon?, reward, camp, travel }` (`travel` picking the next site on the run's realm, `getRealm`) (a `BattlePlanner` for the player, and a function from a `RunSession` to the next `RunCommand` for the reward pick and for camp); `playRun(start, policy, { maxStages, maxCampCommands })` starts the run (`startRun`: the seed and the first unit's class and name), plays each stage's battle with `runBattle` on the stage's map and run-seeded dice, writes it back with `finishBattle` (a battle that runs out of turns is lost by the objective's `TURN_LIMIT`, and its `StageRecord` is marked `stalled`), and asks the policy for every reward and camp command until the warband falls, wins the run (the content's `finalStage`, `RunEnd` `'won'`) or `maxStages` stages have been fought. It returns a `StageRecord` per stage and a `RunScript` (`{ start, steps }`, each step a battle's commands or a run command, plain JSON) that `replayRun` plays back into the same run. `BASELINE_POLICY` plays like the enemy (the rush AI, the first offered recruit at a recruitment visit, then rest when possible). `runPolicy.ts` is the default policy, `DEFAULT_POLICY`: `planPlayerTurn` in battle, `pickStartingRelic` (by `RELIC_PREFERENCE`), `pickBoonOffer` (by `BOON_SCORES` times the offer's `RARITY_PERCENT`), `pickReward` (the offer `scoreReward` rates highest, from `REWARD_SCORES`), `pickRecruit` (a guest, or the draft's first recruit of a class the roster lacks) and `planCamp` (rest when someone deploying is badly hurt; arm each deploying unit, `getDeployingUnits`, by equipping a better carried weapon or staff (a one-handed one first when it carries a shield), taking one from the convoy or buying one, preferring what its class starts with; rest when the group is hurt enough; put on better gear, a higher gear ladder tier of its main weapon's family or of its class's armor weight that costs no movement, from the convoy or bought with gold beyond `UPGRADE_RESERVE`; march) and `planTravel` (the next site `scoreSite` rates highest: villages for recruits while the roster is small, towns when hurt or rich, forts once the warband is big enough, shrines; battles otherwise). `simulate.ts` plays many starts (`getSimStarts`) with a policy and sums them per starting class (`SimSummary`: stages won, runs that lasted, where runs fell, stalls, losses); `formatSummary` prints it. `npm run sim` (`scripts/sim.ts`, which loads the modules through Vite's `runnerImport`) runs it from the command line and can write the worst run's script out. Tested in `src/game/warband/autoRun.test.ts`, `runPolicy.test.ts` and `simulate.test.ts`.

### `src/game/warband/merchantScreen.ts`

The merchant screen as a pure state machine over `merchant.ts`. `MerchantScreenState` is `{ run, stock, column, stockIndex, convoyIndex, recipients }`, the cursor in the `'stock'` or `'convoy'` column. `openMerchantScreen(run)` starts on the first stock item; `moveMerchantCursor(state, dx, dy)` steps between the columns (stopping at the ends) and within one (wrapping); `pointMerchantCursor(state, column, index)` is the mouse's version; `confirmMerchant` on a stock item opens `recipients` (`getRecipients`: each unit, disabled when it can't take the item, then the convoy, highlighting the first unit the item `isSuitedTo` that can take it, else the convoy), confirm there buys it with `buyItemFor`, and on a convoy item sells it, keeping the convoy index in range; `cancelMerchant` backs out of the recipients, else closes the screen. ### `src/game/warband/origins.ts` and `heat.ts`

What a new run starts as, and how hard it is. `origins.ts`: an `Origin` (`{ id, label, description, units, gold, relicPicks, convoy }`): `BASE_ORIGINS` is one lone-unit origin per `STARTING_CLASSES` class, by the class's id, and `UNLOCKABLE_ORIGINS` the ones renown opens, none stronger at the start than a villager or two (`MILITIA` (two villagers, 20 gold), `BEAST_TAMER` (a villager and a whelp, `src/game/Whelp.ts`, a villager-strength young beast that `warband/whelp.ts`'s `growUpWhelp` turns into a Beast at level 5 whenever `snapshotUnit` saves it), `PEDDLERS` (a villager, 60 gold and potions in the convoy) and `SURVIVORS` (three villagers, no gold, no starting relic)); the Sellswords, Pilgrims and Lone Wolf were retired, and a saved run naming one still loads (one relic pick, its id humanized as its label); `createOriginWarband(origin, name, seed)` builds the units (`<classId>-<n>`, the leader named, the rest given seeded names), `createOriginRun(seed, originId, name, heat)` the run (its gold and convoy, and `origin` / `heat` kept on `RunState`), and `getRelicPicks(run)` how many starting relics it picks (`runCommands.ts`'s `startRunSession` keeps the session on `'relic'` until they're taken, each later pick three relics it doesn't hold, and skips the pick for an origin with none). `heat.ts`: `HEAT_LEVELS` 1–5 (Hardened Foes: the enemy surge 5.5% a stage instead of 4.5%; Lean Purses: clears pay 75%; Costly Rest: rest costs double; Closed Ranks: no guests; Warlord's Wrath: the surge 6.5%), each a function on `HeatRules`; `getHeatRules(heat)` stacks every level up to it, `getRunHeatRules(run)` reads the run's. The title screen asks for the Heat after the origin once one is open, and `npm run sim -- --heat N --class <origin>` plays runs at a Heat. Tested in `origins.test.ts` and `heat.test.ts`.

### `src/game/warband/stageLevel.ts`

A Warband Mode stage's battle. `createStageLevel(seed, region, roster?, maxDeployed?, lootCount?)` returns the same shape as `createDemoLevel`, built from the seed and a `RegionConfig`. First `sizeStageRegion(seed, region, maxDeployed)` sizes the map for the fight (`mapSize.ts`: room for `maxDeployed` warband units and every enemy of the region's groups, shaped by its archetype, never smaller than the region's own `width` and `height`, which act as a minimum, with its patch and building counts scaled to the area), from a salted copy of the seed. The seed then lays out `MAP_CANDIDATES` (30) candidate maps, from the seeds `getCandidateSeeds(seed)` gives (the seed itself first), and `pickStageLayout` keeps the one `scoreMap` grades best among those that pass `checkMap` (the best-scoring of all of them if none does), the earliest on a tie, stopping early at a perfect 0; each candidate (`layOutStage`) is the terrain and buildings from `generateMap` with `region.terrain` and `region.terrain.setPieces` (one per 45 tiles when unset) set pieces of the region's season drawn from a salted copy of the candidate's seed (`drawSetPieces` over `SET_PIECES`), the deployment zone (the map type's when it has one), and the tiles `pickZonedEnemyTiles` finds for `region.enemies` in the map type's enemy zones, with a second way opened past a lone chokepoint (`openLoops`, `mapLoops.ts`), graded against the cave targets on a cave region, and the rest of the level is built on with the winning candidate's own `Rng`, so a seed still always rebuilds the same battle. The level's `palette` is `region.palette`. The deployment zone is the path's south end and the tile on each side of it. An enemy of its group's `unitClass` (`DEFAULT_ENEMY_CLASS`, a soldier, when unset; named e.g. "Enemy Soldier"; of the region's `faction` when it sets one, else the enemy team's default) stands on each tile `pickEnemyTiles` finds for `region.enemies` (numbered `enemy-1`, `enemy-2`, … in group order), grown to its group's `level` on its class's growths (`growToLevel`, with `getLevelUpGains` from `experience.ts`, so the same class and level always has the same stats) and outfitted for it (`outfitEnemy` in `enemyGear.ts`), starting on its group's `health` (capped at its max) when the group sets one and with `levelUpOnKill` set from its group; the first enemy of the first group that sets `boss` takes that name, holds its ground and is the level's `bossUnitId`, which a boss objective (`placeObjective`) targets as it is instead of promoting a "Chief", and green ginkgos are scattered on grass that no building, overhang or mountain peak is drawn on (`region.treeChance`). On `SPIKE_TRAP_CHANCE` (half) of seeds the map then gets `SPIKE_TRAP_COUNT` (2 or 3) spike traps from `pickSpikeTiles`, within `SPIKE_TRAP_REACH` (3) of an enemy's start and clear of the deployment zone, trees, buildings and the seize tile, drawn from a salted copy of the seed so the rest of the stage is the same with or without them. Last of all, `lootCount` of the enemies (0 by default) each get a `loot` item from `assignLoot` (`loot.ts`), drawn from the same seed after everything else so the map doesn't change with the count; `createBattleLevel` passes `getStageLootCount(stage)`. The roster is `roster`'s units (a run's warband) deploying up to `maxDeployed`, else `createStartingWarband()` deploying up to `WARBAND_MAX_DEPLOYED`. `createStartingWarband(classId = 'villager', name = WARBAND_LEADER_NAME)` is what a new run starts with and a region preview fields: a single level-1 unit of the chosen class named `name` (the New Run menu passes the name the player settled on; the default is the first `PLAYER_ROSTER` name, Alden), by unitId `<classId>-1`. Every built-in region uses the planned generator (`mapPlan.ts`). `pickStageArchetype(stage, region, seed, objective)` picks a stage's map type: the region's own `terrain.archetype` if it sets one, `advance` on stage 1, else a seeded pick from `OBJECTIVE_ARCHETYPES` for the stage's objective (rout, seize, boss and survive each have the types that suit them); `withArchetype` sets it on the region and the level carries the plan's `seizeTile`. Stage 1's region (Meadowlands) is built around that lone unit: one slime (6 HP, 0 DEF, dealing 1 damage a hit, worth the usual XP; clearing the stage is what reliably brings the first level, see `stageClearExperience.ts`) exactly three steps from the deployment zone, so whichever class the run starts as can reach and strike it on turn 1 from any deployment tile, and the first battle is a quick, likely win. The built-in regions are a ten-stage run (`finalStage` 10) that ramps up in kind and level: two goblins (one starts at 5 HP), two slimes and a beast in the Deep Woods, two level-2 goblins and a skeleton, skeletons and bats in the Barrow Hills, beasts and bats in the Fens, a level-3 skeleton and goblin garrison in the Fortress, level-4 brigands (soldier, archer, vanguard) with goblins, then orcs, beasts and goblins on the Orc Marches, and on stage 10 the Warlord's Hold, a boss stage on a fortress map where the level-7 Orc Warlord holds the keep with a level-5 orc, archer and two beasts. Beating it wins the run. There are no dialogs or structures. The title screen's Warband Mode starts a run with `runStage`, and `createBattleLevel` builds each stage with `getStageRegion(stage, content.regions)`. Tested in `src/game/warband/stageLevel.test.ts`.

### `src/game/warband/stageObjective.ts`

### `src/game/camera.ts`

### `src/game/movement.ts`

Pure movement rules. `TERRAIN_MOVE_COSTS` maps terrain to the movement points spent entering it (grass, dirt and meadow 1, forest 2; water, walls and mountains `Infinity` = impassable; unlisted terrain costs 1). `getMovementRange(grid, origin, movement, { terrainCosts, canPassThrough })` runs Dijkstra over orthogonal neighbors and returns every reachable destination as `[{ x, y, cost }]`, including the origin at cost 0. Other units block unless `canPassThrough(unitId)` allows them, occupied tiles are never destinations, and `canStopOn(terrain)` (when set) rules out more. `BLINK_MOVEMENT` is the Blink evolution's options: every terrain at 1 MOV (`BLINK_TERRAIN_COSTS`), through any unit, ending only on terrain a walker could stand on. `getMovePath(grid, origin, destination, movement, options)` uses the same search to return the cheapest route as a list of orthogonally adjacent tiles from origin to destination (one entry per step), or `null` if the destination isn't in range — so the range and the path can never disagree. `extendMovePath(grid, path, target, movement, options)` updates a planned route as the cursor moves: it cuts back to a tile already on the path, appends an adjacent step while the traced route stays within movement, and otherwise falls back to `getMovePath` (leaving the path unchanged if the target is unreachable), so the route follows the way the player traced it. `getPathCost` sums the cost of the tiles a path enters. `canMoveAlongPath(range, path, to)` is whether a move can be confirmed: `to` must be in the movement range (not a tile the mover can only pass through) and where the planned route ends. Tested in `src/game/movement.test.ts`.

### `src/game/attackMove.ts`

Pure rule for attacking straight from the move range. `pickAttackPlan(range, path, target, weapons)` returns `{ tile, weaponIndex }`, a tile of the mover's movement range that one of `weapons` (each a `{ minRange, maxRange }`) strikes `target` from, or `null` if none does. Tiles are tried in order: where the planned route ends, then the mover's own tile, then the rest from cheapest to reach; from that tile the first weapon in reach wins, so callers pass the equipped weapon first. Tested in `src/game/attackMove.test.ts`.

### `src/game/dangerZone.ts`

Pure rule for the enemy danger zone (ROADMAP 3.1). `getDangerZone(grid, sources)` takes each enemy as a `DangerSource` (`origin`, `movement`, the `ranges` of the weapons it can wield, and its `MovementOptions`) and returns every tile any of them could strike next phase, without duplicates: `getAttackRange` from every tile of its `getMovementRange`, per weapon range, so min ranges and gaps between weapons hold. `GridScene` builds the sources from the enemies on the map, shades the result under every other highlight while the zone is toggled on (the D key, or `DangerZoneButton` in the header via the `toggle-danger-zone` command; `gameStore.dangerZoneVisible` mirrors it), and redraws it whenever a unit finishes acting, falls, or is placed. Alongside it (`refreshThreats`), every player phase `GridScene.refreshIntents` draws each enemy's intent (`battle/intents.ts`) in world space, a faint line along its route and an arrow onto the unit it'll strike, and publishes `intentTags` (`toIntentTagView`) for React's `MapTags` to label the HP at risk; they're redrawn after every action, move and undo, and cleared in any other phase. While aiming a Shove, `updatePushPreview` shades the tile it would leave its target on and publishes `pushTag`; a `pushed` event plays as a slide (or a lurch and back when blocked), then the damage, a "Drowned!" sink or "Steadfast". Confirming on an enemy on the bare map shows just that enemy's move and attack reach. Tested in `src/game/dangerZone.test.ts`.

**Auto play.** The A key or `AutoPlayButton` in the header (the `toggle-auto-play` command) flips `gameStore.autoPlay`, which outlives each battle. While it's on, `GridScene.updateAutoPlay` takes a step every `AUTO_STEP_MS` whenever input is free: it skips dialog, closes the objective screen and the camp's sub-screens, moves on from the result, deploys with `planPlayerDeployment`, plays each player unit's action with `planPlayerTurn` through the same `takeEnemyAction` the enemy phase uses, picks the reward with `pickReward` (selecting the card, then confirming it like the player would) and runs camp with `planCamp` through the run commands. It leaves input alone while the pause menu or unit info is open or the player is midway through a unit's action, and turning it off hands control back before the next step.

### `src/game/push.ts` and `hazards.ts`

Pure push and hazard rules (Warband idea 35, Into the Breach's shoves and Vandal Hearts' traps). `hazards.ts`: `HAZARDS` maps a terrain to what being shoved onto it does (`{ damage, drowns }`): a `spikes` trap deals 5, deep `water` drowns (a ford doesn't); walking onto either is never harmful (spikes cost 1 to cross, water stays impassable), so only a shove makes them matter (a push skill, or an attack by a unit with the `shove-on-attack` modifier, the slime's Bounce). `getHazard(terrain)` looks one up. `pickSpikeTiles(grid, { count, enemyTiles, reach, avoid }, rng)` picks the tiles for a stage's traps: open ground (grass, dirt, meadow) with no unit, within `reach` of an enemy's start, not on or next to an avoided tile, never two side by side. `push.ts`: `getPushDirection(from, to)` is the one-step direction a shover at `from` pushes the unit at `to`; `getPushResult(grid, units, from, direction)` says what shoving the unit on `from` would do, as a `PushResult`: it slides onto the next tile (taking the hazard there, or `drowned` in deep water), or is `blocked` by the map's edge, impassable terrain or another unit and takes `BUMP_DAMAGE` (2) where it stands, as does the unit it slams into (`collidedId`); a unit that `holdsPosition` (a boss) is `steadfast` and doesn't move. Tested in `src/game/push.test.ts` and `src/game/hazards.test.ts`.

### `src/game/teams.ts`

Pure team relations over the `unitId -> unit` registry (anything with a `team`). `getTeamUnitIds(units, team)` lists a team's unit ids in registry order (the enemy phase's queue), `areAllied(a, b)` says two teams fight on one side (a team with itself, and the player with the guests), `isAllyOf(units, team, unitId)` says a unit on `team` may walk through that unit (an allied one; GridScene's `canPassThrough` for movement), and `isHostileTo(units, team, unitId)` says it may attack it (any team not allied with it), so the enemy fights the player and the guests both. Ids missing from the registry are neither. Tested in `src/game/teams.test.ts`.

### `src/game/turns.ts`

Pure turn rules. A battle cycles through phases in `PHASE_ORDER` (guest, player, then enemy); the cycle makes one turn. `Team` is `'player' | 'enemy' | 'guest'`: guests are allies nobody controls, the AI playing them on their own phase, first in each turn (Fire Emblem's "other" phase, moved to the front). Turn state is a frozen `{ turn, team, moved, done }` from `createTurnState(turn, team)`: `moved` / `done` list the unitIds that have moved or finished this phase. `markMoved` and `markDone` (which also counts as moved, and ends the unit's canto) return new states; `hasMoved` / `isDone` read them; a state's optional `canto` (`startCanto(state, unitId, movement)`, read with `getCanto`) is a unit that has acted but may still move `movement` tiles before it's done (a Momentum kill); `isPhaseOver(state, unitIds)` is true once every one of the phase team's units in play is done (trivially true for none); `getFirstPhase(turn, hasGuests)` is the phase a turn opens with: the guests' while a guest is in play, else the player's (the battle passes whether one is, including for turn 1 at `start-battle`); `nextPhase(state, hasGuests)` advances guest → player → enemy (same turn) → the next turn's first phase with a clean slate. `getBattleOutcome(units)` returns `'victory'` when no enemy is alive, `'defeat'` when no player unit is (defeat wins a tie; guests count for neither), else `null`. Tested in `src/game/turns.test.ts`.

### `src/game/enemyAI.ts`

Pure enemy decision-making. `getPhaseMovement(unit)` is how far a unit moves on its phase: its movement less what its load costs (`getLoadMovementPenalty`, never below 0), or 0 for one that `holdsPosition` (a boss), which the scene uses for the enemy's plan, the danger zone and an inspected enemy's reach. `planRushAction(grid, origin, unit, isHostile, movementOptions, scoreTarget)` returns `{ path, target }` for one enemy, striking with its equipped weapon's range (min and max; an enemy without a weapon never finds a target and stays put): if any tile in its movement range lets it attack a hostile unit, it scores every (tile, target) pair with `scoreTarget(from, target)` and takes the highest, breaking ties by the cheapest tile (so an enemy already adjacent stays put; without a scorer every attack ties); otherwise it finds the nearest tile it could attack from by walking distance (ignoring its movement limit, respecting terrain and blockers), follows the route there, and stops at the furthest tile it can reach and stand on this phase (allies can be walked through, not stopped on). With no reachable hostile it stays put (`path: [origin]`, `target: null`). Built on `movement.ts` and `combat.ts`. Tested in `src/game/enemyAI.test.ts`.

### `src/game/aiScoring.ts`

Pure scoring of enemy attacks. `scoreAttack(forecast, { soft })` rates one attack from `getCombatForecast`'s output: expected damage dealt (hit and crit chances folded in, capped at the defender's health), minus half the expected counter damage, plus `KILL_BONUS` × hit chance when every strike landing would kill, plus `SOFT_TARGET_BONUS` for a soft target, minus `SUICIDE_PENALTY` when the counter could kill the attacker and the attack couldn't kill first. `isSoftTarget(unit)` is true for mages (a magical weapon) and healers (a staff in the pack). `createAttackScorer(attacker, getFoe)` wraps both into the `scoreTarget` that `GridScene.takeEnemyAction` passes to `planRushAction`, forecasting at the distance from each candidate tile so ranged enemies prefer spots the target can't counter from. Tested in `src/game/aiScoring.test.ts`.

### `src/game/moveArrow.ts`

Pure logic for the movement arrow. `getArrowPieces(path)` returns `[{ x, y, piece }]` for every tile of a route after the origin: an arrowhead (`head-up`/`down`/`left`/`right`) on the last tile pointing the way it last stepped, and on the tiles before it a straight segment or corner named for the two tile edges it joins (`up-down`, `left-right`, `up-left`, `down-right`, …). `ARROW_TILES` in `tileset.ts` maps each piece name to its tile on the terrain sheet. Tested in `src/game/moveArrow.test.ts`.

### `src/game/keyRepeat.ts`

Pure key repeat for the arrow keys. `updateKeyRepeat(state, { isDown, justPressed }, deltaMs, timing)` advances one frame and returns `{ state, step }`, `step` being a `DIRECTIONS` entry or null: a press steps at once (even a tap shorter than a frame), holding repeats after `KEY_REPEAT.delayMs` and then every `intervalMs`, at most one step per frame. The most recently pressed key still held sets the direction, so the cursor never moves diagonally; letting go of it hands back to the older key after the delay. `GridScene.readArrowKeys` feeds it Phaser's key states each frame, so holding an arrow moves the cursor and menu highlights continuously. Tested in `src/game/keyRepeat.test.ts`.

### `src/game/combat.ts`

Pure combat rules. `getAttackRange(grid, origin, maxRange, minRange = 1)` returns every in-bounds tile within that orthogonal distance band as `[{ x, y }]` — never the attacker's own tile, and not blocked by terrain or units. `getAttackTargets(grid, origin, maxRange, isHostile, minRange)` narrows that to occupied tiles whose unit `isHostile(unitId)` accepts, as `[{ x, y, unitId }]`. `getThreatRange(grid, stops, maxRange, minRange)` is the fringe of tiles a unit could strike after moving: every tile in attack range of any of `stops` (its movement range), minus the stops, without duplicates. A fighter brings its stats plus its equipped `weapon` (from `weapons.ts`; null for none) and optionally the `weaponUses` it has left (no unit passes it since gear stopped wearing out, so it never limits a strike). `DAMAGE_TYPES` maps each damage type to the attacker stat that powers it and the defender stat that guards it (`physical`: `strength` vs `defense`; `magical`: `magic` vs `resistance`), `getDamageType(attacker)` follows the weapon type (`WEAPON_DAMAGE_TYPES`; physical without a weapon, throws on unknown types), and `calculateDamage(attacker, defender)` is power plus weapon power minus guard for that type (and, for a physical hit, the defender's `armorDefense` from worn armor), floored at 0. `isInStrikeRange(unit, distance)` checks a distance against the unit's weapon `minRange`–`maxRange` (false without a weapon). `getStrikeOrder(attacker, defender, distance)` lists who strikes, in order, as `'attacker'`/`'defender'`: the attacker, the defender if the attacker is within its strike range, then whoever doubles (`canDouble`; the attacker takes precedence, and a defender that can't reach never doubles). A side given `weaponUses` drops its strikes past the last one (unused now that gear never breaks); a side with no weapon never strikes. `resolveCombat(attacker, defender, { distance, rng = Math.random, trueHit = false })` plays that order without mutating anything: each strike rolls to hit against `getHitChance` and, if it lands, to crit against `getCritChance` (×`CRIT_MULTIPLIER`); a miss deals 0, and the exchange stops as soon as someone dies. Procs from a side's modifiers act on its strikes: `getStrikeHitChance` is 100 with `sure-hit`, `getCritMultiplier` takes the highest `crit-multiplier`, `always-double` makes a side double whatever its speed (in `getStrikeOrder`, so the forecast counts it), a hit that leaves the foe at or under its `finisher` percent fells it (the strike's `finished`), `lifesteal` heals the striker a share of the HP it took (`drain`), and after each strike `twin-strike` rolls for one more by the same side at once, while its weapon has uses left (twins don't chain; the forecast doesn't count them). Gear effects act there too: a killing crit heals an `overkill-heal` striker by the damage past the foe's HP (in `drain`), and a landed strike the foe survives costs the striker `getRecoil(struck, dealt, distance)` (the foe's `thorns` from the next tile plus its `reflect` percent of the damage; the strike's `recoil`, with `recoilLethal` ending the exchange when it fells the striker, which `battle/commands.ts` plays as a `recoil` event and a kill for the struck unit). It returns `{ strikes, attackerHealth, defenderHealth }`, where `strikes` is the ordered `[{ by, target, damage, hit, crit, lethal }]`. The RNG is injected so tests are deterministic. Applying damage is left to the caller (`Unit.takeDamage`). A fighter's `modifiers` (`modifiers.ts`) count too: `withCombatBonus(unit, opponent, attacking)` copies a side's stats with the `bonus` its modifiers add for the exchange (`getFighterBonus`: whether it's the attacker, under half HP, or facing a `monster`, plus the foe's side of `getFighterContext` — wounded, unhurt, debuffed, Marked — and the counted gear effects `crit-per-foe-debuff` and `missing-health-bonus`; a `sure-hit` with a `when` is kept only while it holds), which `getHit`, `getAvoid` and `getCrit` and `calculateDamage` (the attacker's `damage`, minus the defender's `guard`) read; `resolveCombat` and `getCombatForecast` both arm their two sides this way, so the forecast still matches the roll, and a side without modifiers is used as it is. `getCombatForecast(attacker, defender, { distance })` previews the same exchange without rolling: per side `{ health, maxHealth, damage, hit, crit, strikes, counters }`, built from the same `getStrikeOrder`, `calculateDamage`, `getHitChance` and `getCritChance` so preview and outcome can't disagree (`damage` is a landed non-crit strike; a defender that can't reach has `counters: false`, 0 strikes and `null` damage/hit/crit). `getForecastHealthAfter(forecast)` walks a forecast's strikes in that same order as if every one lands without a crit, stopping at the first kill, and returns the health each side is left on, for the forecast's health bars. Tested in `src/game/combat.test.ts`.

### `src/game/modifiers.ts`

The one way bonuses reach the formulas (roadmap W.5). A `Modifier` is plain data: `combat` (a `term` — `hit`, `avoid`, `crit`, `damage`, `guard` (damage taken off each hit), or the percent terms `damage-percent` and `guard-percent` that `scaleDamage` in `combat.ts` applies after defense, guard capped at `MAX_GUARD_PERCENT` — and an `amount`, optionally only `when` `attacking`, `defending`, `wounded` (under half HP), `vs-monster`, or about the foe: `vs-wounded`, `vs-unhurt` (full HP), `vs-debuffed`, `vs-marked`), `movement`, `experience` (XP rate points), the triggers `kill-heal`, `phase-heal`, `phase-heal-percent` (a share of max HP), `phase-mana` and `spare-weapon-on-kill`, `skill` (teaches a skill), and the combat procs `combat.ts` reads: `twin-strike` (percent chance a strike is followed by another), `finisher` (fells a foe a hit leaves at or under that percent of max HP), `lifesteal` (percent of the HP taken healed), `always-double`, `sure-hit` (optionally `when`) and `crit-multiplier`, the gear effects `crit-per-foe-debuff`, `missing-health-bonus`, `thorns`, `reflect` (optionally only while the unit has a `status`) and `overkill-heal`, the gear effects `battle/commands.ts` plays: `status-on-hit` (a landed strike, or only a crit, lays a status on the foe it struck), `status-on-recoil` (its recoil lays a status on the striker), `kill-stack` (each kill adds to a combat term for the rest of the battle), `kill-heal-percent`, `encore` (a kill in its own attack lets it move and act again, once a phase: `grantEncore` / `hasEncored` in `turns.ts`, an `encore` event), `contagion` (a foe it fells passes its debuffs to the foe nearest it), `taunt-aura` (its phase starts by Taunting the foes beside it), `veil-on-wait` (waiting leaves it Veiled, +30 avoid, or with the modifier's own `status`: the Ambush Cloak's Lurking, +15 avoid) and `linger-debuffs` (the debuffs it lays outlast one more wear-off; `Unit.lingering` holds such debuffs, and a debuff laid on a unit during its own phase lingers too, so it isn't gone the moment that phase ends), plus the map actions `battle/commands.ts` plays: `cleave-through` (a percent of each hit splashed onto the foes beside the target), `chain-kill` (percent chance a kill in the unit's own attack earns one free, uncountered strike on the weakest foe in reach), `shove-on-attack` (a hit in the unit's own attack shoves the target a tile back once the exchange is over, if both still stand: the slime's Bounce passive) `blink` (moves as `BLINK_MOVEMENT`, via `getMovementOptions`) and `momentum` (a kill in the unit's own attack, unless it decided the battle, starts a canto of that many tiles and a `momentum` event instead of ending the unit's action; the unit can then only `move` (within the canto, which ends it) or `wait`, an order to any other unit ends the canto with the unit in place, and the AI planners wait it out; GridScene opens the canto's move range straight after the attack plays, and cancelling it waits). A unit carries them as `Unit.modifiers`; `applyModifiers(unit, modifiers)` adds them to a freshly built unit and bakes movement and XP rate into its MOV and `experienceRate`. `getCombatBonus(modifiers, context)` sums the combat terms whose condition holds (stacking freely), `getStandingCombatBonus` the unconditional ones (the unit info screen's rates), `sumModifiers` / `hasModifier` read the rest, and `getModifierSkills` lists taught skills. Combat (`combat.ts`, `skills.ts`) reads the combat terms; `battle/commands.ts` fires the triggers: a kill heals the killer its `kill-heal` and a `spare-weapon-on-kill` strike that kills doesn't wear its weapon, and as each phase starts its team's units recover `phase-heal` HP and `phase-mana` MP, each reported as a `recovered` event (`trigger` `'kill'`, `'phase'`, or `'drain'` for a lifesteal strike's heal, which GridScene plays like a kill's); a cleave-through hit reports each splashed foe as a `splash` event, and a chain kill a `chain` event before its free strike. Relics (`warband/relics.ts`) and boons (`warband/boons.ts`) are the sources today; traits and elite enemies are meant to come the same way. Tested in `src/game/modifiers.test.ts`, with the combat and trigger rules in `combat.test.ts`, `skills.test.ts` and `battle/commands.test.ts`.

### `src/game/curses.ts`

What cursed gear costs. A `Curse` makes the enemy side stronger, only in battles where a unit carrying it is deployed: a unit holds its curses for the battle as `Unit.curses` (set by whatever gives it cursed gear), and `startBattle` in `battle/commands.ts` gathers the deployed units' curses (`getDeployedCurses`) and lays them on clones of the enemies (`applyCurses(enemies, curses, rng)`), stacking. Kinds: `enemy-surge` (every enemy's stats grow by a percent, the curses' percents added together, through `applySurge` in `warband/enemyCurve.ts`), `enemy-affix` (every enemy carries an elite affix from `warband/elites.ts`), `elite-enemy` (the strongest non-boss enemy carries that many random affixes and is ranked an elite) and `boss-modifiers` (the boss, `getCurseBoss`: the one ranked boss, else the enemy with the most max HP, carries the modifiers: a mirror curse). Tested in `src/game/curses.test.ts`.

### `src/game/gearKits.ts`

Signature and cursed gear: worn items that bend a rule. Each is a `Weapon` or `Armor` whose optional `modifiers` (`modifiers.ts`) carry its effect and, when cursed, whose `curses` (`curses.ts`) carry the enemy-side cost; `Weapon`, `Staff` and `Armor` all take both fields, and `getGearModifiers` / `getGearCurses` in `equipment.ts` read them off what a unit wears. `KIT_GEAR` holds the three kits (Reaper, Mark and exploit, Thorns tank: a weapon, armor and accessories each, plus a cursed upgrade each); `MONSTER_GEAR` one special-slot item per monster class (`forClass`, `findMonsterGear`); `SIGNATURE_GEAR` both, all in `RUN_ITEMS`. `GEAR_DESCRIPTIONS` says what each does, `isCursed` tells cursed gear apart, and `equipEnemyMonsters(units, stage, rng)` (called from `battleSetup.ts`) dresses enemy monsters in their class's gear at `getMonsterGearChance(stage)`. Tested in `src/game/gearKits.test.ts`.

### `src/game/combatStats.ts`

Pure Fire Emblem–style combat formulas, all whole percentages. The unit's `weapon` (`{ hit, crit, weight, type? }`, optional), `armorWeight` and `armorAvoid` (its worn armor's weight and light armor's avoid, optional) and `weaponTypes` (the families it's trained in) feed them. `getOverload(unit)` = `max(0, weapon weight + armorWeight − strength)`; `getAttackSpeed(unit)` = `speed − overload`; `getLoadMovementPenalty(unit)` = `floor(overload / OVERLOAD_PER_MOVEMENT)` (4), which `getPhaseMovement` in `enemyAI.ts` takes off movement; `isProficient(unit)` says its weapon is of a trained family (`isTrained` in `weapons.ts`); `getHit(unit)` = weapon hit + `dexterity × 2` + `luck / 2`, + `PROFICIENCY_HIT` (15) when proficient; `getAvoid(unit)` = attack speed `× 2 + luck + armorAvoid`; `getCrit(unit)` = weapon crit + `dexterity / 2`, + `PROFICIENCY_CRIT` (5) when proficient; `getDodge(unit)` = `luck` (halves round down, missing stats count as 0); an optional `bonus` (`modifiers.ts`'s combat terms) adds to hit, avoid and crit. `getHitChance(attacker, defender)` and `getCritChance(attacker, defender)` are rate minus the opponent's avoid/dodge, clamped to 0–100. `canDouble(unit, opponent)` is true when the unit's attack speed beats the opponent's by at least `DOUBLE_THRESHOLD` (4). `rollChance(chance, rng, { trueHit })` rolls 0–99 from the injected `rng` and succeeds under `chance`; with `trueHit` it averages two rolls (FE's "2RN"). Tested in `src/game/combatStats.test.ts`.

### `src/game/experience.ts`

Pure Fire Emblem–style experience and growth rules. `getHitExperience(level, enemyLevel)` = `max(1, floor((31 + enemyLevel − level) / 3))` (10 at an even level); `getExperienceForLevel(level)` is the XP a level needs (`FIRST_LEVEL_EXPERIENCE`, 50, from level 1 to 2, else `EXPERIENCE_PER_LEVEL`, 100); `getKillExperience` adds `KILL_BONUS` (20) + 3 per level the opponent is above (never negative). `getCombatOutcome(strikes, side)` reads a `resolveCombat` strike list as `'died'` / `'kill'` / `'hit'` (landed damage) / `'miss'`, and `getCombatExperience(level, enemyLevel, outcome)` turns it into XP (`MISS_EXPERIENCE` 1 for a miss, 0 for a death, at most the level's `getExperienceForLevel`). `addExperience(level, experience, amount)` carries overflow past each level's `getExperienceForLevel` into further levels; there is no level cap. `getLevelUpGains(growths, step)` is the stat gains of a unit's `step`-th level up, with no dice (players, recruits and enemies alike): a growth `g` is worth `g/100` of a point a level, each level up hands out the whole points the growth total has earned by then (`floor(step × total / 100)` in all), one at a time to the stat furthest behind its share `step × g / 100` (ties to the higher growth, then `GROWTH_STATS` order), so every level gives about the same number of points and each stat stays within a point of its share; it replays steps 1..`step`, so it needs no saved state. Stats have no caps. `scaleExperience(amount, rate)` applies a unit's XP rate (percent, `DEFAULT_EXPERIENCE_RATE` 100), rounding to the nearest point and never below 1 for a positive gain. `getExperienceToNextLevel(level, experience)` is what's left of the current level (0 at the max). `getCombatAward(unit, opponent, outcome)` returns the `{ amount, scaled }` award for a combat: `getCombatExperience`'s XP, to be scaled, except a kill of an opponent with `levelUpOnKill`, which is exactly the XP to the next level, unscaled, so every class lands on it with 0 XP. `resolveExperienceGain(unit, amount, { trees, scaled })` scales the gain by the unit's `experienceRate` (unless `scaled` is false), then combines them without mutating: `{ amount (what it earned), level, experience, levelUps: [{ level, gains, stats, skills }] }`, with caps applied across consecutive level ups and the skills each new level teaches from `getSkillsLearnedBetween`. Tested in `src/game/experience.test.ts`.

### `src/game/Unit.ts`

Base `Unit` class that specific unit types extend. `clone()` copies a unit of the same class that changes independently. Holds stats (`name`, `unitClass`, `level` (default 1), `health`/`maxHealth`, `mana`/`maxMana` (default 0), `strength`, `magic`, `skill`, `speed`, `luck`, `defense`, `resistance` (all but `strength` and `defense` default to 0), `movement`, `team`), the `weaponTypes` its class masters (default none), and its kit in three parts (`equipment.ts`): `equipment` (gear by slot, in its class's `gearLayout`), `innate` (the attacks its body comes with: fists, a monster's natural weapon, spells it knows) and `items`, its bag of up to four consumables. The constructor takes a mixed `items` kit, as the class files list it, and sorts it with `createLoadout` (or takes `equipment` and `innate` as given, as a saved snapshot restores them). Getters read what it fights with: `weapon` (the attack `attackIndex` picks among the main-hand weapon its class is trained in and its innate attacks, or null), `equippedWeapon` (`{ weapon, index }`), `wieldableWeapons` (the picked one first), `staves` (the main-hand staff), `wornArmor`, `canUseShield`, `armorDefense` and `armorWeight`; `equip(index)` picks an attack for the battle (the gear itself never changes mid-battle), and `recordStrike()` returns `{ weapon, learned }`, a strike with a tome counting towards learning its spell in `tomeProgress` (see `tomes.ts`), the learned spell joining `innate`. Nothing wears out. It also has the state changes every unit shares: `isAlive()`, `takeDamage(amount)`, `heal(amount)` (both clamp health between `0` and `maxHealth`), `spendMana(amount)` (throws if the unit can't afford it), `restoreMana(amount)` (clamped to `maxMana`), `useItem(itemId)` (restores a consumable's stat, uses one up, and returns `{ item, amount }` with the amount actually restored; throws if it isn't carried or is a weapon), and `levelUp(gains)` (level + 1 and the stat gains added; health and mana gains raise both maximum and current), and `gainExperience(amount, rng, scaled)` (runs `resolveExperienceGain` from `experience.ts`, applies each level up, stores the leftover `experience`, and returns the result). It also holds `experience` (default 0), `growths` and `caps` (default `{}`), `experienceRate` (percent of each XP gain it earns, default 100), and `levelUpOnKill` (default false; killing it gives the killer exactly a level, see `getCombatAward`). No Phaser dependency — subclasses set their class, stat line, growths, weapon types and starting items (e.g. `Villager`: physical, a Wooden Sword and Fists; `Soldier`: physical, an Iron Spear; `Acolyte`: magical, the Light spell and a Heal staff). It also holds a `faction` (a `FactionId` from `factions.ts`, or null for neutral units and monsters), defaulting by team through `getDefaultFaction`. Tested in `src/game/Unit.test.ts`.

`Unit.modifiers` and `Unit.curses` are accessors: a unit's own (`ownModifiers`, `ownCurses`: relics, boons, keystones, battle stacks) followed by its worn gear's (`getGearModifiers` / `getGearCurses`). Setting either sets the own list, leaving out the gear's entries by identity, so `unit.modifiers = [...unit.modifiers, more]` (as `applyModifiers` does) never doubles gear effects. Gear `movement` modifiers aren't read yet; gear `experience` ones add to the XP rate in `resolveExperienceGain`.

### `src/game/healing.ts`

Pure healing rules. A staff is an item `{ kind: 'staff', id, label, power, minRange, maxRange, hands }` — not a weapon, so it never attacks or counters, and it never wears out; it's held in the main hand (`equipment.ts`). `HEAL_STAFF` (power 2, range 1) is the only one so far, and `staffEntry(staff)` makes a kit entry. A unit's staves are `{ staff, index }` (`Unit.staves`), `isWounded(patient)` says whether a unit is alive and below its maximum health, `getHealAmount(healer, staff, patient)` is the staff's power plus the healer's intelligence capped at the patient's missing health, `getHealTargets(grid, origin, staff, canHeal)` finds the tiles in the staff's range holding a unit `canHeal` accepts (the scene passes wounded allies), and `findUsableStaff(staves, hasTarget)` picks the first staff with someone to heal. Each heal earns the healer `HEAL_EXPERIENCE` (10). Tested in `src/game/healing.test.ts`.

### `src/game/skills.ts`

Pure skill rules. A skill is `{ id, label, manaCost, range, animation }` plus optional `power` (added to the user's attack stat, default 0; for a healing skill, its base heal) and `damageScale` (multiplies the damage, default 1) — every skill's damage is a variant of the user's regular hit (`animation` names the effect the scene plays) — and `push`, which also shoves a target it leaves standing (see `push.ts`). A skill with `effect: 'heal'` (`isHealingSkill`) strikes no one: it mends a wounded ally for its `power` + the user's intelligence (`getSkillHealAmount`), which `battle/commands.ts` plays as a `healed` event carrying the skill; `getSkillTargets` there gives a skill's targets (foes, or wounded allies for a healing one; the user's own tile for a range-0 skill) to the command and the scene alike, and `getSkillVictims` everyone it lands on. An `area` skill (`'sides'`, `'line'` or `'burst'`, see `getSkillAreaTiles`) also lands on the units it affects on the tiles past its target (foes, every unit but the user with `friendlyFire`, wounded allies for a healing one), each a `skill` event marked `splash` that the scene plays as a flash with the first blow; the user earns the XP of the victim that rewards most. A `followUp` skill (Tandem Strike) strikes its target again for that share of the first blow (`getFollowUpDamage`, also in the forecast), as a second `skill` event marked `followUp`. `intelligenceScale` scales the INT a healing skill adds (Prayer: half). A `status` skill (Pinning Shot, Sunder, Mark, Roar, Taunt) leaves a status (`statuses.ts`) on the foes it lands on, and a `selfStatus` one one on its user too (Taunt leaves foes within 2 tiles, the `'wide'` area, Taunted and the user Taunting). A skill with `effect: 'buff'` (`isBuffSkill`; `isSupportSkill` is a heal or a buff, which the scene aims in green with no forecast) strikes no one: `buffWith` in `battle/commands.ts` gives its `status` to the ally it's aimed at, or every ally its area reaches (Phalanx, Bulwark, Ward, Tailwind), and earns a heal's XP. `SKILL_TREES` maps each unit class to `[{ level, skill }]`, so every class has its own skills and a unit knows each one whose level it has reached — skills are gained by leveling up rather than stored on the unit. `getLearnedSkills(unitClass, level, trees)` lists the known skills in tree order, `getSkillsLearnedBetween(unitClass, fromLevel, toLevel, trees)` the ones a level up unlocks, `getUnitSkills(unit)` / `findUnitSkill(unit, skillId)` add its secondary class's skills (`getSecondarySkills`, see `warband/mentors.ts`) and the skills its modifiers teach (a skill boon) to its class's, each once, and are what the battle and menus use, `calculateSkillDamage(skill, user, defender)` is the user's regular `calculateDamage` (so its weapon's power and damage type count) with the skill's `power` added to its attack stat (strength or intelligence, by damage type), times `damageScale`, rounded up (so a halved hit that would have dealt damage deals at least 1), `getSkillForecast(skill, user, defender, push?)` previews an offensive skill in the same shape as `getCombatForecast` (100% hit, 0% crit, one strike, no counter, plus any push damage or drowning), `canUseSkill(unit, skill)` checks mana, and `getSkillActions(unit, skills)` builds skill menu entries (`{ id, label, manaCost, disabled }`, disabled when unaffordable). Every class learns its skill at `SKILL_UNLOCK_LEVEL` (2), its first level up, so a new unit starts with none, bar the soldier's `SHOVE` (1 mana, range 1, `damageScale` 0, `push`), known from level 1. The soldier learns `SHIELD_BASH` (3 mana, range 1, power 1, `push`); the villager learns `THROW_STONES` (2 mana, range 4, damageScale 0.5 — half its regular damage, rounded up), which every promoted class's tree starts with so a promoted villager keeps it; the archer learns `LONG_SHOT` (2 mana, range 3, its regular hit, flown with the stone animation); the vanguard learns `CLEAVE` (3 mana, range 1, its regular hit on the target and the foes on either side); the sapper learns `BLAST`; the acolyte learns `MEND` (3 mana, range 1, heals 2 + INT, like its staff). The siege learns `BARRAGE` (range 3, half damage, a burst); the beast learns `SAVAGE_BITE`. A `drain` skill (Savage Bite) heals its user that share of the damage it dealt foes (a `recovered` event with trigger `drain`), a `recoil` one (Reckless Swing) costs its user that much HP, never its last (a `recoil` event), and `monsterPower` adds power against a monster (Smite). Some skills move their user (geometry in `skillMoves.ts`): a `leap` skill (Jump Swing, Pounce; a `straight` one only along a clear row or column, Battering Charge) lands it next to its target before the blow, a `strafe` one (Strafing Run) flies it in a line to the farthest free tile and strikes every foe it passes over, a `retreat` one (Hit and Run, Disengage) steps it straight back after, and `chargePower` (Charge) adds 1 power per tile it walked this phase (`Unit.movedTiles`, set by the move command and reset as its team's phase starts). A skill with `effect: 'swap'` (`isSwapSkill`; Lend a Hand, Airlift) trades places with an ally (`swapWith`). Each move is a `relocated` event the scene tweens. A tile skill (`isTileSkill`) is aimed at a tile, not a unit (`getSkillTargets` gives TargetTiles with an empty `unitId`; `reshapeWith` in `battle/commands.ts`): a `mine` skill (Lay Mine) lays a mine on empty open ground (`BattleState.mines`, a `mine-laid` event), and a `breach` skill (Breach, Breaching Shot) turns a wall or mountain into dirt (a `breached` event); see `terrainSkills.ts`. The scout learns `HIT_AND_RUN`, the beast rider `CHARGE` and the ram `BATTERING_CHARGE`. `CLASS_SKILL_PICKS` maps a class to the skills a level up may offer it as a skill boon (Villager: `LEND_A_HAND`, Archer: `PIERCING_SHOT`, `PINNING_SHOT` and `DISENGAGE`, Soldier: `LUNGE`, `PHALANX` and `TAUNT`, Vanguard: `SUNDER`, `RECKLESS_SWING` and `JUMP_SWING`, Sapper: `SHRAPNEL`, `LAY_MINE` and `BREACH`, Acolyte: `SMITE`, `PRAYER` and `WARD`, Scout: `MARK`, `TAILWIND` and `AIRLIFT`, Beast: `WING_BUFFET`, `ROAR` and `POUNCE`, Beast Rider: `SKEWER`, `TANDEM_STRIKE` and `STRAFING_RUN`, Siege: `DEADEYE` and `BREACHING_SHOT`, Ram: `BULWARK` and `BREACH`), only ever its own class's, read with `getClassSkillPicks(unitClass)`. `describeSkill(skill)` is a one-line description for offers, and `hasSkillTree(unitClass)` whether a class has skills to teach. Tested in `src/game/skills.test.ts`.

### `src/game/skillMoves.ts`

Pure geometry for skills that move their user: `canStandOn(grid, tile, self)` (in bounds, empty but for `self`, walkable), `getStep` / `isInLine`, `getLeapLanding(grid, self, from, target, leap, straight)` (the free tile next to the target nearest the leaper, or the tile short of it along a clear line for a straight charge; null when none is in reach), `getRetreatTile(grid, self, from, target, steps)` (straight back from the target as far as free tiles allow) and `getStrafePath(grid, self, from, target, reach)` (the farthest free tile in line past the target, with the tiles flown over). `getSkillTargets` in `battle/commands.ts` offers a leap or strafe only where these find a landing. Tested in `src/game/skillMoves.test.ts`.

### `src/game/terrainSkills.ts`

Pure rules for skills that change the map. A `Mine` is `{ x, y, team, damage }`, kept on `BattleState.mines`: `addMine` / `removeMine` keep one a tile, `canLayMineOn` wants empty walkable ground, `findTrippedMine(mines, path, team)` finds the first mine a foe of its layer's team steps on along a move (the move command then emits `mine-tripped` and removes it; the walker carries on), and `getMineDamage` never takes the last HP, so a mine can't end a unit's turn mid-plan. `BREACHABLE_TERRAIN` (wall, mountain) and `RUBBLE_TERRAIN` (dirt) are what a breach knocks down and leaves. The scene redraws the terrain art when the grid's terrain changes (`refreshTerrain`, so undo puts a wall back) and marks the player's side's mines (`refreshMines`); the enemy's stay hidden. The enemy-action player plays a move's other events (a tripped mine) after the walk. Tested in `src/game/terrainSkills.test.ts`.

### `src/game/statuses.ts`

Pure rules for statuses: short-lived conditions a skill with a `status` (skills.ts) leaves on each foe it lands on that's still standing — the debuffs `rooted` (can't move: `getPhaseMovement` in `enemyAI.ts` gives it 0, which the move command, the scene's move range, the player AI and the enemy planners all read), `sundered` (a `guard` −3 combat modifier) `marked` (`avoid` −15) and `taunted` (`getTargetFilter` in `battle/ai.ts` has a Taunted unit go only after Taunting foes while one is in play), and the buffs a buff skill gives an ally, `guarded` (`guard` +2), `warded` (`guard` +4) `hastened` (+2 MOV through `getPhaseMovement`, `getStatusMovement`) and `taunting` (Taunt's user). `STATUSES` names and describes each with the modifiers it adds; `addStatus` adds one without stacking, `getStatusModifiers` lists what statuses add (`getFighterBonus` in `combat.ts` folds them in with the unit's own modifiers, so attacks, counters, skills and forecasts all count them, and the unit info screen's rates too), and `isRooted` checks the first. A unit carries its statuses on `Unit.statuses` for the battle only (never saved); `battle/commands.ts` emits a `status` event as one lands; in `startPhase` a team's debuffs wear off when its phase ends and its buffs when its next phase starts (`clearStatuses`), so either kind given in the player phase lasts through the enemy phase after it. The scene pops the status's name over the unit, and the unit panel lists them (`UnitView.statuses`). Tested in `src/game/statuses.test.ts`.

### `src/game/items.ts`

Pure rules for items. An `Item` is a consumable, a weapon (`weapons.ts`), a staff (`healing.ts`), armor or a seal, told apart by `kind`. Armor is `{ kind: 'armor', id, label, slot, defense, weight, weightClass?, avoid?, resistance?, forClass? }` with `slot` `'shield'`, `'head'`, `'body'`, `'accessory'` or `'special'` (special gear names the monster class it's made for in `forClass`); body and head pieces have a `weightClass` (`ArmorWeight`: `'heavy'`, `'light'` or `'cloth'`, labelled by `ARMOR_WEIGHT_LABELS`), light ones add `avoid` and cloth ones `resistance`. `ARMORS` holds `WOODEN_SHIELD`, `WOODEN_ARMOR` (heavy) and the rest of the gear ladder (`LADDER_ARMORS` in `gearLadder.ts`), and `isArmor` tells one apart. Wearing it is `equipment.ts`'s job: its defense is subtracted from physical hits and its resistance from magical ones (`Unit.armorDefense`, `Unit.armorResistance`, `calculateDamage`), its avoid adds to avoid (`Unit.armorAvoid`, `getAvoid`) and its weight adds to the weapon's (`Unit.armorWeight`, `getAttackSpeed`, `getLoadMovementPenalty`). A consumable is `{ kind: 'consumable', id, label, stat, amount }` — `stat` is what it restores (`'health'` or `'mana'`), `amount` the most it restores per use; `HEALTH_POTION` (+5 HP) and `MANA_POTION` (+3 MP) exist so far, and `STARTING_ITEMS` gives one of each (classes add their weapon). A unit's bag is an inventory, a frozen list of `{ item, quantity }` entries of consumables only: `createInventory(entries, limit)` builds one (dropping empty entries; throws past `MAX_INVENTORY_SLOTS`, 4 — each entry takes a slot whatever its quantity), `canAddItem` says whether an item stacks onto an entry or has a free slot (only consumables go in a bag), `addItem(inventory, item, quantity)` returns a new inventory with it stacked or in a new slot (throws when full), `findItem` looks one up by id, and `removeItem` returns a new inventory with one used up (dropping an entry that runs out; throws if the item isn't there). `getItemRecovery(unit, item)` is what the item would actually restore — its amount capped by how far the stat is below its maximum, and 0 for anything but a consumable — `canUseItem` is whether that's above 0, `getConsumables(inventory)` lists the consumable entries, and `getItemActions(unit, inventory)` builds item menu entries for the consumables (`{ id, label, quantity, disabled }`, disabled when the item would restore nothing). Tested in `src/game/items.test.ts`.

### `src/game/equipment.ts`

Pure rules for equipment, Tactics Ogre style: a unit wears gear in slots apart from its bag. `GearSlot` is `'main' | 'off' | 'head' | 'body' | 'accessory' | 'special'`; `getGearLayout(classId)` gives a humanoid the paper doll (`GEAR_SLOTS.humanoid`: main hand, off hand, head, body, accessory) and a monster (the monster classes, the Beast, Whelp, Ram, Bat, Dragon and the elementals) its two (`GEAR_SLOTS.monster`: special, accessory). `Gear` is a weapon (not a natural one), a staff or armor (`isGear`); `getGearSlot(gear)` puts weapons and staves in the main hand, a shield in the off hand and other armor in its own slot. `Equipment` is a frozen slot → gear map (`NO_EQUIPMENT` empty). `canEquip(equipment, gear, layout, classId)` needs a slot the layout has, special gear made for the class, and for a shield a hand free (`hasHandFree`: the main hand empty or one-handed); `equipGear` wears a piece and returns `{ equipment, removed }` (the slot's old gear, and the shield when a two-handed weapon or a staff goes in); `unequipGear` empties a slot. `getWornGear`, `getWornArmor`, `getArmorDefense`, `getArmorAvoid`, `getArmorResistance`, `getArmorWeight`, `getMainWeapon` and `getMainStaff` read it. `createLoadout(entries, layout, classId)` sorts a mixed kit (a class's starting items, an old save's inventory) into `{ equipment, innate, bag, spare }`: natural weapons are innate, the first gear for each slot is worn, consumables fill the bag, and the rest is spare (a save sends it to the convoy). Gear never breaks and is set between battles only. Tested in `src/game/equipment.test.ts`.

### `src/game/loot.ts`

Pure loot rules: items enemies drop when defeated. `LOOT_ITEMS` is what can drop (the gear ladder's wooden tier, see `gearLadder.ts`, and the Fire tome, see `tomes.ts`). `STAGE_LOOT_DROPS` is how many enemies carry loot per Warband stage (one each in stages 1–3, none after, until it's tuned) and `getStageLootCount(stage)` reads it. `assignLoot(enemyIds, count, rng)` picks `count` enemies at random and an item for each, by enemy id; the item sits on the enemy's `Unit.loot`, apart from its kit, so it never fights with it. `claimLoot(inventory, item)` → `{ inventory, stored }` puts a consumable in the killer's bag, or leaves that alone and says it goes to the convoy (always for gear, which is equipped between battles); `getLootQuantity` is the entry's quantity (1). `GridScene.dropLoot` calls it when a player unit lands the killing blow (an attack, a counter or a skill): a "Got …" / "… to convoy" popup names the item, the convoy's share goes into the run through `finishStage`, and an enemy carrying loot shows it only as a "Drops" line on the unit panel; nothing is drawn over its sprite on the map. Tested in `src/game/loot.test.ts`.

### `src/game/gearLadder.ts`

The gear ladder, as data: four tiers (`GEAR_TIERS`: wooden, iron, steel, silver), each with a weapon of every `LADDER_FAMILIES` family (sword, spear, axe, bow, dagger), a shield, and a body and a head piece in each armor weight. It defines the pieces the game didn't have before (`LADDER_WEAPONS`, `LADDER_ARMORS`, which `WEAPONS` and `ARMORS` list; it imports only types, so `weapons.ts` and `items.ts` can import it) and names every tier's pieces by id (`GEAR_LADDER`, including the older wooden and iron pieces). `getTierItemIds(tier)` lists a tier, `getGearTier(itemId)` finds one's tier (null off the ladder), `isHigherTier` compares two, and `getClassArmorWeight(classId)` is the armor weight a class wears by choice (`CLASS_ARMOR_WEIGHTS`: heavy for the front line, cloth for casters, light for the rest). The merchant (`warband/merchant.ts`), loot (`loot.ts`), enemy loadouts (`enemyGear.ts`) and the auto-run policy read it. Numbers in `UNITS.md`. Tested in `src/game/gearLadder.test.ts`.

### `src/game/enemyGear.ts`

Enemy loadouts. `outfitEnemy(enemy, level, items)` returns a humanoid enemy's equipment for its level: its weapon moves up the gear ladder in its own family to `getEnemyTier(level)` (`ENEMY_TIER_LEVELS`, the merchant's stages: iron at 4, steel at 11, silver at 20), and from `ARMOR_FROM_LEVEL` (3) it wears a body piece, from `HELM_FROM_LEVEL` (8) a head piece, of the tier `ARMOR_LAG` (3) levels lower in its class's armor weight. It never trades down what it starts with and never puts on armor that would cost it movement; monsters and staff-holders keep their kit. `createStageLevel` (`warband/stageLevel.ts`) calls it on each enemy after `growToLevel`. Tested in `src/game/enemyGear.test.ts`.

### `src/game/weapons.ts`

Pure weapon rules. A weapon is an item `{ kind: 'weapon', id, label, type, hands, power, hit, crit, weight, minRange, maxRange }`; `type` is its family, one of `WEAPON_TYPES` — `sword`, `spear`, `axe`, `bow`, `dagger`, `tome`, `staff`, `siege` or `natural` (a body's own weapons and Fists), labelled by `WEAPON_TYPE_LABELS` — which decides the damage it deals (`WEAPON_DAMAGE_TYPES`: tomes and staves hit magically, the rest physically). Any unit wields any weapon; a class lists the families it's trained in (`weaponTypes`), and `isTrained(weaponTypes, weapon)` (a natural weapon always is) gives the proficiency bonus (`PROFICIENCY_HIT`, `PROFICIENCY_CRIT`, applied in `combatStats.ts`). `hands` (1 or 2) is how many hands it takes; bows, the Great Axe and siege weapons take two, and so does every staff (`healing.ts`), which leaves no hand for a shield (`hasHandFree` in `equipment.ts`). Weapons never wear out. `WEAPONS` holds one starter weapon per armed unit in the unit catalog (`FISTS`, `IRON_SPEAR`, `IRON_AXE`, `IRON_BOW`, `FIRE` (the Fire tome), `POWDER_KEG`, `BALLISTA`), `FIRE_SPELL` (Fire once learned from its tome), the monsters' natural weapons, the basic wooden set no class starts with (`WOODEN_SWORD`, `WOODEN_SPEAR`, `WOODEN_AXE`; numbers in `UNITS.md`), and the rest of the gear ladder (`LADDER_WEAPONS` in `gearLadder.ts`), and `weaponEntry(weapon)` is a kit entry. What a unit attacks with is `Unit.wieldableWeapons`, `{ weapon, index }` (`EquippedWeapon`): its main-hand weapon and its innate attacks. `getWeaponReach(weapons)` is the `{ minRange, maxRange }` span of several weapons (for the threat fringe), `formatWeaponRange` reads a range as "1" or "1–2", and `getWeaponActions(attacks, hasTarget)` builds the weapon menu entries (`{ id, label, index, type, power, hit, crit, weight, range, disabled }`, disabled when `hasTarget(weapon)` says nothing is in range). A weapon with `teaches: { spellId, afterUses }` is a tome (`tomes.ts`). `NATURAL_WEAPON_IDS` are the weapons that belong to a body and never move: fists, the monsters' weapons and learned spells. Tested in `src/game/weapons.test.ts`.

### `src/game/tomes.ts`

Pure rules for tomes: magical weapons that teach a spell. `isTome(weapon)` checks for `teaches`, `getTomeSpell(tome)` looks the spell weapon up in `WEAPONS`, and `knowsSpell(innate, tome)` is whether the spell is among a unit's innate attacks. A unit's progress is a `TomeProgress` map of tome id to strikes made (`Unit.tomeProgress`, saved on its `UnitSnapshot` and absent when empty): `recordTomeUse(progress, tome)` → `{ progress, learned }` counts a strike and drops the tome from the map once it reaches `afterUses` (Fire tome: 5). `Unit.recordStrike` runs it for a strike with a tome whose spell the unit doesn't know and, on learning, adds the spell to `innate`; the tome stays in the main hand and can go back to the convoy for another unit. `GridScene.resolveAttack` shows a "Learned …!" popup. Acolytes wield magical weapons, so they're the ones who learn. Tested in `src/game/tomes.test.ts`.

### `src/game/battle/`

The battle as data and commands, so it can be undone, replayed or played without the game running. Pure, no Phaser.

- `state.ts`: `BattleState`, the whole battle as one frozen value — `grid`, `units` (in play), `roster`, `deploymentZone`, `deploymentLimit`, `objective`, `stage` (`'deployment'` | `'battle'`), `turnState`, `outcome`, `deployed` (roster units that started), `fallen`, `convoyLoot` (loot and tomes sent to the convoy), `kills` (how many units each unit felled), `rngState`, the seed its next roll comes from (`createResumableRng` in `rng.ts`), and `boss`, a boss with rules' `BossState` (see `bosses.ts`), else null. `createBattleState(level, seed)` starts one in deployment; `getDeployedUnits` is what a Warband run writes back (`finishStage`), and `getRunBattleResult(state, elapsedMs)` the whole result a run takes (those units and the guest, the convoy loot, the kills and whether a boss objective was won); `getBattleSnapshot` is what objectives are checked against.
- `commands.ts`: `BattleCommand`, plain JSON objects — `place`, `start-battle`, `move` (with an optional `path`), `equip`, `attack`, `skill`, `heal`, `item`, `wait`, `end-phase`, and `take-boon` (a Warband unit's level-up boon, taken as it levels; not an action, and `undoLastAction` takes it back with the action before it) — and `applyCommand(state, command)`, which returns the next state and the `BattleEvent`s saying what happened (`moved`, `strike`, `skill`, `pushed`, `healed`, `item-used`, `loot`, `defeated`, `experience`, `unit-done`, `phase-started`, `outcome`, a boss's `war-horn`, `reinforced`, `reinforcement-blocked` and `boss-enraged`, ...), or throws a `BattleCommandError` for an order the rules don't allow (a unit out of turn or reach, a target out of range, ...). It never changes the state it's given: units it changes are cloned (`Unit.clone`) into the new state. A `push` skill (Shove) runs `getPushResult` after its blow and carries it out: the shoved unit slides (or sinks, taken off the map at 0 HP), bump and hazard damage land on it and on a unit it slammed into, and a foe it knocks out is the shover's kill (an ally isn't counted). The rules the scene used to carry out itself live here: combat exchanges with weapon wear and tome learning, loot, defeat, XP and level ups (rolled from the state's seed), finishing units, ending phases, a boss's horn as the enemy phase starts and its rage after an action (`bosses.ts`), and checking the objective.
- `history.ts`: `BattleHistory`, the starting state plus every command with the state it led to. `dispatch` adds one; `undo` / `rewindTo` drop entries (every state is kept, so going back costs nothing); `undoLastAction(history, team)` goes back to before a team's last action (a unit's move, equips and act together, with a canto's move or wait after it, or ending the phase), dropping whatever followed; `getCommands` is the script that `replay` turns back into the same battle, rolls included.
- `intents.ts`: enemy intents (Warband idea 34). `getEnemyIntents(state)` plans every enemy's coming phase the way the enemy phase will (`planUnitTurn`, in registry order, each with those before it moved to where they'll stop, on a copy of the grid), as `EnemyIntent`s: its `path`, its `target` (or null) and the forecast's `damage`, `strikes` and `hit` against it. `getIntentThreats(state, intents)` totals them per targeted unit (`damage` if every strike landed, `lethal` when that's its HP). Only dice (a kill or a miss changing a later enemy's choice) make the enemy phase differ from it.
- `ai.ts`: commands nobody chooses. `planUnitTurn` plans a unit's move and attack (or wait) with `planRushAction` and `createAttackScorer` (through `createShoveScorer` for a unit whose attacks shove, which adds what the shove would do: spikes, a bump, a drowning), for either team, then takes a skill or staff use from `skillActs.ts` instead when one scores higher (and above nothing), from the tile nearest where the rush would have ended between equals; `planNextTurn` does it for the phase's next unit that hasn't acted (the scene's enemy and guest phases); `planDeployment` places the roster on the zone and starts the battle.
- `skillActs.ts`: the acts a battle AI can take besides attacking. `getSkillActs(state, unitId, tile, { isTarget, weights, staves })` lists every skill (but a swap or a breach) and staff use the unit could make after moving to `tile`, each scored exactly (skills and heals roll no dice): a plain one (one target: a blow with its follow-up, status and shove, a heal, a buff, a mine) is worked out with the battle's own pure rules (`calculateSkillDamage`, `getPushResult`, the heal amounts), and the rest (an area, a leap, a strafing run, a retreat, a drain, a recoil, a charge) are played out with `applyCommand` on a copy where the unit stands on `tile` and the foes' hidden mines are gone, weighing its events up to `unit-done` (`weighEvents`); both weigh damage and kills on foes (a shove onto spikes or into deep water included), HP healed (twice over under half health), buffs and debuffs that weren't there, a mine laid within `MINE_REACH` of a foe, against harm to its own side and the mana spent. `SKILL_ACT_WEIGHTS` holds the weights. Used by `ai.ts` and `playerAI.ts`.
- `playerAI.ts`: a battle AI for the player's side, so a run can play itself. `getPlayerPlans(state, weights)` scores every action each unit yet to act could take from every tile it could reach (attacking, by the forecast's expected damage, counter and kill chance; using a skill, scored by `skillActs.ts`, except in a lookahead play-out's rest of the phase, to keep it quick; healing with a staff; a potion at half health or under; waiting), plus what the tile is worth (the seize bonus, progress toward the objective on a unit-free distance map, minus the damage enemies could deal there next phase, plus a little for staying near allies), and keeps each unit's best tile for each different act. `planPlayerTurn(state, { weights, lookahead })` hands the best few of those to `lookahead.ts` when one of them fights or stands in reach, else takes the best outright. The heuristic plans from the forecast, never the dice. `PLAYER_AI_WEIGHTS` holds every weight. `planPlayerDeployment` fields the healthiest units, close fighters nearest the enemy.
- `lookahead.ts`: `pickByLookahead` plays each candidate action out (the rest of the player phase by the heuristic, then the enemy and guest phases by `ai.ts`) a few times with dice seeded from where the battle stands, never from its own `rngState`, and keeps the candidate whose end states average best by `scorePlayOut`: damage dealt and taken, units lost, the outcome, and a growing penalty for a battle dragging toward its `TURN_LIMIT`. `LOOKAHEAD` sets how many candidates and samples, and its weights.
- `runner.ts`: `runBattle({ setup, seed, commands }, { auto, maxTurns, planners })` plays a battle headlessly from `createBattle(setup, seed)`: a team in `planners` is played by its `BattlePlanner` (a function from the state to its next commands), the teams in `auto` (default the enemy and the guests) by `ai.ts`, the script's commands play the rest, and it stops once the battle is decided, the script runs out, or `maxTurns` passes, returning the history and, if a scripted command was refused, which one and why. `auto: ['player', 'enemy', 'guest']` lets a battle play itself out, e.g. for balancing.
- `testLevel.ts`: small hand-built battles for the module's tests.

Tested in `src/game/battle/*.test.ts`.

### `src/scenes/GridScene.ts`

The Phaser scene that renders a grid. Loads the terrain tileset and every sprite image in `SPRITE_URLS`, gets the starting grid, unit registry, roster, and deployment zone from a level — `createBattleLevel(setup, getActiveContent())` (`src/game/battleSetup.ts`, with any dialog the player uploaded) for its scene data, the store's `battleSetup` (the first story chapter if none) — converts it into Phaser tilemaps for terrain (a 32px grass layer, then one 16px quarter-tile layer per autotiled terrain from `autotile.ts`, with animated sets such as water stepped through their frames on a timer), draws the forest, mountain and building overlays from `mapArt.ts` (`renderMapSprites`; the `wall` autotile and the buildings come in the level's `palette`), the level's trees and multi-tile structures (each structure drawn tile by tile from `getStructureTiles`: its roof rows over units, so they pass behind the roof, but under the cursor; the rest under units) over the terrain, and places sprites for occupied cells using `gridToWorld` for positioning. Each unit gets a blob shadow from `addUnitShadow` (`src/scenes/unitShadow.ts`): a translucent pixel ellipse (`UNIT_SHADOW` in `tileset.ts`, rasterized by `pixelShapes.ts`) under its feet, since the unit sprites have none. The shadow follows its sprite every frame and is destroyed with it. These followers (shadow, outline, rank badge) are added with `listenUntilStopped` (`src/scenes/sceneListeners.ts`, tested beside it): Phaser's emitter still calls listeners removed mid-event, so a follower stopped when its sprite is destroyed does nothing even if the same event is still running. Each unit is also outlined in its team's color (`UNIT_OUTLINE` in `tileset.ts`: blue player, red enemy, green guest) by `addUnitOutline` (`src/scenes/unitOutline.ts`), which builds a white outline texture of each unit sheet once with `getOutlineMask` (`pixelShapes.ts`), cut into the same frames, and keeps a tinted copy under the sprite in step with its position, sheet, animation frame, flip and visibility; the sprite's own colors are never changed. A boss or an elite (`Unit.rank`, set to `'boss'` by `placeObjective`/`makeBoss` in `stageObjective.ts` and to `'elite'` by `applyEliteAffixes`) also wears a badge in its tile's top-right corner from `addRankBadge` (`src/scenes/rankBadge.ts`): `RANK_BADGES` in `tileset.ts` (a skull on a red plate, a star on a violet one), pixel rows drawn with `getPixelArtSpans` (`pixelShapes.ts`), following the sprite like its outline; the React `RankBadge` draws the same art on the unit panel's and unit info screen's portraits and before the name in the combat forecast (`rank` on `UnitView` and `ForecastSideView`). Unit sprites are drawn by `addTileSprite`, stretched to fill one 32px tile. The terrain sheet is loaded as a 32px spritesheet, so each movement-arrow piece is a sprite of its `ARROW_TILES` frame; the cursor sprite loops `CURSOR_ANIMATION`'s two frames of its own sheet. Also renders that cursor sprite and moves it one tile per keypress by calling `src/game/cursor.ts` from `update()` and re-rendering the sprite at the new position — the scene holds no movement rules itself. The canvas is as big as the stage the page gives it (see `src/ui/` and `main.ts`), and `fitCamera` draws the map at the largest whole zoom it fits at (`getFitZoom`, 2x–4x) and points the view at the cursor with `getFollowView` (`camera.ts`) — centered where the map fits the canvas, scrolling with the cursor where it doesn't — and runs again whenever the canvas is resized. `pixelArt: true` (set in `main.ts`) keeps the pixel art crisp when scaled.

Occupied cells are backed by `src/game/Unit.ts` instances held in a `unitId -> Unit` registry (`this.units`) built alongside the grid; `cell.unitId` stays a plain string so grid data remains Phaser-free, and the registry is where actual stats/behavior live. The battle itself — grid, registry, roster, deployment zone and limit, objective, turn state, outcome — is a `BattleState` from `src/game/battle/` kept in a `BattleHistory` (`this.history`, made on `create()` with its dice seeded from the run for a Warband stage, `getBattleDiceSeed`, else `randomSeed()`), and every change to it is a command the scene gives with `dispatch` (see **Commands** below); `this.grid`, `this.units`, `this.turnState` and the rest are getters on `this.shown`, the state the map shows. Each frame, `updateHoveredUnit()` looks up the unit (if any) under the cursor and, only when it changes, publishes `toUnitView(unit)` (or `null`) to `gameStore` as `hoveredUnit`, along with `hoveredAnchor`, the TileAnchorView of the cursor's tile (or `null`), which the unit panel docks away from. Pressing I while the cursor is free to roam and on a unit publishes `toUnitDetailView(unit)` as `unitInfo`, which opens the unit info screen; while it's up it owns input, and I, confirm or cancel clears it. GridScene has no knowledge of React — it only writes plain state.

On `create()` the scene resets the battle-related store fields, plays the level's `opening` dialog if it has one (see **Dialog** below), and then starts in the **deployment phase** (`phase: 'deployment'`), publishing `toObjectiveView` of the battle's `describeBattle` title and the level's `describeObjective` as `deploymentObjective`, which the deployment menu shows above its entries. A level with no deployment zone (training) shows the Objective screen instead (`showObjective` publishes it as `objective`; confirm or cancel clears it in `hideObjective`) and goes straight to the battle. Deployment opens with the roster already placed by `planPlayerDeployment` and Start highlighted. The deployment zone is highlighted and the map cursor is hidden while a deployment menu has input (a hidden cursor hovers nothing, so the unit panel clears too). Input runs through three steps (published as `deploymentStep`): `'menu'` — the Place Units / Start menu (`deploymentMenu`); `'roster'` — the roster menu (`rosterMenu`, entries from `toRosterEntryView`, disabled when `canPickToDeploy` says no) to pick a unit; `'placing'` — the cursor roams and confirm on a tile `canDeployUnitAt` accepts dispatches the placement (moving, swapping or benching) and redraws the roster's sprites, then returns to the menu with Start highlighted once `isDeploymentComplete`, else Place Units. The scene computes the limit once from the level (`deploymentLimit`) and publishes it for the roster menu's count. Cancel steps back (placing → roster → menu). The cursor only shows during `'placing'`. Start is ignored while disabled; once chosen it clears the zone, drops roster units that weren't placed from the registry (they sit the battle out), sets `phase: 'battle'`, and starts turn 1 (see **Turns** below). All menus are mirrored to the store through `publishMenu(key, menu)`.

In the battle phase, pressing cancel on the bare map (no menu open, no range shown) opens the **pause menu** (`pauseMenu`, from `getPauseActions`), which owns input while open: cancel closes it, End Turn ends the player phase early (units that haven't acted forfeit their action) and starts the enemy phase, Undo takes the last player action back (`undoLastPlayerAction`, see **Commands**), Main Menu resets the battle store fields and sets `screen: 'title'` (which makes `main.ts` remove the scene), and Settings is a placeholder.

Pressing confirm (Enter/Z) while hovering a ready player unit selects it (`activeUnit`, the unit and its tile) and goes straight to moving: the tiles from `getMovementRange` are drawn as translucent blue overlays (allies pass through, anyone else blocks), ringed in red by the tiles it could attack from there (`getThreatRange` over the span of all its wieldable weapons, `getWeaponReach`). While the range is shown the cursor moves freely; cancel clears it and lets go of the unit, and as the cursor moves the scene keeps a planned route with `extendMovePath` and draws it as an arrow from `getArrowPieces` (sprites above the range overlay, below units); confirm on an in-range tile at the end of that route walks the unit's sprite along it (`walkSprite`: a chain of linear tweens, one per tile, playing the move animation facing each step), ignoring input until it arrives (the `move` command is given as it sets off; confirming the unit's own tile keeps it in place) and opens the action menu beside it (unless the cursor was on a hostile unit; see below): GridScene creates it with `src/game/actionMenu.ts` and publishes it to `gameStore` as `actionMenu`. While it's open the menu owns input — up/down call `moveSelection`, confirm reads `getSelectedAction`, and cancel takes the move back and shows the move range again. Sprites are kept in a `unitId -> sprite` map (`this.unitSprites`) so moves can find them. Choosing **Attack** (greyed out without a weapon the unit can wield) opens the **weapon menu** (`weaponMenu`, from `getWeaponActions`): each attack it can make (its main-hand weapon and innate attacks) with its range, greyed out when nothing hostile is in its range from the unit's tile; cancel returns to the action menu, and confirm equips the weapon (an `equip` command) and draws the tiles from `getAttackRange` for its range in red, putting the cursor on the first hostile unit in range; confirm only accepts a tile holding a hostile unit (any other team) from `getAttackTargets`, and cancel backs out to the weapon menu, so picking another weapon re-forecasts with it. While the cursor is on such a target, GridScene publishes `combatForecast` (`getCombatForecast` → `toCombatForecastView`, anchored to both units' tiles merged with `mergeTileAnchors`), refreshed whenever the cursor moves or the camera refits and cleared when the range is hidden. Confirming the target gives an `attack` command, whose exchange (rolled with `resolveCombat`) `playEvents` plays strike by strike with input locked (`playStrike`): the striker lunges at its target (`playLunge`, leaning in from range) and the blow lands at the far end — for a hit the struck unit's new health on the HUD right away, a damage popup published to `gameStore` (see below), a hit-stop that freezes both units for `getStrikeJuice`'s beat (`playHitStop`), then its sprite's hit flash from `src/scenes/effects.ts`; a unit at 0 health bursts apart (`playDeathBurst`, raising the store's `defeats` for its sound) and leaves the sprite map, which also ends the exchange. So the defender counterattacks when it can reach, a faster unit strikes a second time, and a counter can kill the attacker. Afterwards the player unit in the fight (only player units gain XP, in either phase), if it survived, gains the XP from `getCombatExperience`; a damaging skill earns XP as one landed strike. `showExperienceGain` plays the gain and publishes `experienceGain` (`toExperienceGainView`) for `EXPERIENCE_BAR_MS`, then one `levelUp` (`toLevelUpView`) per level gained for `LEVEL_UP_MS` each, with input still locked, before the action finishes. A missed strike shows a "Miss" popup and pauses briefly instead of flashing; a crit shows a "Crit!" popup, holds the hit-stop longer and shakes the camera (a plain finishing blow bumps it lightly; no shakes or particle bursts when the system asks for reduced motion). Confirming a hostile unit while choosing where to move skips the menus when the unit can strike it after moving: `getMoveAttackPlan` picks the tile and weapon with `pickAttackPlan` (the arrow already runs to that tile while the cursor is on the enemy), the unit walks there, equips that weapon, and goes straight to aiming at the enemy with its forecast up, so one more confirm attacks; cancel there undoes the move and the equip together (`undoMove`) and shows the move range again. Move/attack share one range overlay (`rangeMode` + `rangeTiles`).

Damage numbers are drawn by React, not Phaser: `showDamagePopup` converts the hit sprite's top center to canvas pixels with `worldToScreen` (using the camera's `worldView` and zoom), then to fractions of the canvas with `toCanvasFraction` (so the popup lands on the unit however large the canvas is displayed), appends a `toDamagePopupView` snapshot to `gameStore.damagePopups`, and removes it after `DAMAGE_POPUP_DURATION_MS`. The same duration travels in the snapshot so React's CSS animation and the entry's lifetime agree. The same popups show crits, misses, and recovery: `showDamagePopup(sprite, amount, kind)` with `kind` `'crit'`, `'miss'`, `'health'`, `'mana'`, or `'broke'` (a weapon wearing out).

The action menu is built per unit with `getUnitActions`, so **Skill** is greyed out (and confirm ignores it) until the unit has learned a skill from its class's tree. Choosing it replaces the action menu with the **skill menu** (`skillMenu`, from `getSkillActions`), which owns input while open: cancel returns to the action menu, and confirm on an affordable skill shows its range (`getAttackRange` with the skill's `range`) in orange as `rangeMode: 'skill'`, remembering the skill as `activeSkill`. Cancel while aiming goes back to the skill menu; confirm on a hostile unit in range gives a `skill` command (mana spent, `calculateSkillDamage` dealt) and plays the skill's animation via `playSkillAnimation` (`'stone'`: `playStoneThrow` onto the target, then a hit flash; `'strike'`: `playLunge` toward the target, then a hit flash and camera shake) before publishing the new health and damage popup and removing a defeated unit.

**Item** is greyed out while the unit carries no consumables (weapons aren't listed there). Choosing it opens the **item menu** (`itemMenu`, from `getItemActions`), which works like the skill menu: cancel returns to the action menu, and confirm on an item that would restore something gives an `item` command (the HUD shows the new HP/MP), publishes a `+N HP` / `+N MP` popup, and plays `playPotionGlow` from `effects.ts` in the stat's color from `POTION_COLORS` (green for health, blue for mana). Items target the user, so there's no range to aim, and using one finishes the unit.

A unit carrying a staff also gets **Heal** after Attack, greyed out unless a wounded ally is within a staff's reach (`findUsableStaff` over `getHealTargets`). Choosing it shows that staff's range in green as `rangeMode: 'heal'`, remembering the staff as `activeStaff`; cancel returns to the action menu, and confirm on a wounded ally gives a `heal` command (`getHealAmount` restored, a staff use spent) and shows a `+N HP` popup and the health-potion glow on the ally, then the healer's `HEAL_EXPERIENCE` XP bar before the unit is done.

**Mouse.** The mouse feeds the same confirm / cancel as the keyboard. A queued `main-menu` command (the header's Main Menu button) is checked before the input lock and calls `exitToTitle` at once, so it works mid-animation, during a dialog, or in the enemy phase; removing the scene stops whatever was playing out. Phaser pointer events on the map (`hover-tile` / `click-tile`, converted with `worldToGrid`) and commands from `gameCommands` are queued as they arrive and drained at the top of `update()` (`drainPointerInput`), so they respect `inputLocked` like keys. While no menu has input (`canRoamCursor`: bare map, aiming a range, placing a unit) the cursor follows the pointer — extending the move arrow in move mode — and a left click moves the cursor there and confirms; hovering or clicking a React menu entry highlights / picks it; right click anywhere on the stage cancels (which on the bare map opens the pause menu); a click once the battle is decided returns to the title.

**Dialog.** `playDialog(lines, onDone)` hides the cursor and shows a conversation: the scene keeps a `dialog` from `src/game/dialog.ts` and publishes `toDialogView` of it as `dialog`, with the unit art for each line's `unitClass` from `getUnitSprite`. While it shows it owns input: confirm calls `advanceDialog` with the time since the line started (the scene clock), so a line still typing finishes at once and a finished one moves on; cancel skips the rest. The cursor is hidden meanwhile and restored as it was when the dialog closes, then `onDone` runs. `playTriggeredDialog(trigger, onDone)` plays the level's conversation for a trigger, or just runs `onDone` when there's none: `opening` on `create()`, `turn N` once the player phase banner of turn N ends, and `victory` / `defeat` from `checkOutcome` — which sets `battleOutcome` on the scene at once (ending the battle) but only publishes it to the store, showing the result, after the dialog. A Warband stage with a run instead hands the roster units placed at the start of the battle (`deployedUnits`, kept after they fall) to `finishBattle` (`src/game/warband/runCommands.ts`), which, on a win, adds the clear's gold (publishing `toStageClearView` of it as `stageClear`, with the battle's tally, the realm site and the clear's level ups) and marks the reward pick owed; the scene takes its offers (`getRewardOffers`), saves the run (`saveRun`) and moves on to its `runStage`, or, when the run is over, clears the save and publishes `toRunOverView` of it as `runOver`. Otherwise a victory works out the next battle with `getNextBattle` (a fresh `randomSeed()` for a Warband stage) and publishes its `describeBattle` title as `nextBattle`. Confirming a won stage's result opens the reward screen instead: the scene publishes the offers as `rewardMenu` (`toRewardMenuActions`: a card per reward, then Skip and Reroll), arrows move the pick, and confirm gives the run command for a card (`pick-reward`; a lesson reward's `level-ups` event then shows one by one through `showLevelUps`, the same panels a combat's level ups use) or for skipping (`skip-reward`), saves the run again, and once any level ups have shown opens the camp (`openCamp`): the scene keeps the run as `campRun` and publishes `getCampActions` of it as `campMenu` and its gold as `campGold` (`setCampRun`, which also saves the run whenever it changes, republishes both). Rest gives the `rest` run command. Mentors opens the mentor screen the same way (`mentorScreen`, `toMentorScreenView`, `hover-mentor` / `select-mentor`). Merchant opens the merchant screen, whose state (`src/game/warband/merchantScreen.ts`) the scene keeps as `merchantScreen` and publishes as `toMerchantScreenView` of it; arrows, confirm and cancel (and `hover-merchant` / `select-merchant` from the mouse) step it, and cancel returns to the camp. Manage Roster opens the roster screen, whose state (`src/game/warband/rosterScreen.ts`) the scene keeps as `rosterScreen` and publishes as `toRosterScreenView` of it; arrows, confirm and cancel (and `hover-roster` / `select-roster` from the mouse) step it, every change to the run is saved at once, and cancelling from the units column returns to the camp. Next Stage gives `march` and moves on to the run's `runStage` with `leaveBattle`. Reroll (`reroll-rewards`) spends the gold, saves, and republishes the new offers in place. Otherwise confirming the result runs `leaveBattle`: with a next battle it clears the battle state and stores the new `battleSetup`, which makes `main.ts` restart the scene with it (everything is reset in `create()`, and the shared animations and textures are only made once); otherwise it returns to the title. The dialog is checked before the outcome in `update()` so it keeps input until then.

**Preview.** When the store's `screen` is `'preview'` (the config editor's map preview), `create()` builds and draws the level as usual but skips the opening dialog, the Objective screen and deployment, and `update()` hands all input to `updatePreview`: the deployment zone is highlighted, the cursor starts on it and roams (so the unit panel shows whoever it's over, enemies included), confirm on a unit draws how far it reaches — its move range and the tiles it threatens, from `drawUnitReach`, the same highlight a selected unit gets — and confirm again (or on an empty tile) clears it, and cancel clears it or else returns to the title. No units can be placed, moved or ordered, and no turn starts.

**Turns.** The battle's turn state from `src/game/turns.ts` (`this.turnState`) is published as `toTurnView` of it as `turn`. `startPhase` clears every unit's "done" tint, publishes a `phaseBanner` (`toPhaseBannerView`) and locks input for `PHASE_BANNER_DURATION_MS` (a `waitSkippably` wait: confirm cuts it short, as it does the XP bar and level-up panels), then either hands input to the player (cursor on their first unit) or runs the enemy or guest phase. In the player phase, a unit that's done can't be selected; once it has moved the action menu opens at its new tile; cancelling that menu undoes the move (`undoMove` rewinds the history to before it, so the unit snaps back and has its move again, and its move range shows again). **Attack**, **Skill**, **Item**, and **Wait** finish the unit (the battle marks it done, and `refreshDoneTints` greys it out); once every living player unit is done, the battle starts the enemy phase. `runEnemyPhase` takes each unit of the phase's team (the enemies, or the guests) in turn with `planNextTurn` (`src/game/battle/ai.ts`): the cursor jumps to it, it walks its planned path (via the same `walkSprite` as the player), then carries out its act: an attack on its target (the same exchange, so player units counter), a skill, a staff heal, or waiting; the last one hands the phase back. The battle checks its objective (`getObjectiveOutcome`) after every action and as each phase starts (so a survive objective is won when its last turn is over); `continueBattle` runs once a command's events have played, catching the map up and then showing the result (`showOutcome`), the next phase, or carrying on. `startPhase` also publishes the objective's `getObjectiveStatus` as `objectiveStatus`, and a seize objective's tile is marked on the map with a pulsing gold outline (`renderObjectiveTile`). Once the battle is decided it publishes `battleOutcome` (which hides the header's turn readout), hides the cursor, and only confirm is accepted, which returns to the title. A won Warband stage skips that result and opens its recruit or reward pick straight away, ignoring confirm for `REWARD_PICK_GRACE_MS` so a press meant for the battle's end doesn't take a reward.

**Commands.** Every change the scene makes to the battle — placing a unit, starting, moving, equipping, attacking, a skill, a heal, an item, waiting, ending the phase, and every enemy's action — is a `BattleCommand` given with `dispatch`, which records it in `this.history` and returns its events. The map keeps showing `this.shown`, the state from before, while `playEvents` animates the events in order (`shownStats` carries a unit's health or mana as each strike, skill or recovery lands), and `syncShown` catches it up afterwards. Going back is rewinding the history: `undoMove` drops the move (and any equip since) when a unit's menu is cancelled, and the pause menu's Undo drops the last player action with `undoLastAction` — its move and act, along with the enemy phase if one followed — then redraws every unit sprite where the battle now has it.

**Auto playback.** `autoPlay` and `autoSpeed` persist across battles in `gameStore`. Auto chooses the next player move and action before its step timer expires; `GridScene` keeps those pending commands (and each enemy's planned pair), removes them as it dispatches, and publishes their labels as `autoCommandQueue` for the React HUD. The selected speed scales the step timer, scene clock and tweens; published HUD animation durations are divided by the same speed. Turning Auto off clears the visible queue and restores normal playback speed.

### `src/scenes/effects.ts`

Presentation-only sprite effects that never touch game state; each calls `onDone` when finished. `playHitFlash(scene, sprite, onDone)` blinks a sprite solid white a few times on the scene clock. `playStoneThrow(scene, from, to, onDone)` lobs a small grey circle along an arc between two world points, flying longer and higher the farther the throw. `playLunge(scene, sprite, toward, { distance, holdMs, onImpact, onDone })` darts a sprite toward a world point, calls `onImpact` at the far end, holds there for `holdMs` (the hit-stop) and darts back. `playHitStop(scene, struck, others, durationMs, onDone)` freezes the sprites' animations with the struck one solid white, on the scene clock. `playDeathBurst(scene, sprite, center, reducedMotion, onDone)` flashes a defeated unit white and fades it out while sparks fly from it (only the fade with reduced motion). `playPotionGlow(scene, sprite, center, color, onDone)` is the potion effect: sparkles rise from the unit's feet in the given color while the sprite pulses that color — one animation for every potion, colored per stat via `POTION_COLORS`. Particle emitters take the scene clock's time scale, so they speed up with the game too. None need sprite art: the shared particle texture is drawn with `Graphics` and generated at runtime the first time it's used.

Unit art with more than idle and move (`UNIT_ART` in `tileset.ts`) animates combat in `GridScene` itself: `preload` loads its bigger sheets at their own frame size and `pinUnitSheetFrames` pins every frame by the unit's tile (a custom pivot), so the sprite's origin stays on its tile's top-left whatever sheet plays and the art spills over the tiles around it (sprite centers are taken from the tile, not the frame). In `playStrike` such a striker turns to face its target and plays its `attack` once (`playAttackAnimation`, over neighboring units) instead of lunging, the blow landing on its impact frame; a struck unit with `hit` flinches through the hit-stop and flash; a fallen one with `die` plays it before its death burst (`playUnitAnimationOnce`, which also finishes on a timer should the animation be cut short). Art with a baked shadow gets no blob shadow, and its outline leaves the see-through shadow out.

### `src/scenes/hitJuice.ts`

Pure tuning for how hard a blow lands, with no Phaser import so it's unit tested. `getStrikeJuice({ hit, crit, lethal }, reducedMotion)` gives the hit-stop (how long both units freeze on contact: longer on a crit, longer again on a finishing blow) and the camera shake (crits shake hard, a plain finishing blow bumps lightly; never with reduced motion). `getLungeDistance(tiles, reducedMotion)` is how far a striker darts in: a full lunge at an adjacent target, a lean from range, a nudge with reduced motion. Durations are at 1x; the scene clock scales them by the game speed, and `GridScene.shakeCamera` divides the shake by it since the camera runs on real time.

### `src/audio/`

Sound effects (recorded samples in `src/assets/sounds/` where there is one, synthesized otherwise) and synthesized music. `cues.ts`: `getSoundCues(prev, next)` compares two store states and returns the cues to play, without repeats — a new `windupSound` (a bow drawn as its archer starts the attack), each new damage popup by its `sound` if the scene tagged one (a blow's weapon, a potion, a healing spell; a crit adds its ring) else by its kind (hit, crit, miss, heal, coins, break, learn), a rise in `defeats` (defeat), a new XP bar or level up, a new phase banner by team, the battle's outcome, a new dialog line, gold changing at camp (coins), a seal spent on the promotion screen (promote), gear going on or off on the equipment screen (`equip-<gear>` / `unequip-<gear>` from the slot's `sound`), and one menu sound per update (`button` as a menu or camp screen opens or closes, or a tick as a menu's pointer moves). `soundKinds.ts`: the pure `getWeaponSound(weapon)`, `getSkillSound(skill, weapon)` (a strike's `StrikeSound`: sword, axe, bow, hammer, fire, shock, air) `getStrikeSoundTiming(sound)` (whether it plays as the attack starts, like a bow being drawn, or as it lands) and `getGearSound(gear)` (a `GearSound` by weapon or armor weight and slot); the scene tags popups with the first two and `toEquipmentScreenView` tags slots with the last. `samples.ts`: `SAMPLE_URLS`, the recorded sample for each cue that has one, and `AMBIENCE_URLS`. `ambience.ts`: `getAmbience(state)` — `camp` while the camp menu or one of its screens is up. `sfx.ts`: `SOUND_EFFECTS`, each cue as data — a few voices (an oscillator or filtered noise, with a pitch sweep, a start time, a length and a gain), the stand-in for a recorded cue until its sample loads. `player.ts`: `createSoundPlayer(context, destination)` fetches and decodes the samples, plays a cue's sample or else its voices through its own gain (the same cue twice within 60 ms plays once), and loops the ambience with a fade (untested glue). `musicTrack.ts`: `getMusicTrack(state)` picks the music for what's on screen — `title` on the title, `march` on the realm map, `camp` while deploying and from the reward pick through camp, `battle` in the player's (and guests') phase, `enemy` in the enemy's — or silence while a map loads, on a map preview, and once a battle is decided until camp, so the victory or defeat jingle plays alone. `songs.ts`: `SONGS`, each track as data — a tempo, a lead and a bass line written as bars of eighth-note tokens (`"A4"`, `"-"` to hold, `"."` to rest) and optional one-bar kick/snare/hat lanes — with the pure `noteFrequency`, `parseLine`, `parseDrumLane`, `getSongLength` and `getStepSeconds` that read them (a typo in a score fails the tests). `musicPlayer.ts`: `createMusicPlayer(context, destination)` loops a song by scheduling its notes a little ahead on the audio clock, crossfades when the track changes, and stops scheduling while the music volume is 0 (untested glue). `settings.ts`: the player's `AudioSettings` (`muted`, and `volume` and `musicVolume` in 10% steps) with `changeVolume`, `cycleVolume` (both per channel), `toggleMute`, `getChannelGain` (squared, so steps sound even) and guarded `loadAudioSettings` / `saveAudioSettings` for localStorage. `index.ts`: `startAudio()`, called from `main.ts`, loads the settings into the store's `audio`, creates one `AudioContext` with both players on the first click or key press (browsers keep audio silent until one), saves and applies settings changes (with a blip at a new effects volume), plays the cues of every store change, plays `button` on any click on a React button, and keeps the music on `getMusicTrack`'s track and the ambience on `getAmbience`'s. Music is switched off for now by the `music` flag in `src/featureFlags.ts` (`FEATURE_FLAGS`, built features kept off until they're wanted): with it off, no music player is made and the music volume is left out of both settings menus (`getSettingsActions(audio, { music })`). The header's Settings panel and the title's Settings menu change `audio` in the store.

### `src/bridge/store.ts`

`createStore(initialState)` → `{ getState, setState, subscribe }`. A minimal observable store: `setState` takes a partial object or `(state) => partial`, shallow-merges into a **new** state object, and notifies subscribers only if a top-level value actually changed. Its shape matches React's `useSyncExternalStore` contract. Tested in `src/bridge/store.test.ts`.

### `src/bridge/gameStore.ts`

The single app-wide store instance and its initial state shape. `BATTLE_STATE_DEFAULTS` holds the fields that only matter while the map runs; the map scene resets them on start and on exit so nothing leaks between battles. New UI-facing state gets added here as plain, serializable values. `defeats` counts the units fallen this battle, for the defeat sound. `audio` (kept across battles) is the sound settings from `src/audio/settings.ts`. `weaponMenu`, `skillMenu` and `itemMenu` are the open weapon, skill and item menus. `turn` (turn number, team, and phase label), `phaseBanner` (the phase announcement while it's up), and `battleOutcome` (`'victory'` | `'defeat'` | `null`) describe the turn flow. `phase` (`'deployment'` | `'battle'` while the map runs), `deploymentStep`, `deploymentLimit`, `deploymentMenu`, and `rosterMenu` describe the deployment phase. `screen` (`'title'` | `'battle'` | `'overworld'` | `'preview'`) is which top-level screen is showing (`'overworld'` the Warband realm between battles, see `OverworldScreen`) (`'preview'` runs the map read-only, see **Preview** under GridScene), and `battleSetup` (a `BattleSetup` from `battleSetup.ts`: story, training or warband) which battle the map runs; they're the fields React writes (Story Mode, Warband Mode, picking a Training unit, or a region map preview sets both), and `main.ts` reacts by starting the map scene with `battleSetup` as its scene data.

### `src/bridge/commands.ts`

`createCommandChannel()` → `{ send, subscribe }`: the React → Phaser direction of the bridge. React sends plain command objects and the running scene subscribes (unsubscribing when it shuts down). `gameCommands` is the app-wide instance. Commands: `hover-menu` / `select-menu` (`{ menu, index }`, where `menu` is the store field of an open menu), `hover-roster` / `select-roster` (`{ target, index }`, an entry of a roster screen column or of its open item actions), `hover-merchant` / `select-merchant` (`{ column, index }`, an entry of a merchant screen column), `confirm`, and `cancel` — the same inputs the keyboard produces, so the scene handles them through its existing input steps — plus `main-menu`, which leaves the battle for the title screen even while input is locked. ### Routing and the config editor

The page's routes are read from the URL hash so they work from the GitHub Pages subpath without server rewrites: the config editor's index (`#/configs`), one config's page (`#/configs/<id>`), a Warband region's map preview (`#/configs/regions/preview/<index>/<seed>`), and the game (any other hash). `src/ui/route.ts` is the pure `parseRoute(hash)` / `routeHash(route)` pair (tested in `route.test.ts`), and `useRoute()` (`src/ui/useRoute.ts`) re-renders on `hashchange`. The battle layout stays mounted on every route; on the config routes `ConfigEditor` covers it like the title screen does, and ends any running battle when it opens (it sends `main-menu`) so Phaser stops taking keyboard input underneath. The title screen's Settings menu links to it. `ConfigEditor` shows the page `CONFIG_PAGES` has for the route's id, or the index; every page shares the `ConfigLayout` frame (title, lede, back link).

`ConfigsPage` is the editor's index: every piece of authored or tunable data, grouped (Story & Dialog, Maps, Units, Equipment, Rules), each card naming its source files and summarizing what's in it now. The list is `getConfigCatalog()` in `src/ui/configCatalog.ts`, which reads its counts from the live data (dialogs, regions, unit classes, weapons, …); `configCatalog.test.ts` checks that ids are unique and every source path exists. Cards for configs with a page link to it; the rest are marked as coming.

`DialogConfigPage` (`#/configs/dialogs`) takes `.txt` dialog files by picker or drag and drop. `checkDialogUpload` (`src/game/dialogUploads.ts`) accepts a file named after a level's dialog file (`demo.txt`, `training.txt`) whose text parses against the character roster, reporting parse errors with their line number; accepted uploads go to `customDialogStore` and play from the next battle. Each dialog file is listed as built-in or uploaded, with its conversations (in play order, `compareTriggers`) expandable to their lines, a Download button (the upload, or the built-in file as a starting point) and, for uploads, Reset to Built-in. `applyCustomDialogs` merges uploads over the built-in files, and an upload that stops parsing (say, a character was removed) is flagged on the page while the built-in file plays. `dialogUploads.ts` is tested in `dialogUploads.test.ts`.

`RegionsConfigPage` (`#/configs/regions`) edits Warband Mode's regions as a form. It keeps a draft, the settings as plain JSON (`src/ui/regionsDraft.ts`, tested: `getIn` / `setIn` and the list edits `insertAt` / `removeAt` / `moveItem` return new drafts; `checkDraft` runs the draft through `parseRegionSettings`, map test included; `pathLabel` / `isErrorAt` / `isErrorWithin` match the parser's error, which names the field at fault, to a field or a region (an old Dungeon Mode upload's errors, which name `floors`, read the same); `readNumberText` reads a number box, blank clearing the setting; `readableError` rewrites an error's path in the form's words, e.g. "Meadowlands › Enemy group 1 › Max distance is 5, …", for the save bar, region cards and upload notices, and `errorReason` drops the path for the message shown under the field it names). The form is built from `DraftFields.tsx` (number, `[min, max]` / `[from, to]` pair, text, select and checkbox fields, each bound to a draft path and marked invalid when the error names it, with the reason beneath; blank optional fields show the generator's `MAP_GEN_DEFAULTS` as placeholders; a field whose setting has an entry in the form's `help`, which the page fills from `FIELD_HELP` in `src/ui/regionFieldHelp.tsx` (tested to cover every setting on the form), gets an `InfoPopover` beside its label: an "i" button opening a plain-words explanation, with a diagram of an example area for the enemy groups' areas) and `RegionEditor` (one card per region: name, description, map, terrain and enemy groups, with Move Up/Down, Duplicate and Remove, plus Add Enemy Group). The page adds Stages per region and Add Region, and a save bar while there are unsaved changes: the draft's error, Discard, and Save (disabled until the draft parses). Saving goes through `src/data/projectSave.ts`: on the dev server (`CAN_SAVE_TO_PROJECT`, i.e. `import.meta.env.DEV`) `saveConfigToProject` POSTs the file to `vite/saveConfigs.ts`, which writes `src/data/regions.json` (and clears any browser upload, which would hide it); the dev server then reloads the page, and a session-storage message reports the save across the reload. Elsewhere Save keeps the file in this browser with `customRegionsStore`. Leaving the page with unsaved edits asks first. A `.json` file can still be uploaded in place of the regions (checked with `parseRegionSettings` and kept with `customRegionsStore`; the next run uses it); the page shows whether the regions are built-in or uploaded (flagging an upload that no longer parses), with Download (the saved file), Reset to Built-in and New Preview Maps. Each region card shows a map generated from it with the preview seed (the last draft that parsed, while there's an error), drawn a square per tile from `getMapPreview(level)` (`src/ui/mapPreview.ts`, tested: each tile's terrain and one marker for an enemy, building, deployment tile or tree), and each enemy group's summary from `describeEnemyGroup`. For a region that matches what's saved, the thumbnail and a View Full Map button open that same map on the battle stage: `RegionPreview` (the preview route, in place of `ConfigEditor`) sets `screen: 'preview'` and `battleSetup` to `regionPreview(index, seed, getActiveRegionSettings())`, showing `LoadingScreen` while it loads. The header swaps in `RegionPreviewBanner` (the region's name, its stages, and the controls) and `RegionPreviewActions` (New Map, which puts a fresh seed in the route and so restarts the scene, and Back to Regions) for `DeploymentBanner`/`TurnIndicator` and `MainMenuButton`. The running is `MapPreview(setup, exitHash)`: leaving the route ends the preview (setting the store straight to the title, so it ends even mid-load), and the scene ending it (Esc) sends the page to `exitHash`, here the Regions page. The title menu's Map Generator (`src/ui/MapGenerator.tsx`, route `#/map-generator/[<index>/]<seed>`) runs `generatedMap(seed, …, index)` through the same `MapPreview`, with `MapGeneratorBanner` (region, stage and seed) and `MapGeneratorActions` (Main Menu) in the header, and `MapGeneratorPanel` in the HUD's bottom-left corner: a region pick (any, or one of the regions; picking one generates a map there) and Generate, which puts a fresh random seed in the route. Esc goes back to the title. The title menu's Animations (`src/ui/AnimationViewer.tsx`, route `#/animations[/<art>]`, covering the page like the config editor) shows every unit art's animations on a canvas stage of tiles with the unit's tile marked: pick the art, the animation (its `getAllUnitSheets`), a facing or all four, zoom and speed, pause and step frames. Its rules are pure in `src/game/animationViewer.ts` (tested: `getViewerArts`, `getFrameRect`, `getStageRect` sized for every sheet of the art so switching never resizes it, `advancePlayback` looping or holding a one-shot's last frame before replaying, `stepFrame`). Both pages share `UploadDrop` (a drop zone that's also a file picker, with the last upload's results) and `downloadText`.

### `vite/saveConfigs.ts`

The dev server's config save endpoint, a Vite plugin applied only to `vite serve` (so builds and `vite preview` can't write files). `POST /__configs/<id>` with the save header (`SAVE_CONFIG_PATH` and `SAVE_CONFIG_HEADER` in `src/data/configSaveApi.ts`, shared with the editor; the custom header means a page from another site can't send it) saves config `<id>` from `SAVABLE_CONFIGS` (just `regions`, to `src/data/regions.json`): `saveConfig(request, configs, deps)` loads the config's parser and formatter through the dev server (`ssrLoadModule`, so they import as they do in the game), turns away text the parser rejects with its message, and writes the formatted file, laid out by Prettier. `formatRegionSettings` writes what fits on one line on one line and keeps each region's terrain settings in the file's order, so saving an unchanged file leaves it byte for byte the same. Tested in `vite/saveConfigs.test.ts` (with the file system and module loading stubbed) and `src/data/projectSave.test.ts`.

### `src/main.ts`

Composition root. Mounts the React page first, starts the audio (`startAudio`) (which opens on the title screen and provides `#game`), then constructs the single `Phaser.Game` instance in `#game` (RESIZE scale mode, so the canvas matches `#game`'s size) with no scenes running, and keeps `GridScene` in step with `gameStore`: when `screen` leaves `'title'` (for `'battle'` or `'preview'`) it adds and starts the scene with `battleSetup` as scene data, when `battleSetup` changes while it runs (the next battle after a victory, another preview map) it restarts the scene with the new one, and when `screen` goes back to `'title'` it removes the scene (so the next battle starts fresh). It also applies the store's state once at boot, since `mountUI` runs React's effects first and a preview link opened directly has already asked for the map. Phaser and React are started independently here and only communicate through `src/bridge/`. Should stay free of game logic.

### `src/assets/` sprites

Structures and decorations (the paifang gate, green and gold ginkgos) are standalone images in `src/assets/`, also listed in `sprites.ts`. Item icons live in `src/assets/items/` (the wooden sword, spear, axe, shield and armor so far), one 32x32 image each. Unit sprite sheets live in `src/assets/units/`, loaded by an `import.meta.glob` in `sprites.ts` (the ships left out): the pack's 16 units with six versions each, cataloged in `.claude/skills/tileset/units-catalog.md`. Each version is a faction (`factions.ts`): a faction unit's art is `FACTION_BODIES[class]` plus its faction's variant (`getUnitSprite(unitClass, faction)` in `tileset.ts`, e.g. `Soldier_02` for a sunward soldier), and the faction-free classes use `UNIT_SPRITES` (`Elemental_01`–`_04` for the elementals). Pack sheets are `_Idle` / `_Move`, 4x4 grids of 32x32 frames. The monsters (`Slime`, `Goblin`, `Skeleton`, `Bat`, `Orc`) have their own `{Name}_{Idle,Move,Attack,AttackBody,AttackEffect,Hit,Die}.png` sheets and the dragon `Red_Dragon`, all laid out in `UNIT_ART` (the orc's frames are 48px tall). Wired up through `sprites.ts`; rows are down, left, right, up (`UNIT_SHEET.rows` in `tileset.ts`). Units start out idling on the down row (so does the deployment roster), play the move sheet facing each step while walking, and idle facing their last step after they stop.
