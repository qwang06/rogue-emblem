# ARCHITECTURES.md

Living documentation of how Rogue Emblem is structured. This tracks the *shape* of the system — modules, their responsibilities, and how they connect — not implementation detail that's better read from the code itself.

## Stack

- [Phaser 3](https://phaser.io/) for the game world: tilemap, sprites, animations, camera, map input, and the game loop.
- [React](https://react.dev/) for UI and the page around the game: the header, sidebar, HUD panels, menus, dialogs — anything that's DOM-shaped rather than world-shaped. React renders the whole page, including the box the Phaser canvas mounts into and a DOM overlay on top of it.
- [Vite](https://vitejs.dev/) for dev server (hot reload) and production bundling.
- [Vitest](https://vitest.dev/) for unit tests.
- [GitHub Actions](https://docs.github.com/actions) (`.github/workflows/deploy.yml`) runs the tests, builds, and deploys to GitHub Pages on every push to `main`. Vite builds with a relative `base` so the game works from the Pages subpath.

## Layering

The codebase is split into layers that don't reach into each other's internals:

- **Pure game logic** (`src/game/`) — plain JS functions and data, no Phaser imports, no rendering, no hidden state. Every rule of the game (grid layout, movement, combat, turn order, etc.) belongs here so it can be unit tested without spinning up a `Phaser.Game`.
- **Phaser presentation** (`src/scenes/`) — Scenes are the thin glue layer. They call into `src/game/` for state and rules, then use Phaser APIs to draw the result and handle input. Game rules should never be implemented inline in a scene.
- **Bridge** (`src/bridge/`) — framework-agnostic store that Phaser writes to and React reads from. Neither Phaser nor React imports the other; this is the only point of contact.
- **React UI** (`src/ui/`) — components that render UI state from the bridge store. No game rules here either; components display snapshots and send player input (mouse clicks on menus, right-click cancel) back as commands through the bridge.

```
 src/game/  ◄── scenes call rules
     ▲
     │
 src/scenes/ ──setState(snapshot)──► src/bridge/gameStore ──useSyncExternalStore──► src/ui/
  (Phaser)                            (plain JS store)                              (React)
     ▲                                                                                 │
     └──────────────────── src/bridge/commands (send / subscribe) ◄────────────────────┘
```

```
src/
  game/       pure logic + data (tested with Vitest, no Phaser dependency)
  scenes/     Phaser.Scene subclasses (rendering + input, calls into src/game/)
  bridge/     Phaser → React state store, React → Phaser command channel (plain JS, tested with Vitest)
  ui/         React components: the page layout, sidebar, and HUD overlay
  assets/     art/tileset source files
  main.js     composition root — builds Phaser.Game, mounts the React UI
```

## Modules

### `src/game/grid.js`
Pure grid data structure for the tactics board. Grid state is `{ width, height, cells }`, cells stored row-major, each cell `{ x, y, terrain, unitId }`. All mutator-shaped functions (`setTerrain`, `setUnit`) return a **new** grid rather than mutating the input.

Key functions: `createGrid`, `isInBounds`, `getCell`, `setTerrain`, `setUnit`, `moveUnit` (relocates a unit id, throwing if the source is empty or the target occupied), `findUnit` (where a unit id stands, or `null`), `getCornerTiles` (the first/last N tiles in reading order from the top-left/bottom-right corner), `getNeighbors` (orthogonal only — no diagonal movement), `gridToWorld` / `worldToGrid` (grid coordinates ↔ pixel coordinates).

Tested in `src/game/grid.test.js`.

### `src/game/terrainMap.js`
`parseTerrainMap(rows, legend)` builds a grid from a text layout — one string per row, one character per tile — so maps can be written as data that looks like the map. `DEFAULT_TERRAIN_LEGEND` maps `.` to grass, `~` to water, `,` to dirt and `#` to wall. Throws on an empty map, ragged rows, or a character the legend doesn't define. Tested in `src/game/terrainMap.test.js`.

### `src/game/tileset.js`
Names the art each piece of the map draws with, so scenes reference terrain/units/UI elements by name instead of magic frame numbers or file names. `TILE_SIZE` (32px) is the map tile, matching the overworld terrain sheet; `TERRAIN_SHEET` names that sheet's texture and size, `TERRAIN_BASE_TILE` the grass tile under every cell, and `TERRAIN_AUTOTILES` each autotiled terrain's source tiles and animation (see `autotile.js`). `CURSOR_ANIMATION` lists the two sheet tiles the cursor pulses between and how long each shows, and `ARROW_TILES` the sheet tile for each `moveArrow.js` piece. `UNIT_SPRITES` (keyed by team, so each side looks alike) names each side's unit art, whose sheets (one per animation in `UNIT_ANIMATIONS`, keyed by `unitSheetKey`) are standalone images listed in `src/assets/sprites.js`; `UNIT_SHEET` says how those sheets are cut (a row per facing), and `UNIT_SHADOW` sets the size, placement, and opacity of the blob shadow under units. Tested in `src/game/tileset.test.js` (every unit animation has an image; cursor and arrow tiles are on the sheet).

### `src/game/pixelShapes.js`
Pure pixel-art rasterizing. `getEllipseSpans(width, height)` returns the rows of pixels an ellipse covers as `[{ y, x, width }]` spans, so scenes can draw crisp shapes with rectangles instead of anti-aliased curves. Tested in `src/game/pixelShapes.test.js`.

### `src/assets/sprites.js`
`SPRITE_URLS`: texture key → imported URL for every standalone sprite image (units). The only module that imports sprite files — GridScene preloads each under its key, and the React `UnitSprite` shows one by key.

### `src/game/autotile.js`
Blob autotiling: a terrain is drawn in its own cells, with its border inside the edge cells, over a grass base. Each cell is drawn as four quarter tiles. `getQuarterShapes(grid, x, y, terrain)` names each quarter's shape from its two side neighbors and the diagonal between them (`'outer'`, `'horizontal'`, `'vertical'`, `'inner'`, `'full'`), which covers all 47 neighbor combinations. Cells off the map take the nearest cell on it, so terrain reads as continuing past the edge. `getShapeTile` picks the sheet tile (from the set's plain 3x3 `block` or its `inner` corner tile) whose same quarter draws that shape. `getQuarterFrames` returns the four frame numbers on the sheet cut into half-size tiles, shifted along the sheet for an animation frame. `getTileFrame` numbers whole tiles. Tested in `src/game/autotile.test.js`.
### `src/game/cursor.js`
Pure logic for the map cursor: a `{ x, y }` grid position. `moveCursor` takes a delta and clamps the result to the grid bounds; it never mutates the cursor it's given. Tested in `src/game/cursor.test.js`.

### `src/game/actionMenu.js`
Pure state for the unit action menu. `UNIT_ACTIONS` lists the offered actions (Attack, Skill, Item, Wait — moving happens before the menu opens) as `{ id, label }`; `getUnitActions({ hasSkills, hasItems })` returns them for a particular unit, with Skill marked `disabled` until the unit knows a skill and Item when it carries nothing; a menu is a frozen `{ actions, selectedIndex }`. `moveSelection` moves the highlight with wrap-around and returns a new menu (or the same one if nothing changed); `selectIndex` jumps straight to an index (ignoring out-of-range ones); `getSelectedAction` reads the highlighted action. The helpers work on any action list, so other menus (e.g. the title menu) reuse them. The module only tracks selection — carrying out an action belongs to whoever consumes the choice. Tested in `src/game/actionMenu.test.js`.

### `src/game/titleMenu.js`
`TITLE_ACTIONS` — the title screen's menu entries (Play, Training, Settings) as frozen `{ id, label }`. Selection uses the `actionMenu.js` helpers. Tested in `src/game/titleMenu.test.js`.

### `src/game/deployment.js`
Pure rules for the **deployment phase** — the pre-battle step where the player places units from their roster onto a deployment zone (a list of `{ x, y }` tiles). `getDeploymentActions({ canStart })` builds the Place Units / Start menu entries (Start carries `disabled` until a unit is placed). `canPlaceUnit` accepts zone tiles that are empty or already hold that unit; `placeUnit` puts a unit there, lifting it off its previous tile (throws on an invalid tile). `isPlaced`, `canStartBattle(grid, roster)` (at least one roster unit on the map), and `getFirstOpenTile(grid, zone)` round it out. Tested in `src/game/deployment.test.js`.

### `src/game/dialog.js`
Pure state for conversations. A script is a list of lines `{ speaker, team, side, text }` (`team` picks the unit art standing in for a portrait until there is portrait art; `side` is `'left'` | `'right'`, where the portrait sits). `createDialog(lines)` starts a frozen `{ lines, index, revealed }` (throws on an empty script, a line without text, or an unknown side). Text types out at `DIALOG_CHARS_PER_SECOND`: `getRevealDurationMs` is how long a line takes and `getRevealedLength` how much shows after a given time. `advanceDialog(dialog, elapsedMs)` is what confirm does — finish typing a line that's still typing, else move to the next line, or return `null` after the last. Tested in `src/game/dialog.test.js`.

### `src/game/demoLevel.js`
`createDemoLevel()` builds the starting state of the demo battle (Level 1) as `{ grid, units, roster, deploymentZone, openingDialog, decorations, structures }`: the terrain comes from `DEMO_MAP` (a text layout parsed by `terrainMap.js`, 16x14 tiles) — a grass field with a one-tile dirt path running north from the south edge to a paifang gate. The gate is a `structures` entry (`STRUCTURE_POSITIONS`, `{ x, y, structure }` by top-left tile, drawn from `STRUCTURE_SPRITES` in `tileset.js`); every tile under it is walkable (the path down its middle, grass under its sides). `decorations` (`TREE_POSITIONS`) puts a stand of gold ginkgos right behind the gate and three clumps of green ginkgos in the field. Three enemy `Soldier`s hold the gate at `ENEMY_POSITIONS`, the player's roster (three named `Soldier`s from `PLAYER_ROSTER`) is kept off the map, and `DEPLOYMENT_ZONE` (the south end of the path) is where they're placed. `openingDialog` is `DEMO_OPENING_DIALOG`, the roster and an enemy soldier talking before deployment. `units` is the `unitId -> Unit` registry for both sides. Stand-in until levels are loaded from data. Tested in `src/game/demoLevel.test.js`.

### `src/game/unitClasses.js`
`UNIT_CLASSES` — the unit classes the game can build, in menu order, as frozen `{ id, label, create(options) }` (only the soldier so far). `createUnitOfClass(classId, options)` builds a fresh `Unit` of a class by id (throws on an unknown one), so code that offers a choice of class doesn't import the subclasses. Tested in `src/game/unitClasses.test.js`.

### `src/game/trainingLevel.js`
The Training mode's practice battle. `getTrainingActions()` lists one `{ id, label }` menu entry per unit class. `createTrainingLevel(unitClass)` returns the same `{ grid, units, roster, deploymentZone }` shape as `createDemoLevel`: a 3x3 grass field (`TRAINING_MAP`) with the chosen class on the player team at `TRAINEE_POSITION` (west edge) and a "Sparring Partner" of the same class on the enemy team at `SPARRING_PARTNER_POSITION` (east edge). Both start on the map, so the roster and deployment zone are empty; `openingDialog` (`TRAINING_OPENING_DIALOG`) is the sparring partner's greeting. Tested in `src/game/trainingLevel.test.js`.

### `src/game/camera.js`
`getFitZoom(mapSize, tileSize, canvasSize, maxZoom)` — the largest whole-number zoom at which the map fits the canvas, capped at `maxZoom` and never below 1. GridScene caps it at 2x, which every map up to 30x22 tiles reaches; only larger maps zoom out further. Tested in `src/game/camera.test.js`.

### `src/game/pauseMenu.js`
`PAUSE_ACTIONS` — the pause menu's entries (End Turn, Main Menu, Settings) as frozen `{ id, label }`. Selection uses the `actionMenu.js` helpers. Tested in `src/game/pauseMenu.test.js`.

### `src/game/structures.js`
`getStructureTiles(sprite, x, y)` lays out a multi-tile structure (a `STRUCTURE_SPRITES` entry) placed by its top-left tile: one `{ x, y, frame, overUnits }` per tile in reading order, `frame` being the piece of the image cut into one-tile frames and `overUnits` true for its top `roofRows` rows. Tested in `src/game/structures.test.js`.

### `src/game/movement.js`
Pure movement rules. `TERRAIN_MOVE_COSTS` maps terrain to the movement points spent entering it (`Infinity` = impassable; unlisted terrain costs 1). `getMovementRange(grid, origin, movement, { terrainCosts, canPassThrough })` runs Dijkstra over orthogonal neighbors and returns every reachable destination as `[{ x, y, cost }]`, including the origin at cost 0. Other units block unless `canPassThrough(unitId)` allows them, and occupied tiles are never destinations. `getMovePath(grid, origin, destination, movement, options)` uses the same search to return the cheapest route as a list of orthogonally adjacent tiles from origin to destination (one entry per step), or `null` if the destination isn't in range — so the range and the path can never disagree. `extendMovePath(grid, path, target, movement, options)` updates a planned route as the cursor moves: it cuts back to a tile already on the path, appends an adjacent step while the traced route stays within movement, and otherwise falls back to `getMovePath` (leaving the path unchanged if the target is unreachable), so the route follows the way the player traced it. `getPathCost` sums the cost of the tiles a path enters. Tested in `src/game/movement.test.js`.

### `src/game/turns.js`
Pure turn rules. A battle alternates phases in `PHASE_ORDER` (player, then enemy); the pair makes one turn. Turn state is a frozen `{ turn, team, moved, done }` from `createTurnState(turn, team)`: `moved` / `done` list the unitIds that have moved or finished this phase. `markMoved`, `unmarkMoved` (takes a move back, unless the unit is already done), and `markDone` (which also counts as moved) return new states; `hasMoved` / `isDone` read them; `isPhaseOver(state, unitIds)` is true once every one of the phase team's units in play is done (trivially true for none); `nextPhase` advances player → enemy (same turn) → player (next turn) with a clean slate. `getBattleOutcome(units)` returns `'victory'` when no enemy is alive, `'defeat'` when no player unit is (defeat wins a tie), else `null`. Tested in `src/game/turns.test.js`.

### `src/game/enemyAI.js`
Pure enemy decision-making. `planRushAction(grid, origin, unit, isHostile, movementOptions)` returns `{ path, target }` for one enemy: if any tile in its movement range lets it attack a hostile unit, it takes the cheapest such tile (so an enemy already adjacent stays put) and targets that unit; otherwise it finds the nearest tile it could attack from by walking distance (ignoring its movement limit, respecting terrain and blockers), follows the route there, and stops at the furthest tile it can reach and stand on this phase (allies can be walked through, not stopped on). With no reachable hostile it stays put (`path: [origin]`, `target: null`). Built on `movement.js` and `combat.js`. Tested in `src/game/enemyAI.test.js`.

### `src/game/moveArrow.js`
Pure logic for the movement arrow. `getArrowPieces(path)` returns `[{ x, y, piece }]` for every tile of a route after the origin: an arrowhead (`head-up`/`down`/`left`/`right`) on the last tile pointing the way it last stepped, and on the tiles before it a straight segment or corner named for the two tile edges it joins (`up-down`, `left-right`, `up-left`, `down-right`, …). `ARROW_TILES` in `tileset.js` maps each piece name to its tile on the terrain sheet. Tested in `src/game/moveArrow.test.js`.

### `src/game/keyRepeat.js`
Pure key repeat for the arrow keys. `updateKeyRepeat(state, { isDown, justPressed }, deltaMs, timing)` advances one frame and returns `{ state, step }`, `step` being a `DIRECTIONS` entry or null: a press steps at once (even a tap shorter than a frame), holding repeats after `KEY_REPEAT.delayMs` and then every `intervalMs`, at most one step per frame. The most recently pressed key still held sets the direction, so the cursor never moves diagonally; letting go of it hands back to the older key after the delay. `GridScene.readArrowKeys` feeds it Phaser's key states each frame, so holding an arrow moves the cursor and menu highlights continuously. Tested in `src/game/keyRepeat.test.js`.

### `src/game/facing.js`
Pure logic for which way a unit faces (`'down'`, `'left'`, `'right'`, `'up'`, the rows of a unit sheet). `getStepFacing(from, to)` names a step's direction (null for a step in place), and `getPathFacings(path, initial)` gives the facing for each step of a route, which `GridScene.walkSprite` plays as the unit walks. Tested in `src/game/facing.test.js`.

### `src/game/combat.js`
Pure combat rules. `getAttackRange(grid, origin, maxRange, minRange = 1)` returns every in-bounds tile within that orthogonal distance band as `[{ x, y }]` — never the attacker's own tile, and not blocked by terrain or units. `getAttackTargets(grid, origin, maxRange, isHostile, minRange)` narrows that to occupied tiles whose unit `isHostile(unitId)` accepts, as `[{ x, y, unitId }]`. `getThreatRange(grid, stops, maxRange, minRange)` is the fringe of tiles a unit could strike after moving: every tile in attack range of any of `stops` (its movement range), minus the stops, without duplicates. `DAMAGE_TYPES` maps each damage type to the attacker stat that powers it and the defender stat that guards it (`physical`: `strength` vs `defense`; `magical`: `magic` vs `resistance`), `getDamageType(attacker)` reads the unit's `damageType` (default `'physical'`, throws on unknown types), and `calculateDamage(attacker, defender)` is power minus guard for that type, floored at 0. `isInStrikeRange(unit, distance)` checks a distance against a unit's `range` (and optional `minRange`, default 1). `getStrikeOrder(attacker, defender, distance)` lists who strikes, in order, as `'attacker'`/`'defender'`: the attacker, the defender if the attacker is within its strike range, then whoever doubles (`canDouble`; the attacker takes precedence, and a defender that can't reach never doubles). `resolveCombat(attacker, defender, { distance, rng = Math.random, trueHit = false })` plays that order without mutating anything: each strike rolls to hit against `getHitChance` and, if it lands, to crit against `getCritChance` (×`CRIT_MULTIPLIER`); a miss deals 0, and the exchange stops as soon as someone dies. It returns `{ strikes, attackerHealth, defenderHealth }`, where `strikes` is the ordered `[{ by, target, damage, hit, crit, lethal }]`. The RNG is injected so tests are deterministic. Applying damage is left to the caller (`Unit.takeDamage`). Tested in `src/game/combat.test.js`.

### `src/game/combatStats.js`
Pure Fire Emblem–style combat formulas, all whole percentages. `getHit(unit)` = `BASE_HIT` (80, a stand-in for weapon hit until weapons exist) + `skill × 2` + `luck / 2`; `getAvoid(unit)` = `speed × 2 + luck`; `getCrit(unit)` = `skill / 2`; `getDodge(unit)` = `luck` (halves round down, missing stats count as 0). `getHitChance(attacker, defender)` and `getCritChance(attacker, defender)` are rate minus the opponent's avoid/dodge, clamped to 0–100. `canDouble(unit, opponent)` is true when the unit's speed beats the opponent's by at least `DOUBLE_THRESHOLD` (4). `rollChance(chance, rng, { trueHit })` rolls 0–99 from the injected `rng` and succeeds under `chance`; with `trueHit` it averages two rolls (FE's "2RN"). Tested in `src/game/combatStats.test.js`.

### `src/game/Unit.js`
Base `Unit` class that specific unit types extend. Holds stats (`name`, `unitClass`, `level` (default 1), `health`/`maxHealth`, `mana`/`maxMana` (default 0), `strength`, `magic`, `skill`, `speed`, `luck`, `defense`, `resistance` (all but `strength` and `defense` default to 0), `movement`, `range`, `damageType` (default `'physical'`), `team`) and an `items` inventory (from `items.js`, empty by default), plus the state changes every unit shares: `isAlive()`, `takeDamage(amount)`, `heal(amount)` (both clamp health between `0` and `maxHealth`), `spendMana(amount)` (throws if the unit can't afford it), `restoreMana(amount)` (clamped to `maxMana`), `useItem(itemId)` (restores the item's stat, uses one up, and returns `{ item, amount }` with the amount actually restored; throws if the item isn't carried), and `levelUp()`. No Phaser dependency — subclasses set their class and stat line. Tested in `src/game/Unit.test.js`.

### `src/game/Soldier.js`
`Soldier` — the basic infantry `Unit` subclass: `unitClass: 'soldier'`, starts at level 1 with the `SOLDIER_STATS` line (10 HP, 5 MP, 4 STR, 0 MAG, 3 SKL, 3 SPD, 2 LCK, 2 DEF, 0 RES, 5 MOV). Carries `STARTING_ITEMS` (a health potion and a mana potion) unless given other `items`. Takes an optional `name` (e.g. "Enemy Soldier") and `level`. Tested in `src/game/Soldier.test.js`.

### `src/game/skills.js`
Pure skill rules. A skill is `{ id, label, manaCost, range, power, animation }` (`animation` names the effect the scene plays). `SKILL_TREES` maps each unit class to `[{ level, skill }]`, so every class has its own skills and a unit knows each one whose level it has reached — skills are gained by leveling up rather than stored on the unit. `getLearnedSkills(unitClass, level, trees)` lists the known skills in tree order, `getSkillsLearnedBetween(unitClass, fromLevel, toLevel, trees)` the ones a level up unlocks, `findLearnedSkill(unitClass, level, skillId, trees)` looks one up by id, `calculateSkillDamage(skill, defender)` is the skill's `power - defense` (floored at 0, independent of the user's attack), `canUseSkill(unit, skill)` checks mana, and `getSkillActions(unit, skills)` builds skill menu entries (`{ id, label, manaCost, disabled }`, disabled when unaffordable). The soldier learns `THROW_GRENADE` (3 mana, range 2, power 6) at level 1. Tested in `src/game/skills.test.js`.

### `src/game/items.js`
Pure rules for consumable items. An item is `{ id, label, stat, amount }` — `stat` is what it restores (`'health'` or `'mana'`), `amount` the most it restores per use; `HEALTH_POTION` (+5 HP) and `MANA_POTION` (+3 MP) exist so far, and `STARTING_ITEMS` gives one of each. An inventory is a frozen list of `{ item, quantity }` entries: `createInventory(entries)` builds one (dropping empty entries), `findItem` looks one up by id, and `removeItem` returns a new inventory with one used up (dropping an entry that runs out; throws if the item isn't there). `getItemRecovery(unit, item)` is what the item would actually restore — its amount capped by how far the stat is below its maximum — `canUseItem` is whether that's above 0, and `getItemActions(unit, inventory)` builds item menu entries (`{ id, label, quantity, disabled }`, disabled when the item would restore nothing). Tested in `src/game/items.test.js`.

### `src/scenes/GridScene.js`
The Phaser scene that renders a grid. Loads the terrain tileset and every sprite image in `SPRITE_URLS`, gets the starting grid, unit registry, roster, and deployment zone from a level — `createTrainingLevel(unitClass)` when its scene data (the store's `battleSetup`) is `{ mode: 'training', unitClass }`, else `createDemoLevel` — converts it into Phaser tilemaps for terrain (a 32px grass layer, then one 16px quarter-tile layer per autotiled terrain from `autotile.js`, with animated sets such as water stepped through their frames on a timer), draws the level's trees and multi-tile structures (each structure drawn tile by tile from `getStructureTiles`: its roof rows over units, so they pass behind the roof, but under the cursor; the rest under units) over the terrain, and places sprites for occupied cells using `gridToWorld` for positioning. Each unit gets a blob shadow from `addUnitShadow` (`src/scenes/unitShadow.js`): a translucent pixel ellipse (`UNIT_SHADOW` in `tileset.js`, rasterized by `pixelShapes.js`) under its feet, since the unit sprites have none. The shadow follows its sprite every frame and is destroyed with it. Unit sprites are drawn by `addTileSprite`, stretched to fill one 32px tile. The terrain sheet is loaded as a 32px spritesheet, so the cursor sprite loops `CURSOR_ANIMATION`'s two tiles from it and each movement-arrow piece is a sprite of its `ARROW_TILES` frame. Also renders that cursor sprite and moves it one tile per keypress by calling `src/game/cursor.js` from `update()` and re-rendering the sprite at the new position — the scene holds no movement rules itself. The canvas is as big as the stage the page gives it (see `src/ui/` and `main.js`), and `fitCamera` zooms the map with `getFitZoom` — capped at 2x (the 16x14 demo map is 512x448 at 1x, so it reaches 2x on a stage of 1024x896 or more) — and centers it; it runs again whenever the canvas is resized. `pixelArt: true` (set in `main.js`) keeps the pixel art crisp when scaled.

Occupied cells are backed by `src/game/Unit.js` instances held in a `unitId -> Unit` registry (`this.units`) built alongside the grid; `cell.unitId` stays a plain string so grid data remains Phaser-free, and the registry is where actual stats/behavior live. Each frame, `updateHoveredUnit()` looks up the unit (if any) under the cursor and, only when it changes, publishes `toUnitView(unit)` (or `null`) to `gameStore` as `hoveredUnit`. GridScene has no knowledge of React — it only writes plain state.

On `create()` the scene resets the battle-related store fields, plays the level's `openingDialog` if it has one (see **Dialog** below), and then starts in the **deployment phase** (`phase: 'deployment'`) — or, when the level has no deployment zone (training), goes straight to the battle. The deployment zone is highlighted and the map cursor is hidden while a deployment menu has input (a hidden cursor hovers nothing, so the unit panel clears too). Input runs through three steps (published as `deploymentStep`): `'menu'` — the Place Units / Start menu (`deploymentMenu`); `'roster'` — the roster menu (`rosterMenu`, entries from `toRosterEntryView`) to pick a unit; `'placing'` — the cursor roams and confirm on a tile `canPlaceUnit` accepts calls `placeUnit` and draws (or moves) the unit's sprite, then returns to the menu with Start highlighted. Cancel steps back (placing → roster → menu). The cursor only shows during `'placing'`. Start is ignored while disabled; once chosen it clears the zone, drops roster units that weren't placed from the registry (they sit the battle out), sets `phase: 'battle'`, and starts turn 1 (see **Turns** below). All menus are mirrored to the store through `publishMenu(key, menu)`.

In the battle phase, pressing cancel on the bare map (no menu open, no range shown) opens the **pause menu** (`pauseMenu`, from `PAUSE_ACTIONS`), which owns input while open: cancel closes it, End Turn ends the player phase early (units that haven't acted forfeit their action) and starts the enemy phase, Main Menu resets the battle store fields and sets `screen: 'title'` (which makes `main.js` remove the scene), and Settings is a placeholder.

Pressing confirm (Enter/Z) while hovering a ready player unit selects it (`activeUnit`, the unit and its tile) and goes straight to moving: the tiles from `getMovementRange` are drawn as translucent blue overlays (allies pass through, anyone else blocks), ringed in red by the tiles it could attack from there (`getThreatRange`). While the range is shown the cursor moves freely; cancel clears it and lets go of the unit, and as the cursor moves the scene keeps a planned route with `extendMovePath` and draws it as an arrow from `getArrowPieces` (sprites above the range overlay, below units); confirm on an in-range tile at the end of that route walks the unit's sprite along it (`walkSprite`: a chain of linear tweens, one per tile, playing the move animation facing each step), ignoring input until it arrives, then commits the move to the grid with `moveUnit` (confirming the unit's own tile keeps it in place) and opens the action menu beside it: GridScene creates it with `src/game/actionMenu.js` and publishes it to `gameStore` as `actionMenu`. While it's open the menu owns input — up/down call `moveSelection`, confirm reads `getSelectedAction`, and cancel takes the move back and shows the move range again. Sprites are kept in a `unitId -> sprite` map (`this.unitSprites`) so moves can find them. Choosing **Attack** works the same way but draws the tiles from `getAttackRange` in red; confirm only accepts a tile holding a hostile unit (any other team) from `getAttackTargets`. `resolveAttack` gets the exchange from `resolveCombat` and plays its strikes in order with input locked: each struck unit takes the strike's damage right away (the hovered-unit snapshot is republished so the HUD updates), its sprite plays the hit flash from `src/scenes/effects.js`, and a damage popup is published to `gameStore` (see below); a unit at 0 health is removed from the grid, the registry, and the sprite map once its flash ends, which also ends the exchange. So the defender counterattacks when it can reach, a faster unit strikes a second time, and a counter can kill the attacker. A missed strike shows a "Miss" popup and pauses briefly instead of flashing; a crit shows a "Crit!" popup and shakes the camera. Move/attack share one range overlay (`rangeMode` + `rangeTiles`).

Damage numbers are drawn by React, not Phaser: `showDamagePopup` converts the hit sprite's top center to canvas pixels with `worldToScreen` (using the camera's `worldView` and zoom), then to fractions of the canvas with `toCanvasFraction` (so the popup lands on the unit however large the canvas is displayed), appends a `toDamagePopupView` snapshot to `gameStore.damagePopups`, and removes it after `DAMAGE_POPUP_DURATION_MS`. The same duration travels in the snapshot so React's CSS animation and the entry's lifetime agree. The same popups show crits, misses, and recovery: `showDamagePopup(sprite, amount, kind)` with `kind` `'crit'`, `'miss'`, `'health'`, or `'mana'`.

The action menu is built per unit with `getUnitActions`, so **Skill** is greyed out (and confirm ignores it) until the unit has learned a skill from its class's tree. Choosing it replaces the action menu with the **skill menu** (`skillMenu`, from `getSkillActions`), which owns input while open: cancel returns to the action menu, and confirm on an affordable skill shows its range (`getAttackRange` with the skill's `range`) in orange as `rangeMode: 'skill'`, remembering the skill as `activeSkill`. Cancel while aiming goes back to the skill menu; confirm on a hostile unit in range spends the mana, applies `calculateSkillDamage`, and plays the grenade animation from `effects.js` (lob, then fire burst) before publishing the new health and damage popup and removing a defeated unit.

**Item** is greyed out while the unit carries nothing. Choosing it opens the **item menu** (`itemMenu`, from `getItemActions`), which works like the skill menu: cancel returns to the action menu, and confirm on an item that would restore something calls `unit.useItem` right away (the HUD shows the new HP/MP), publishes a `+N HP` / `+N MP` popup, and plays `playPotionGlow` from `effects.js` in the stat's color from `POTION_COLORS` (green for health, blue for mana). Items target the user, so there's no range to aim, and using one finishes the unit.

**Mouse.** The mouse feeds the same confirm / cancel as the keyboard. A queued `main-menu` command (the header's Main Menu button) is checked before the input lock and calls `exitToTitle` at once, so it works mid-animation, during a dialog, or in the enemy phase; removing the scene stops whatever was playing out. Phaser pointer events on the map (`hover-tile` / `click-tile`, converted with `worldToGrid`) and commands from `gameCommands` are queued as they arrive and drained at the top of `update()` (`drainPointerInput`), so they respect `inputLocked` like keys. While no menu has input (`canRoamCursor`: bare map, aiming a range, placing a unit) the cursor follows the pointer — extending the move arrow in move mode — and a left click moves the cursor there and confirms; hovering or clicking a React menu entry highlights / picks it; right click anywhere on the stage cancels (which on the bare map opens the pause menu); a click once the battle is decided returns to the title.

**Dialog.** `playDialog(lines, onDone)` hides the cursor and shows a conversation: the scene keeps a `dialog` from `src/game/dialog.js` and publishes `toDialogView` of it as `dialog`, with the unit art for each line's `team` from `UNIT_SPRITES`. While it shows it owns input: confirm calls `advanceDialog` with the time since the line started (the scene clock), so a line still typing finishes at once and a finished one moves on; cancel skips the rest. When it closes, `onDone` runs.

**Turns.** GridScene keeps a turn state from `src/game/turns.js` (`this.turnState`) and publishes `toTurnView` of it as `turn`. `startPhase` clears every unit's "done" tint, publishes a `phaseBanner` (`toPhaseBannerView`) and locks input for `PHASE_BANNER_DURATION_MS`, then either hands input to the player (cursor on their first unit) or runs the enemy phase. In the player phase, a unit that's done can't be selected; once it has moved the unit is `markMoved` and the action menu opens at its new tile; cancelling that menu undoes the move (the unit snaps back to where it started, `unmarkMoved` gives the move back, and its move range shows again). **Attack**, **Skill**, **Item**, and **Wait** finish the unit (`finishPlayerAction` → `markDone`, sprite tinted grey); once `isPhaseOver` for the living player units, the enemy phase starts. `runEnemyPhase` takes each enemy in turn: the cursor jumps to it, it follows `planRushAction`'s path (via the same `walkSprite` as the player), commits the move, attacks its target if it has one through the shared `resolveAttack` (the same exchange, so player units counter), and is greyed out; then the next phase begins. After every action `checkOutcome` runs `getBattleOutcome`; once the battle is decided it publishes `battleOutcome`, hides the cursor, and only confirm is accepted, which returns to the title.

### `src/scenes/effects.js`
Presentation-only sprite effects that never touch game state; each calls `onDone` when finished. `playHitFlash(scene, sprite, onDone)` blinks a sprite solid white a few times on the scene clock. `playGrenadeThrow(scene, from, to, onDone)` lobs a drawn circle along an arc between two world points. `playFireBurst(scene, sprite, center, onDone)` explodes a particle burst tinted yellow → orange → red that drifts upward, while the sprite flickers orange. `playPotionGlow(scene, sprite, center, color, onDone)` is the potion effect: sparkles rise from the unit's feet in the given color while the sprite pulses that color — one animation for every potion, colored per stat via `POTION_COLORS`. None need sprite art: the shared particle texture is drawn with `Graphics` and generated at runtime the first time it's used.

### `src/bridge/store.js`
`createStore(initialState)` → `{ getState, setState, subscribe }`. A minimal observable store: `setState` takes a partial object or `(state) => partial`, shallow-merges into a **new** state object, and notifies subscribers only if a top-level value actually changed. Its shape matches React's `useSyncExternalStore` contract. Tested in `src/bridge/store.test.js`.

### `src/bridge/gameStore.js`
The single app-wide store instance and its initial state shape. `BATTLE_STATE_DEFAULTS` holds the fields that only matter while the map runs; the map scene resets them on start and on exit so nothing leaks between battles. New UI-facing state gets added here as plain, serializable values. `skillMenu` and `itemMenu` are the open skill and item menus. `turn` (turn number, team, and phase label), `phaseBanner` (the phase announcement while it's up), and `battleOutcome` (`'victory'` | `'defeat'` | `null`) describe the turn flow. `phase` (`'deployment'` | `'battle'` while the map runs), `deploymentStep`, `deploymentMenu`, and `rosterMenu` describe the deployment phase. `screen` (`'title'` | `'battle'`) is which top-level screen is showing, and `battleSetup` (`{ mode: 'demo' }` | `{ mode: 'training', unitClass }`) which battle the map runs; they're the fields React writes (Play or picking a Training unit sets both), and `main.js` reacts by starting the map scene with `battleSetup` as its scene data.

### `src/bridge/commands.js`
`createCommandChannel()` → `{ send, subscribe }`: the React → Phaser direction of the bridge. React sends plain command objects and the running scene subscribes (unsubscribing when it shuts down). `gameCommands` is the app-wide instance. Commands: `hover-menu` / `select-menu` (`{ menu, index }`, where `menu` is the store field of an open menu), `confirm`, and `cancel` — the same inputs the keyboard produces, so the scene handles them through its existing input steps — plus `main-menu`, which leaves the battle for the title screen even while input is locked. Tested in `src/bridge/commands.test.js`.

### `src/bridge/views.js`
Pure snapshot functions that turn live game objects into frozen plain objects for the UI: `toUnitView` (stats plus the carried items as `{ id, label, quantity }`), `toDamagePopupView` (a floating number with a `kind` — `'damage'`, `'crit'`, `'miss'`, `'health'`, or `'mana'` — and the `text` to show: the bare number for damage, `Crit! N` for a crit, `Miss` for a miss, `+N HP` / `+N MP` for recovery), `toRosterEntryView` (a roster menu entry: id, name, sprite frame, placed flag), `toTurnView` (turn number, team, and "Player Phase" / "Enemy Phase" label from a turn state), `toPhaseBannerView` (a turn view plus an `id` and `durationMs` for the phase announcement), `toDialogView` (the dialog line being spoken: speaker, side, text, the stand-in sprite, whether the player skipped its typing, and the typing speed, with an `id` per line), `toTileAnchorView` (a map tile's edges as canvas fractions, which GridScene publishes as `menuAnchor` for the active unit whenever its action, skill, or item menu opens and again after the camera refits), plus `worldToScreen` (world point + `{ x, y, zoom }` camera view → pixels at the canvas's own resolution) and `toCanvasFraction` (canvas pixels → 0–1 fractions of the canvas) for placing map-anchored UI, which React positions in percentages. React never holds live `Unit` instances — a mutation like `takeDamage()` must be followed by publishing a fresh snapshot, which is what triggers the re-render. Tested in `src/bridge/views.test.js`.

### `src/ui/`
React renders the whole page, mounted by `mountUI(container)` into `#root` (see `index.html`). It renders synchronously, so the `#game` element the Phaser canvas goes in exists before `main.js` builds the game. The page, styled with the title screen's navy/gold theme (shared tokens on `:root` in `ui.css`), is a header, then the **stage** (the canvas plus the HUD overlay, framed in gold) with a **sidebar** beside it. The page fills the window: the stage fills the space left beside the sidebar, and Phaser's `Scale.RESIZE` keeps the canvas the same size (one canvas pixel per CSS pixel); on narrow windows the sidebar drops below the map and the stage is a full-width 4:3 box. HUD text is sized in `rem` and isn't scaled with the map, so it follows the browser's font size and zoom; animations fall back to plain fades under `prefers-reduced-motion`, and the header status is an `aria-live` region. Map-anchored UI (menus, banners, damage popups, dialogs) goes in the HUD overlay on top of the canvas; readouts that don't need to cover the map go in the header or sidebar. The HUD overlay has `pointer-events: none` so input falls through to the canvas; interactive panels (`.panel`) opt back in. Components read state through `useGameStore(selector)` — a thin `useSyncExternalStore` wrapper; selectors must return stored references, not freshly built objects. Current components: `App` (page root — always renders the battle layout, since `#game` must stay mounted, and covers it with `TitleScreen` while `screen` is `'title'`), `LoadingScreen` (mounted while `screen` is `'battle'`: covers the page with the title screen's backdrop and a bar filled from `mapLoadProgress`, which GridScene publishes from its loader's progress, then fades out once GridScene sets `mapReady` at the end of `create()`, so starting a battle never shows a blank canvas), `PageHeader` (wordmark plus a status slot holding `DeploymentBanner` or `TurnIndicator`, and an actions slot holding `SettingsButton` — a placeholder drop-down panel with no settings yet, in local state, that closes on a click elsewhere or Esc (stopped before it reaches Phaser) — and `MainMenuButton`, which shows once the map is ready and sends `main-menu`, so the player can return to the title at any time without pausing), `ControlsPanel` (sidebar key reference), `TitleScreen` (the full-viewport landing page: title, crest, and the Play/Training/Settings menu; driven by arrows + Enter/Z or the mouse, holds its menu selection in local state via the `actionMenu.js` helpers; Play starts the demo battle, Training swaps in a unit-class menu from `getTrainingActions` (Esc/X or right click goes back) whose choice starts a training battle, Settings is a placeholder), `DeploymentBanner` (header status: names the deployment phase and hints at the current step), `DeploymentMenu` (Place Units / Start, with Start greyed while disabled; like `RosterMenu`, centered on the map), `RosterMenu` (units available to deploy, each with its sprite via `UnitSprite`, which shows a sprite image by texture key), `PauseMenu` (the End Turn / Main Menu / Settings menu over a dimmed map), `UnitPanel` (sidebar card for the unit under the cursor: sprite, level, HP/MP meters, stats, and carried items, with a placeholder when nothing is hovered), `ActionMenu` (the open action menu with its highlighted entry, disabled entries greyed; input is handled by GridScene — like every map menu, its entries forward hover/click through `menuItemPointerProps` in `menuPointer.js`), `SkillMenu` (the active unit's skills with their mana cost, unaffordable ones greyed), `ItemMenu` (the active unit's items with how many are left, ones that would restore nothing greyed) — these three open beside the active unit through `useMenuBesideUnit`, which measures the menu and places it with the pure `placeMenuBesideTile` (`src/ui/menuPlacement.js`, tested): to the unit's right when it fits, otherwise its left, top lined up with the tile and kept on the stage — `DamagePopups` (floating damage and recovery numbers at the screen positions GridScene publishes, colored by kind and animated with a CSS rise-and-fade), `TurnIndicator` (header status during the battle: turn number and current phase), `PhaseBanner` (the full-width "Player Phase" / "Enemy Phase" sweep at the start of each phase, timed by the published `durationMs`), `DialogBox` (the conversation box along the bottom of the map: a 96px portrait frame on the speaker's side — the speaker's unit sprite at 3x stands in until there is portrait art — a gold name plate, and the line typing out with `getRevealedLength`, the untyped rest laid out invisibly so the box doesn't reflow; a blinking marker shows once the line is complete; a click anywhere on the map confirms), `BattleResult` (Victory / Defeat over a dimmed map, with the return-to-title hint; clicking it confirms). `App` sends `cancel` on a right click anywhere on the stage. Styles live in `ui.css`.

### `src/main.js`
Composition root. Mounts the React page first (which opens on the title screen and provides `#game`), then constructs the single `Phaser.Game` instance in `#game` (RESIZE scale mode, so the canvas matches `#game`'s size) with no scenes running, and subscribes to `gameStore` so that when `screen` becomes `'battle'` it adds and starts `GridScene` with `battleSetup` as scene data, and when it goes back to `'title'` it removes the scene (so the next Play starts a fresh battle). Phaser and React are started independently here and only communicate through `src/bridge/`. Should stay free of game logic.

### `src/assets/overworld.png`
Terrain art: the used area of the Tactical RPG Overworld Pack sheet (drawn at 3x; the original isn't kept in the repo) redrawn at 2x, so its 16px tiles are 32px. It's 42x63 tiles of blob autotile sets (grass, sand, water with 6 animation frames, deep water), mountains, forests, team-colored buildings and UI. Made with the `tileset` skill's `rescale-png.js`. Everything on it is cataloged in `.claude/skills/tileset/overworld-catalog.md`.
### `src/assets/` sprites
Unit sprite sheets `Villager_01_Idle.png` / `Villager_01_Move.png` (player) and `Soldier_03_Idle.png` / `Soldier_03_Move.png` (enemy): 4x4 grids of 32x32 frames (rows are facing directions, columns animation frames). Wired up through `sprites.js`; rows are down, left, right, up (`UNIT_SHEET.rows` in `tileset.js`). Units start out idling on the down row (so does the deployment roster), play the move sheet facing each step while walking, and idle facing their last step after they stop.
